# Wabi 문제 기록

## P-01. 에이전트 패널에 지시가 제출되지 않음 (해결됨)

- **언제**: 2026-08-28, Architecture와 Research-team에 첫 작업을 지시하던 시점
- **어디서**: tmux `product-team`, `Research-team` 세션의 Claude Code 패널
- **무엇이**: `tmux send-keys`로 보낸 지시가 입력창에만 남고 제출되지 않았습니다. 사용자가 직접 타이핑한 메시지도 같은 증상이었습니다.
- **어떻게**: 긴 텍스트와 `Enter`를 한 번에 보내면 TUI가 빠르게 들어온 입력을 붙여넣기로 처리하는 동안 뒤따라온 Enter가 함께 삼켜집니다. 대체로 시도한 `KPEnter`와 `-H 0d`는 제출 없이 입력창만 비워 메시지를 잃게 만들었습니다(이 과정에서 사용자 메시지 1건이 유실되어 다시 넣었습니다).
- **왜**: 입력 전달 속도와 TUI의 붙여넣기 판정이 겹쳤기 때문입니다. 네트워크나 세션 문제가 아니었습니다.

### 해결 방법

`.claude/bin/agent-send.sh`를 만들어 모든 지시를 이 스크립트로 보냅니다. 입력창을 비우고 → `-l`로 텍스트만 보내고 → `Enter`를 따로 누르고 → 제출 여부를 확인해 실패 시 한 번 더 누릅니다. 각 단계 사이 간격은 사용자 지시에 따라 **1초**로 고정합니다.

제출 판정에서 두 번 더 걸렸고 함께 고쳤습니다. 상태줄 문구가 `esc to interrupt`가 아니라 `paste again to expand`로 바뀌는 경우가 있어 문구 대신 입력창이 비었는지로 판정하도록 바꿨고, 제출된 메시지도 기록에 `❯`로 남는 데다 프롬프트 뒤 공백이 일반 공백이 아닌 U+00A0이어서 마지막 `❯` 줄만 보고 U+00A0을 제거하도록 고쳤습니다.

## P-02. 미검증 정보를 계획서에 그대로 옮김 (해결됨)

- **언제**: 2026-08-28, `Project-plan/discussion.md` 최초 작성 시점
- **어디서**: 계획서 6절 데이터 항목
- **무엇이**: 디자인 캔버스에 적혀 있던 비자 심사 기간, 세금 번호 미신청 시 세율, 계좌 개설 기한, 보험 증서 요구 여부를 확인 없이 계획서에 옮겼습니다.
- **어떻게**: 사용자가 "필요한 정보들은 직접 찾아서 확인한 뒤에 넣어야 한다"고 지적했습니다.
- **왜**: 디자인 캔버스는 화면을 채우기 위한 예시값을 담은 목업인데, 이를 확정된 사실로 취급했습니다.

### 해결 방법

계획서를 고쳐 **디자인 명세**(색상·타이포·간격·컴포넌트·화면 구성·모션 — 캔버스가 확정 사실)와 **제품 콘텐츠**(비자·세금·보험 등 현실 정보 — 확인 필요)를 분리했습니다. 콘텐츠는 조사로 확인된 값으로 교체하기 전에는 코드에 넣지 않으며, 확인되지 않은 항목은 임의로 채우지 않고 화면에서 뺍니다. `src/Front/common/data/tasks.ts`는 빈 배열로 두고 타입에 `sourceUrl` 필드를 추가해 값과 근거가 함께 보관되도록 했습니다. 국가별 실무 정보는 Research-team에 조사를 의뢰했습니다.

## P-03. 에이전트가 조사 도구 실패를 사이트 차단으로 단정 (해결됨)

- **언제**: 2026-08-28, Research-team 1차 조사 결과와 Architecture의 TechSpec 초안 검토 시점
- **어디서**: `Result/Data/워킹홀리데이_준비정보.json`, `Docs/State/TechSpec.md` 0절·7절
- **무엇이**: 여러 에이전트가 "도메인 접근 차단", "DNS 타임아웃"을 이유로 항목을 검증불가로 처리했습니다. 조사 결과 전체 43개 항목 중 `verified: true`는 20개(호주 3/15, 캐나다 7/14, 일본 10/14)에 그쳤습니다.
- **어떻게**: PM이 직접 확인한 결과 `immi.homeaffairs.gov.au`는 HTTP 200으로 1.2MB를 정상 수신하고, `nextjs.org`도 200이며 DNS 해석도 정상이었습니다. 실제로 막힌 곳은 `www.ato.gov.au`(브라우저 UA를 붙여도 403)와 `www.fairwork.gov.au`(연결 실패) 두 곳뿐이었습니다.
- **왜**: 에이전트의 웹 조회 도구가 실패한 것을 네트워크·사이트의 문제로 단정하고, bash `curl` 같은 다른 경로를 시도하지 않았습니다.

### 해결 방법

웹 조회 도구가 실패하면 곧바로 접근 불가로 기록하지 말고 bash `curl`로 재시도하되 필요 시 `-A`로 브라우저 User-Agent를 붙이도록 지시했습니다. Architecture는 이 방법으로 `nextjs.org` 원문을 열어 로컬 문서와 글자 단위로 일치함을 대조하고 TechSpec 0절·7절 서술을 정정했습니다. Research-team은 같은 방법으로 재조사 중이며, 호주 항목을 최우선으로 비자 나이·비용·심사 기간·잔고 증명액·체류 기간과 보험 의무 근거인 비자 조건 8501을 원문에서 확인합니다. 실제로 막힌 두 사이트는 대체 경로를 찾도록 했습니다.

## P-04. 보안 검토의 일반 등급 지적 4건 (해결됨)

- **언제**: 2026-08-28, Security의 `Docs/State/SecurityReview.md` 제출 시점
- **어디서**: `app/layout.tsx` 인라인 스크립트, localStorage 사용 범위, 파일 추가 시트, 저장소 비밀값 관리
- **무엇이**: 긴급 항목은 없으나, 지금 정해둔 방향(서버 없음, localStorage 기반, "서류는 기기에만 저장")이 구현 시점에 조용히 깨질 수 있는 위험 4건이 지적됐습니다.
- **어떻게**: `<script>`에 넣는 `dangerouslySetInnerHTML`은 HTML 이스케이프가 아니라 JS로 실행되므로, 나중에 변수를 보간하면 그 순간 주입 지점이 됩니다. 나머지는 localStorage에 개인식별정보 필드 추가 금지, 파일 저장 구현 시 서버 업로드 금지, 첫 커밋 전 비밀값 확인입니다.
- **왜**: 아직 해당 기능이 구현되지 않아 지금은 악용 가능한 결함이 없지만, 제약을 문서에 남기지 않으면 다음 차수에서 근거 없이 깨질 수 있습니다.

### 해결 방법

사용자 지시에 따라 Security가 이 제약들을 `Docs/State/TechSpec.md`에 선반영하고 있습니다. 파일 추가 시트 구현은 그 반영이 끝난 뒤에 착수합니다.

## P-05. 온보딩 제외와 D-day·비자 만료 값의 출처 충돌 (해결됨)

- **언제**: 2026-08-28, QA가 빈 상태 시나리오(EMPTY-01~15)를 추가하며 보고
- **어디서**: `Project-plan/discussion.md` 9절(제외 범위), `src/Front/common/data/tasks.ts`의 `COUNTRIES`
- **무엇이**: 이번 범위에서 온보딩(국가·출국일 입력)을 제외했는데, 홈 화면의 D-day와 '나' 화면의 출국일·비자 만료일은 온보딩 없이는 값의 출처가 없습니다.
- **어떻게**: 디자인 캔버스는 `COUNTRIES`에 국가별 출국일("9월 9일")과 비자 만료일("2027년 9월 8일")을 하드코딩해 두었습니다. 그러나 출국일은 조사로 확인할 수 있는 사실이 아니라 **이용자마다 다른 개인 값**입니다. 조사 결과로 채울 수 있는 것은 비자 나이 요건·비용·체류 허용 기간 같은 국가별 제도 정보뿐입니다.
- **왜**: 캔버스의 예시값을 사실로 취급하지 않기로 한 원칙(P-02)을 적용하는 순간, 출국일·비자 만료일을 채울 근거가 사라집니다. 국가 선택 자체는 '나' 화면의 국가 변경으로 가능하므로 온보딩이 필요 없지만, 날짜 입력 경로가 없으면 D-day는 영구히 빈 상태가 됩니다.

### 해결 방법 (2026-08-28 사용자 승인)

온보딩 전체가 아니라 **출국일 입력 한 가지만** 이번 범위에 넣는 것을 제안합니다. '나' 화면의 설정에 출국일 항목을 추가해 이용자가 날짜를 고르면 D-day를 계산하고, 비자 만료일은 조사로 확인된 국가별 체류 허용 기간을 출국일에 더해 산출합니다. 국가 선택은 캔버스에 이미 있는 '나' 화면의 국가 변경을 그대로 씁니다.

이렇게 하면 3단계 온보딩 화면을 만들지 않고도 D-day와 비자 만료일이 근거를 갖게 되며, 온보딩 화면 자체는 다음 차수로 남길 수 있습니다. 승인 시 `discussion.md` 9절의 포함/제외 범위를 함께 갱신합니다.

2026-08-28 사용자가 출국일 입력 추가를 승인했습니다. `discussion.md` 9절 범위를 갱신하고 10절에 상세 명세를 추가했습니다.

## P-06. 시간대에 따라 D-day와 출국일이 하루 앞으로 표시됨 (긴급, 해결됨)

- **언제**: 2026-08-28, QA가 QAPlan 시나리오를 실제로 실행하던 중 발견
- **어디서**: `src/Front/app-shell/state/wabiLogic.ts`의 `computeDDay`, `formatKoreanDate`
- **무엇이**: UTC보다 느린 시간대에서 D-day가 실제보다 하루 적게 표시되고, '나' 화면의 출국일도 하루 앞 날짜로 표시됩니다.
- **어떻게**: PM이 직접 재현했습니다. 출국일 `2026-09-09`, 오늘 `2026-08-28` 기준으로 `Asia/Seoul`·`UTC`·`Europe/London`은 `D-12`와 `2026년 9월 9일`이 나오지만, `America/Toronto`와 `America/Vancouver`는 `D-11`과 `2026년 9월 8일`이 나옵니다.
- **왜**: 날짜 전용 ISO 문자열(`2026-09-09`)을 `new Date()`로 파싱하면 **UTC 자정**으로 해석되는데, 거기에 로컬 기준인 `setHours(0,0,0,0)`과 `getFullYear`/`getMonth`/`getDate`를 섞어 썼습니다. UTC보다 느린 시간대에서는 그 UTC 자정이 전날 저녁에 해당하므로 날짜가 하루 앞으로 밀립니다.

지원 3개국 중 캐나다 전역이 이 조건에 해당합니다. 구현과 1차 확인이 모두 한국 시간대에서 이뤄져 그 환경에서는 재현되지 않았고, QA가 시나리오를 실제로 실행하고 나서야 드러났습니다. 시나리오 작성만으로는 잡히지 않는 종류의 결함이었습니다.

### 해결 방법

날짜 전용 문자열을 로컬 날짜로 파싱하는 헬퍼를 만들어 `computeDDay`·`formatKoreanDate`·`computeVisaExpiry` 세 함수가 모두 사용하도록 지시했습니다. 정규식으로 연·월·일을 나눈 뒤 `new Date(year, month-1, day)`로 만들면 로컬 자정이 됩니다. `computeVisaExpiry`는 파싱과 `toISOString`이 둘 다 UTC라 결과는 우연히 맞았지만 같은 취약한 패턴이므로 함께 정리합니다.

회귀 방지를 위해 `wabiLogic.ts`의 순수 함수에 대해 `TZ`를 `Asia/Seoul`·`UTC`·`America/Toronto`로 바꿔 가며 같은 입력에 같은 결과가 나오는지 확인하는 테스트를 추가하도록 했습니다. QA는 수정 후 두 시간대에서 재검증합니다.

### 수정 확인 (2026-08-28)

Front-end가 `parseLocalDateOnly`와 `formatDateOnly` 헬퍼를 추가하고 `computeDDay`·`computeVisaExpiry`·`formatKoreanDate` 세 함수가 모두 이를 쓰도록 통일했습니다. 회귀 테스트는 `wabiLogic.test.ts`로 추가되어 `npm run test:wabi-logic`으로 실행되며, 자기 자신을 `Asia/Seoul`·`UTC`·`America/Toronto` 세 시간대의 자식 프로세스로 재실행해 결과가 일치하는지 비교합니다.

PM이 독립적으로 재검증한 결과, 수정 전 실패하던 `America/Toronto`와 `America/Vancouver`를 포함해 지시 범위 밖이던 `Pacific/Honolulu`(UTC-10, 가장 극단적인 음수 오프셋)까지 다섯 시간대 모두 `D-12`·`2027-09-09`·`2026년 9월 9일`로 일치합니다. `npm run build`·`typecheck`·`test:wabi-logic` 모두 통과합니다.

QA가 `Asia/Seoul`과 `America/Toronto` 두 시간대에서 화면 단위 재검증을 진행합니다.

## P-07. 모든 버튼이 디자인 시스템 서체가 아닌 브라우저 기본 폰트로 렌더됨 (긴급, 해결됨)

- **언제**: 2026-08-28, 디자인 시스템을 claude.ai/design으로 동기화하며 미리보기를 렌더하던 중 발견
- **어디서**: `app/globals.css`
- **무엇이**: 앱의 모든 `<button>`이 Noto Sans KR이 아니라 브라우저 기본 폰트(Arial)로 렌더됩니다.
- **어떻게**: 실행 중인 앱에 헤드리스 브라우저로 접속해 `getComputedStyle`로 측정했습니다. `body`는 `"Noto Sans KR", "Noto Sans KR Fallback", system-ui, sans-serif`인데 `button`과 `nav button`은 `Arial`이었습니다.
- **왜**: `globals.css`가 `font-family`를 `body`에만 선언했는데, `<button>`·`<input>` 같은 폼 요소는 `font-family`를 상속하지 않고 브라우저 UA 기본값을 씁니다. `TextField`만 자신의 module CSS에서 `font-family`를 직접 지정하고 있어 예외적으로 정상이었습니다.

영향 범위는 `Button`·`Chip`·`Segment`·`TabBar`·`ListRow`의 체크/본문 버튼·`NextActionCard`의 CTA·`BottomSheet`의 닫기까지 사실상 모든 동작 요소입니다. 한글 폰트가 설치된 환경에서는 OS 대체 서체로 조용히 어긋날 뿐 깨지지 않아 눈으로는 발견되지 않았습니다. 폰트가 없는 컨테이너에서 미리보기를 렌더하자 버튼 글자만 두부(□)로 드러나 원인이 잡혔습니다.

### 해결 방법

`app/globals.css`에 폼 요소가 서체를 물려받도록 `button`·`input`·`select`·`textarea`에 `font-family: inherit`을 추가하도록 지시했습니다. 크기와 굵기는 각 컴포넌트의 module CSS 클래스가 지정하고 있고 클래스 선택자가 요소 선택자를 이기므로 덮이지 않습니다.

QA에는 눈으로 보는 확인으로는 잡히지 않는 종류이므로 **`getComputedStyle`로 실제 적용된 서체를 측정해 `body`와 대조하는** 회귀 시나리오를 추가하도록 했습니다.

## P-08. Chip이 한글 라벨에 mono 서체를 써서 글자가 깨짐 (해결됨)

## P-10. 이용자 파일 저장 기능을 도입했다가 철회함 (해결됨 — 방향 전환)

- **언제**: 2026-08-28. 계획서 14절로 도입을 정하고 16절로 명세를 세워 구현까지 마친 뒤, 같은 날 철회했습니다.
- **어디서**: 문서 탭 전체
- **무엇이**: 이용자가 여권 사본·보험 증서 같은 파일을 앱에 보관하는 기능입니다. IndexedDB 저장, AES-GCM 암호화, 파일별 키, 60일 자동 삭제, 위장 파일 검사까지 구현하고 검증을 마친 상태였습니다.
- **어떻게**: 사용자가 "앱에 비해 너무 큰 기능"이라고 판단해 철회를 지시했습니다.
- **왜**: 파일을 대신 보관하겠다는 약속 하나에 딸려 오는 것이 너무 많았습니다. 암호화, 키 파쇄, 보관 기간 약속과 그 약속을 지키는 실제 삭제, 확장자를 위장한 파일 검사, 미리보기 샌드박스 — **그중 하나만 빠져도 이용자에게 한 약속이 깨지는 구조**였습니다. 정보 전달이라는 앱의 목적에 비해 무게가 맞지 않았습니다.

이용자의 로컬 파일 경로를 참조하는 방식(File System Access API의 `showOpenFilePicker`)도 검토했습니다. MDN browser-compat-data를 직접 확인한 결과 **Safari가 데스크톱·iOS 모두 미지원, Firefox 미지원, 표준 상태 experimental**이었습니다. 모바일 우선인 이 앱에서 iOS 이용자가 기능을 통째로 못 쓰게 되므로 채택할 수 없었습니다.

### 해결 방법

문서 탭을 **메모 탭**으로 바꿨습니다. 남이 만든 파일을 대신 보관하는 것이 아니라 이용자가 직접 적어 두는 짧은 글이라, 위의 장치들이 필요 없습니다. `localStorage`에 `{ id, body, updatedAt }` 세 필드로 저장합니다.

서류 정보 자체는 이미 할 일 상세의 "준비물"이 전달하고 있어 정보 전달에는 구멍이 생기지 않았습니다.

**검토 기록은 지우지 않고 남겼습니다.** `SecurityReview.md` 6·7절(위협 경계 분석, 파일별 키 근거, IV 관리 주의사항, 매직 넘버 검사 시점)과 `QAPlan.md` 25절, `QAResult.md` 11절(철회 직전 통과한 KEY-01~04 결과)에 취소 표시와 사유만 달았습니다. 나중에 파일 저장을 다시 논의할 때 처음부터 반복하지 않기 위해서입니다.

### 남은 판단거리

Security 7-1절이 짚은 **앱 내 잠금**은 여전히 열려 있습니다. 지금 구조는 잠금 해제된 기기에서 습득자가 앱을 그냥 여는 경우를 막지 못합니다. 메모에 민감한 정보를 적지 말라는 안내로 대신하고 있으며, 계획서 9절의 다음 차수 항목에 기록해 두었습니다.

## P-11. 추천 항목이 디자인 토큰이 아닌 브라우저 기본 글자색으로 렌더됨 (해결됨)

- **언제**: 2026-08-28, 사용자가 "타이틀 칸에 비해 너무 강한 채도"라고 지적해 실측하던 중 발견
- **어디서**: `AddTaskSheet`의 추천 항목 제목 버튼
- **무엇이**: 색이 디자인 토큰 밖에 있었습니다. 다크에서 `rgb(255,255,255)` 순백, 라이트에서 `rgb(0,0,0)` 순흑이 나왔습니다. 토큰은 각각 `--strong: #f2f3f1`, `#121312`입니다.
- **어떻게**: 두 화면 모드에서 `getComputedStyle(...).color`를 재고 `--text`·`--strong` 토큰값과 대조했습니다.
- **왜**: 버튼에 `color`가 아예 지정되어 있지 않아 브라우저 기본값(`buttontext`)이 나왔습니다. **P-07과 같은 원인입니다** — `<button>`은 UA 기본값이 상속을 이깁니다. P-07에서는 `font-family`였고 여기서는 `color`입니다.

다크 모드에서 흰색이라 우연히 봐줄 만해 보였을 뿐이고, 화면 모드를 바꾸면 어긋나는 상태였습니다.

### 해결 방법

추천 항목의 글자색을 `--text`로, 고른 상태에서는 `--strong`으로 지정했습니다. 제목 입력칸(`--strong`)보다 한 단계 옅어 "추천은 제목을 채우는 보조 수단"이라는 위계도 함께 드러납니다.

같은 시트의 모든 버튼·입력·링크·텍스트를 훑어 계산된 색이 토큰 6개 중 하나와 일치하는지 대조했고, 토큰 밖의 색을 쓰는 요소는 더 없었습니다.

**P-07의 교훈이 `font-family`에만 적용되고 `color`에는 적용되지 않았습니다.** 앞으로 `<button>`에 새로 스타일을 줄 때는 상속되지 않는 속성(`font-family`, `color`, `font-size`, `line-height`, `letter-spacing`)을 함께 확인합니다.

## P-13. 메모 저장 실패가 조용히 묻히고 id가 겹칠 수 있었음 (해결됨)

- **언제**: 2026-08-28, 사용자가 "메모가 삭제되는 코드가 있는지" 확인을 요청해 훑던 중 발견
- **어디서**: `src/Front/common/storage/notes.ts`, `useWabiApp.ts`
- **무엇이**: 두 가지입니다. ① 저장 실패가 알려지지 않아 **화면에는 메모가 보이는데 실제로는 저장되지 않는** 상태가 됩니다. ② `note-${Date.now()}`라서 같은 밀리초에 만들어진 두 메모의 id가 겹치고, 그러면 하나를 지울 때 `filter`가 **둘 다** 지웁니다.
- **어떻게**: `Storage.prototype.setItem`이 `wabi:notes`에서만 예외를 던지게 만들어 재현했습니다.
- **왜**: `writeStoredNotes`의 `catch`가 비어 있었습니다. 프라이빗 모드나 용량 초과를 조용히 넘기려던 의도가, 실패를 숨기는 결과가 되었습니다.

메모는 개수 제한이 없는 유일한 데이터라 용량 한도에 닿을 수 있는 것도 메모뿐입니다.

### 해결 방법

**"조용히 무시한다"는 주석이 붙은 `catch`는 그 자체로 점검 대상입니다.** 무시해도 되는 실패인지, 이용자가 알아야 하는 실패인지 구분해야 합니다.

## P-14. 숨긴 요소가 자리를 차지하거나 아예 닿을 수 없었음 (일부 해결, 일부 의도된 선택)

- **언제**: 2026-08-28, 목록 여백을 실측하던 중 발견
- **어디서**: `NotesPanel`의 메모 삭제 버튼, `ListRow`
- **무엇이**: `visibility: hidden`으로 숨긴 삭제 버튼이 **자리는 그대로 차지해서**, 오른쪽에만 32px 여백을 준 것처럼 보였습니다. 또한 `visibility: hidden`은 포커스 대상에서도 빠져 **`Tab`으로 닿을 수 없었습니다**(25번 눌러 확인).
- **왜**: 안 보이게 하는 방법에 따라 레이아웃과 접근성에 다른 결과가 따라옵니다. `visibility: hidden`은 자리를 남기고 포커스를 막습니다.

### 해결 방법

메모 행과 할 일 행 모두 **폭 0에서 자라나는 방식**으로 바꿨습니다. 숨어 있을 때 자리를 차지하지 않고, 마우스를 올리면 오른쪽에서 밀고 들어옵니다.

구현 중 함정이 하나 더 드러났습니다 — `width: 0`을 줘도 **브라우저 버튼 기본 `padding`(1px 6px)** 때문에 12px이 남습니다. `padding`까지 0으로 눌러야 실제로 사라집니다.

할 일 행의 삭제 버튼은 **포커스만으로도 나타나** 키보드로 닿습니다. 홈 우측 패널의 메모 삭제 버튼은 여전히 마우스로만 닿지만, 메모 탭에 항상 보이는 48×48 삭제 버튼이 있어 지우는 길이 막히지 않으며 **사용자가 "모바일에서는 이 디자인이 좀 더 나은 것 같다"고 확인해 그대로 둡니다.**
