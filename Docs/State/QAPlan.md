## 0. 문서 목적과 전제

- 이 문서는 **아직 코드가 없는 시점**에 작성되었습니다. 실행 테스트는 하지 않았고, 구현 완료 후 아래 시나리오를 하나씩 수동(또는 자동화)으로 확인하는 용도입니다.
- 근거 우선순위: `discussion.md` 7절(동작 명세, 확정 사실) → 캔버스 05 섹션 스크립트(`Component` 클래스의 실제 로직, `WabiDesignSystem.dc.html:631~867`) → 캔버스 04 섹션(정적 컴포넌트 스펙). 캔버스의 색상·배치·모션은 그대로 따르되, 캔버스 상단의 라이트/다크·국가 전환 버튼(05 섹션 상단 pill 버튼)은 **디자인 캔버스 미리보기 전용 컨트롤**이며 실제 앱 UI가 아닙니다. 실제 앱에서 테마·국가는 discussion.md 7절대로 '나' 탭 설정에서 바꿉니다.
- `TASKS`/`GUIDE`/`PAIN`/`COUNTRIES`의 구체적 값(비자 심사 기간, 세율, 출국일 등)은 discussion.md 6.2절에 따라 **미확정 예시**입니다. 값 자체가 캔버스와 다르게 나와도 결함이 아니며, Research-team 산출물로 교체되었는지만 확인합니다. 아래 시나리오는 값이 아니라 **동작**을 검증합니다.
- 시나리오 ID는 `영역-번호` 형식이며, 회귀 테스트 시 체크리스트로 그대로 재사용할 수 있습니다.

| DETAIL-06 | 완료 취소 후 화면 유지 | 완료된 항목 상세에서 "완료 취소하기" 클릭 | 항목이 미완료로 바뀌지만 **상세 화면은 닫히지 않고 그대로 유지**되며, CTA가 "완료로 표시하기"로, 취소선/색상이 미완료 스타일로 즉시 갱신된다(캔버스 `undoDetail`은 `detail`을 null로 만들지 않음 — DETAIL-04와 다른 동작이므로 구분해서 확인). |
| DETAIL-07 | 마감 색상 | 긴급(urgent)이고 미완료인 항목의 상세 진입 | 마감 텍스트가 `alert` 색으로 표시된다. 완료 처리하면 "완료됨" 텍스트로 바뀌며 alert 색이 아닌 기본 색(muted)으로 바뀐다. |

| ADD-09 | **직접 추가한 할 일의 홈 노출 조건 — 노출되지 않는 경우** | 마감을 '이번 달' 또는 '도착 후'로 선택해 등록 | 홈 화면 "이번 주 할 일" 목록에 나타나지 않는다(할 일 탭 해당 세그먼트에서는 정상적으로 보임). |
| ADD-10 | 긴급 표시 연동 | 마감을 '오늘까지'로 선택해 등록 | 목록/홈에서 해당 항목이 긴급 항목 스타일(alert 테두리/텍스트, 7절 참고)로 표시된다(캔버스 `urgent: due === '오늘까지'`). '이번 주' 이하 다른 마감은 urgent가 아니다. |

## 11. 체크 원 vs 행 클릭 — 이벤트 분리 (교차 시나리오)

discussion.md 7절: "체크 토글은 행 전체가 아니라 체크 원에서만 발생하며, 행 클릭은 상세를 엽니다(이벤트 전파 차단)."

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| ROW-01 | 체크 원 클릭 — 상세 열리지 않음 | 홈/할 일 목록에서 체크 원(좌측 22px 원)만 정확히 클릭 | 완료 상태만 토글되고 상세 화면은 열리지 않는다. |
| ROW-02 | 행(제목/메타) 클릭 — 토글되지 않음 | 체크 원이 아닌 제목·메타·화살표 영역 클릭 | 상세 화면이 열리고, 완료 상태는 변경되지 않는다. |
| ROW-03 | 이벤트 전파 차단 검증 | 체크 원 클릭 시 이벤트 버블링으로 상세가 함께 열리는지 확인 | 체크 원 클릭 이벤트가 상위 행의 클릭 핸들러로 전파되지 않는다(`stopPropagation` 동작 확인, 개발자 도구로 이벤트 리스너 확인 가능하면 함께 확인). |
| ROW-04 | 연속 토글 | 체크 원을 빠르게 두 번 클릭 | 완료 → 미완료로 정확히 두 번 토글되며 중간에 상세가 열리지 않는다. |
| ROW-05 | 홈/할 일 화면 모두 동일 동작 | 홈의 "이번 주 할 일"과 할 일 탭 목록 각각에서 ROW-01~ROW-02 반복 | 두 화면 모두 동일하게 동작한다(공통 `ListRow` 컴포넌트 재사용 여부 확인). |

## 14. NEXT 카드 선택 규칙

discussion.md 7절: "NEXT 카드는 미완료 항목 중 첫 번째를 보여주고, 설명은 본문의 첫 문장만 씁니다." 캔버스 로직: `ALL.find(x => !done[x.id]) || ALL[0]`.

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| NEXT-01 | 첫 미완료 항목 노출 | 기본 데이터 상태로 홈 진입 | NEXT 카드 제목이 전체 목록(`TASKS` + 직접 추가한 할 일, phase 구분 없이 순서대로) 중 **가장 먼저 등장하는 미완료 항목**과 일치한다. |
| NEXT-02 | phase 무관 여부 | '현지 정착' 항목이 먼저 완료되고 '출국 전' 항목이 남아있는 상태 확인 | NEXT 카드는 phase로 필터링하지 않고 원본 배열 순서상 첫 미완료 항목을 그대로 보여준다(phase 우선순위가 없음에 유의). |
| NEXT-03 | 설명은 첫 문장만 | 본문이 여러 문장인 항목이 NEXT로 선택된 상태 | 카드 설명에는 본문 전체가 아니라 **마침표 기준 첫 문장**만 표시된다(캔버스 `next.body.split('.')[0] + '.'`). |
| NEXT-04 | 완료 처리 후 NEXT 갱신 | NEXT 카드에 뜬 항목을 완료 처리 | NEXT 카드가 즉시 그 다음 미완료 항목으로 교체된다. |
| NEXT-05 | 전체 완료 시 폴백 | 모든 항목을 완료 처리 | 미완료 항목이 없으므로 NEXT 카드는 목록의 첫 항목(`ALL[0]`)을 그대로 보여준다(빈 카드가 아님). CTA를 눌러도 이미 완료된 항목의 상세로 이동함을 확인한다. |
| NEXT-06 | CTA 동작 | NEXT 카드의 "지금 하기" 클릭 | 해당 항목의 상세 화면이 열린다. |
| NEXT-07 | 직접 추가한 할 일도 후보에 포함 | 마감이 이른(예: '오늘까지') 새 할 일을 원본 `TASKS`보다 먼저 등장하도록 추가할 수 있는지 확인 | 직접 추가한 할 일도 `ALL` 배열에 포함되어 NEXT 후보가 될 수 있다(원본 TASKS 뒤에 추가되므로, 실제로 NEXT가 되려면 그 앞의 모든 항목이 완료되어 있어야 함 — 배열 순서 규칙을 정확히 확인). |

## 15. 진행률 계산

discussion.md 7절: "진행률은 기본 할 일 + 직접 추가한 할 일을 합쳐 계산합니다." 캔버스: `ALL = TASKS.concat(custom)`.

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| PROG-01 | 홈 전체 진행률 초기값 | 초기 데이터 상태(완료 표시된 기본 항목 수 확인) | 홈 "준비 진행률" 라벨이 "완료 수 / 전체 수"와 정확히 일치하고, 프로그레스바 폭이 그 비율(%)과 일치한다. |
| PROG-02 | 기본 항목 완료 시 갱신 | 기본 `TASKS` 항목 하나를 완료 처리 | 분모(전체 수)는 변하지 않고 분자(완료 수)만 1 증가, 라벨/바 즉시 갱신. |
| PROG-03 | 직접 추가 시 분모 증가 | 할 일 추가 시트로 새 항목 등록 | 전체 수가 1 증가한다(완료 여부와 무관하게 분모에 포함). |
| PROG-04 | 직접 추가 항목 완료 시 분자 증가 | PROG-03에서 추가한 항목을 완료 처리 | 완료 수가 1 증가한다(기본 항목과 동일하게 취급됨을 확인). |
| PROG-05 | phase별 진행률과 전체 진행률 구분 | 할 일 탭에서 phase별 "n/m"과 홈의 전체 "n/m"을 동시에 비교 | 두 값은 서로 다른 모수를 쓴다(phase 진행률은 해당 phase 항목만, 홈 진행률은 전체 항목). 둘 다 직접 추가한 할 일을 포함해 재계산된다. |
| PROG-06 | 분모 0 방지(엣지 케이스) | 특정 phase에 항목이 하나도 없는 상태를 만들 수 있는지 확인(데이터 구조상 가능하다면) | 0으로 나누어 `NaN%`가 표시되지 않는다(캔버스 원본은 이 케이스를 방어하지 않으므로, 실제 데이터에서 발생 가능한지와 구현 시 방어 로직이 있는지 확인 필요). |

## 19. 빈 상태(빈 데이터) 시나리오

`src/Front/common/data/tasks.ts` 확인 결과, Research-team 조사 완료 전까지 `COUNTRIES`, `TASKS`, `GUIDE.pre`, `GUIDE.post`, `PAIN`가 모두 빈 배열입니다. 이는 "코드가 없어서"가 아니라 **데이터가 의도적으로 비어 있는 상태**이며, 조사 산출물이 도착하기 전까지 실제로 이 상태로 배포/미리보기될 수 있습니다. 따라서 이 절의 시나리오는 "나중에 값이 채워지면 저절로 해결되는 문제"로 넘기지 말고, 빈 배열 상태 자체에서 앱이 예외 없이 렌더되는지를 반드시 확인해야 합니다.

캔버스 05 섹션 원본 스크립트는 이 빈 상태를 가정하지 않고 만들어졌습니다(`ALL.find(x => !done[x.id]) || ALL[0]`처럼 배열이 비어 있으면 `undefined`가 나오는 로직, `doneCount / total`처럼 분모가 0이 될 수 있는 나눗셈 등). 그대로 포팅하면 런타임 에러나 `NaN`/`Infinity` 표시로 이어질 수 있으므로, 구현 시 이 분기들이 방어되었는지가 이 절의 핵심 확인 대상입니다.

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| EMPTY-01 | 홈 D-day 표시 | `COUNTRIES`/`TASKS` 빈 배열 상태로 홈 화면 진입 | 출국일 정보가 없으므로 "D-NaN", "D-undefined" 같은 값이 아니라 정의된 빈 상태 문구(예: "출국일을 설정해 주세요") 또는 안전한 placeholder가 표시된다. 콘솔에 런타임 에러가 없다. |
| EMPTY-02 | 홈 진행률 — 분모 0 방지 | 위 상태에서 홈 "준비 진행률" 블록 확인 | `doneCount=0, total=0`이 되어도 "NaN%"나 "Infinity%"가 렌더되지 않는다. "0 / 0"을 그대로 보여주거나 진행률 블록 자체를 빈 상태로 대체하는 두 방식 중 하나를 택하되, 아래 EMPTY-07(할 일 phase별 진행률)에도 동일한 방식이 일관되게 적용되는지 확인한다. |
| EMPTY-03 | NEXT 카드 — 후보 없음 | `TASKS`가 비어 있고 직접 추가한 할 일도 없는 최초 진입 상태에서 NEXT 카드 확인 | 원본 로직(`ALL.find(...) || ALL[0]`)을 그대로 포팅했다면 전체 배열이 비어 `next`가 `undefined`가 되어 `next.title` 등에 접근할 때 크래시할 수 있다. 크래시 없이 "지금 준비할 일이 없습니다" 류의 전용 빈 상태 카드가 표시되는지 확인한다 — Frontend 구현에서 이 분기가 빠지지 않았는지 특히 주의해서 본다. |
| EMPTY-04 | NEXT 카드 — CTA 비활성화 | EMPTY-03 상태에서 "지금 하기" 버튼 유무 확인 | 이동할 상세 항목이 없으므로 CTA가 숨겨지거나 비활성화되고, 존재하지 않는 항목의 상세로 이동을 시도하지 않는다. |
| EMPTY-05 | 이번 주 할 일 — 빈 목록 문구 | 홈 "이번 주 할 일" 섹션 확인 | 목록이 비어 있을 때 빈 여백만 남지 않고 "아직 할 일이 없습니다" 류의 빈 상태 문구가 보인다. |
| EMPTY-06 | 할 일 화면 — 세그먼트별 빈 목록 | 할 일 탭 진입 후 출국 전 / 현지 정착 세그먼트 각각 확인 | 두 세그먼트 모두 목록이 비어 있고 각각 빈 상태 문구가 표시된다. 세그먼트 전환 자체는 데이터 유무와 무관하게 정상 동작한다. |
| EMPTY-07 | 할 일 화면 — phase 진행률 | 세그먼트별 진행률("n/m", 프로그레스바) 확인 | EMPTY-02와 동일한 규칙으로 "0/0"이 그대로 보이거나 진행률 블록이 빈 상태로 대체되며, `NaN%` 폭의 프로그레스바가 렌더되지 않는다. |
| EMPTY-08 | 데이터 추가 시 정상 상태로 전환 | 빈 상태에서 할 일 추가 시트로 항목 1개 등록 | `TASKS`가 비어 있어도 추가 시트는 정상적으로 열리고 등록할 수 있다. 등록 후에는 진행률이 "1/1" 등으로, NEXT 카드도 방금 추가한 항목으로 정상 전환되어 EMPTY-01~07의 빈 상태 문구가 사라진다. |

**확인 필요(Frontend/PM 재확인 요청)**: `discussion.md` 9절은 온보딩(국가·출국일 입력) 3단계를 이번 구현 범위에서 제외했습니다. 그런데 `COUNTRIES`가 비어 있는 한 나 화면에서 국가를 바꿀 대상 자체가 없고(EMPTY-12/13), 홈의 D-day도 계산할 근거가 없습니다(EMPTY-01). 즉 온보딩 없이도 최소 1개 국가 데이터는 있어야 앱이 "정상 상태"로 보일 수 있다는 뜻인데, 그 최소 데이터가 언제 채워지는지(Research-team 산출물 도착 시점 vs 그 전 임시값)가 현재 문서들에 명시되어 있지 않습니다. 이 절의 빈 상태 시나리오는 "그 전까지 최소한 깨지지는 않아야 한다"는 하한선을 확인하는 용도이지, 온보딩 없이 빈 상태를 계속 노출해도 된다는 뜻은 아니므로 범위를 다시 확인할 필요가 있습니다.

### 20.5 클라이언트 날짜 계산 — 빌드 시점 고정 방지 (10.3절)

> discussion.md 10.3절: "오늘 날짜는 반드시 클라이언트에서 계산합니다. 이 라우트는 정적 프리렌더 대상이므로 서버 렌더 시점에 `new Date()`를 쓰면 빌드 시점 날짜로 고정되고, 하이드레이션 불일치도 발생합니다."

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| DAY-14 | 정적 HTML에 날짜가 박혀 있지 않음 | `next build` 산출물의 정적 프리렌더 HTML(서버가 실제로 응답하는 첫 HTML, "페이지 소스 보기"로 확인 가능)에서 D-day 값 확인 | 서버가 내려주는 HTML 자체에는 특정 날짜로 계산된 D-day 숫자가 박혀 있지 않아야 한다(첫 페인트에는 비어 있거나 placeholder이고, 클라이언트 마운트 후 `new Date()`로 계산되는 구조인지 소스 코드에서 함께 확인 — `useEffect`/클라이언트 컴포넌트 여부). |
| DAY-15 | 하이드레이션 불일치 없음 | 프로덕션 빌드(`next build && next start`)로 페이지를 브라우저에서 로드 | 콘솔에 React 하이드레이션 불일치 경고("Text content did not match", "Hydration failed" 등)가 발생하지 않는다. |
| DAY-16 | **빌드 후 하루 경과 재현 — 시스템/브라우저 시간 조작** | ① 빌드는 그대로 둔 채 OS 또는 브라우저의 시스템 시계를 하루 뒤로 바꾸고 새로고침하거나, ② Chrome DevTools의 Sensors 패널(또는 동급 기능)로 클라이언트 `Date`를 하루 뒤로 override한 뒤 새로고침 | D-day 값이 멈춰 있지 않고 새 "오늘" 기준으로 갱신된다(숫자가 1 감소하거나, DAY-07/08의 D-DAY↔D+1 경계를 넘어간다). 값이 그대로라면 날짜 계산이 서버·빌드 시점에 고정되어 있다는 뜻이므로 **실패로 기록**한다. |
| DAY-17 | 빌드 후 하루 경과 재현 — 재배포 없이 확인하는 대안 | 빌드 서버의 시스템 시간을 바꾸기 어려운 환경이라면, 한 번 빌드해 정적 HTML을 고정시킨 뒤 **서버는 그대로 두고 클라이언트 쪽에서만** DAY-16의 DevTools 시간 override(또는 브라우저 콘솔에서 `Date`를 하루 뒤로 mock)를 적용해 새로고침 | 서버를 재시작하거나 재배포하지 않아도 D-day가 클라이언트 쪽 "오늘"을 기준으로 다시 계산되어 표시된다. 이는 날짜 계산이 서버 렌더 시점이 아니라 브라우저 실행 시점에 일어난다는 것을 재배포 없이 증명하는 것이 핵심이다. |

- 출국일의 `localStorage` 저장 범위·경계는 이 QA 문서의 범위가 아니라 Security 검토서 2절을 따릅니다(discussion.md 10.3절 참고).

데이터의 `sourceUrl`을 화면에 노출하는 기능입니다. 비자·세금·보험처럼 틀리면 실제 손해로 이어지는 정보이므로 원문을 확인할 수 있게 하는 것이 목적입니다. 정보 예산을 지키기 위해 **목록이 아니라 상세에서만** 노출한다는 것이 이 절 시나리오 전체의 전제입니다.

### 23.1 노출 위치 (13.1절)

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| SRC-01 | 할 일 상세 — 출처 노출 | `sourceUrl`이 있는 할 일의 상세 화면 진입 | 준비물 목록 아래에 출처 줄이 표시된다. |
| SRC-02 | 가이드 답변 — 출처 노출 | `sourceUrl`이 있는 가이드 질문의 답변 화면 열기 | 대처법(`points`) 목록 아래에 출처 줄이 표시된다. |
| SRC-03 | 어려움 답변 — 출처 노출 | `sourceUrl`이 있는 어려움 항목의 답변 화면 열기 | 대처법 목록 아래에 출처 줄이 표시된다. |

## 24. 폰트 상속 회귀 — 버튼·입력 요소 (2026-08-28 결함 발견, Frontend 수정 중)

`app/globals.css`가 `font-family`를 `body`에만 선언해 두었는데, `button`과 `input`은 브라우저 기본 UA 스타일시트상 폰트를 **부모로부터 상속하지 않는 요소**라 이 규칙이 적용되지 않는다. 그 결과 body는 Noto Sans KR로 렌더되는데 버튼류는 브라우저 기본 폰트(예: Arial)로 렌더되는 결함이 실제로 발견됐다(`getComputedStyle`로 직접 측정: body는 Noto Sans KR, `button`은 Arial).

**이 결함은 눈으로 보는 확인만으로는 잘 잡히지 않는 종류다.** Noto Sans KR과 시스템 기본 산세리프체는 한글·영숫자 렌더링이 육안으로는 비슷해 보일 수 있고, 화면 스크린샷만으로는 놓치기 쉽다. 그래서 아래 시나리오는 전부 **`getComputedStyle`로 실제 적용된 `font-family` 값을 읽어 `body`의 값과 문자열로 대조**하는 방식으로만 확인한다. 육안 확인은 보조 수단으로만 쓰고, 통과 판정의 근거로 쓰지 않는다.

측정 방법(모든 ID 공통): 헤드리스 브라우저에서 대상 요소를 얻어 `getComputedStyle(element).fontFamily`를 읽고, 같은 방식으로 얻은 `getComputedStyle(document.body).fontFamily`와 **완전히 동일한 문자열**인지 비교한다. 다르면(특히 대상 요소의 첫 번째 폰트가 `Arial`, `-apple-system`, `system-ui` 같은 브라우저 기본값으로 나오면) 실패로 기록한다.

| ID | 대상 | 절차 | 기대 결과 |
|---|---|---|---|
| FONT-01 | `Button` (primary/secondary/disabled 각 variant) | 각 variant 버튼 하나씩 렌더된 화면에서 요소를 찾아 `getComputedStyle`로 `font-family` 측정. **정정**: 이 컴포넌트는 앱 화면 어디에도 실제로 쓰이지 않는다(2026-08-28 확인). 대신 `ds-bundle/components/general/Button/Button.html`(디자인 시스템 미리보기 카드, `file://`로 열람, 개발 서버 불필요)이 Primary/Secondary/Disabled/ActionPair 네 variant를 모두 실제로 렌더하므로 여기서 측정한다. 판정 기준은 앱의 `body` 문자열이 아니라 **이 카드 자체의 `body` 계산값**(카드가 별도 CSS 진입점을 써서 next/font 합성 폴백 이름이 빠짐)과 대조한다. | 네 variant 모두 `font-family`가 그 카드의 `body`와 완전히 동일하다. |
| FONT-02 | `Chip` | Chip이 쓰인 화면(국가 선택 칩처럼 한글 라벨을 담는 곳, 문서 목록 확장자 배지처럼 라틴 문자만 담는 곳 둘 다)에서 측정 | `body`와 동일. **정정 이력**: 최초 실행(2026-08-28) 때는 `Chip.module.css`가 처음부터 `font-family: var(--font-mono), monospace`를 쓰고 있어 이를 "상속 누락 버그와는 무관한 설계 의도"로 판정했으나, 이후 Chip이 국가 선택처럼 **한글 라벨도 담는 컴포넌트**라는 점이 확인되어 이 판정이 틀렸음이 드러났다. mono 서체는 한글 글리프를 담지 못해 한글 라벨이 깨지는 실제 결함이었다. Frontend에 본문 서체(13px, 미선택 500 / 선택 700, discussion.md 3.2절 `label` 규격)로 맞추도록 지시했고, 올바른 기대값은 다시 "`body`와 동일"이다. 최신 판정 기준은 아래 FONT-11 표를 따른다. |
| FONT-03 | `Segment` (탭 역할 버튼) | 할 일 화면의 "출국 전"/"현지 정착" 세그먼트 버튼에서 측정 | `body`와 동일. |
| FONT-04 | `TabBar` (하단/사이드바 탭 버튼) | "홈"/"할 일"/"문서"/"나" 탭 버튼 각각에서 측정 | `body`와 동일. |
| FONT-05 | `ListRow` — 체크 버튼(`checkButton`) | 할 일 목록 행의 체크 원 버튼에서 측정 | `body`와 동일. |
| FONT-06 | `ListRow` — 본문 버튼(행 클릭 영역) | 같은 행의 제목·메타를 감싼 버튼에서 측정 | `body`와 동일. |
| FONT-07 | `NextActionCard`의 CTA 버튼 | 홈 화면 NEXT 카드의 "지금 하기" 버튼에서 측정 | `body`와 동일. |
| FONT-08 | `BottomSheet`의 닫기 버튼 | 아무 시트나 열어 상단 딤 영역의 공용 닫기 버튼(`aria-label="닫기"`)에서 측정 | `body`와 동일. |
| FONT-09 | `TextField` (`input` 요소) | 할 일 추가 시트의 제목 입력란(`input`)에서 측정 | `body`와 동일. |
| FONT-10 | 총괄 스냅샷 | FONT-01~09에서 측정한 `font-family` 값을 한 번에 표로 모아 `body` 값과 나란히 비교 | 예외 없이 전부 일치한다. 하나라도 다르면 그 컴포넌트를 특정해 실패로 기록한다(전체를 "실패"로 뭉뚱그리지 않는다). |

**수정 방향(참고, 결정은 Frontend 담당)**: `button`/`input`/`select`/`textarea`에 `font-family: inherit`를 명시하는 것이 일반적인 해결책이지만, 이 QA 시나리오는 방법을 규정하지 않고 결과(측정값 일치 여부)만 확인한다.

### FONT-11 · FONT-12 · FONT-13 — 한글 라벨이 mono 서체로 깨지는 결함 (2026-08-28 추가 발견, Chip 외 SourceLink도 해당)

FONT-02 재검토 과정에서, 상속 누락과는 별개로 **Chip 자체가 처음부터 `font-family: var(--font-mono)`를 명시하고 있어 한글 라벨(국가 선택 칩 등)이 깨지는 결함**이 추가로 발견됐다. Frontend에 discussion.md 3.2절의 `label` 규격(13px, 미선택 500 / 선택 700, 본문 서체)에 맞추도록 지시했다.

이어서 같은 종류의 결함이 **`SourceLink`에도 있다는 것이 정정 보고됐다**. `SourceLink`가 그리는 문구는 "출처 {도메인}" 형태로 앞에 한글 라벨("출처")이 붙는데, 링크 전체가 통째로 mono 처리돼 있었다면 도메인뿐 아니라 "출처"라는 한글까지 깨진다. 그래서 mono 허용 목록은 애초 생각했던 "`NextActionCard`의 NEXT 캡션과 `SourceLink`의 도메인" 두 곳이 아니라 **`NextActionCard`의 NEXT 캡션 한 곳으로만 좁혔고**, `SourceLink`는 "출처" 라벨(본문 서체)과 도메인(mono)을 요소 자체를 분리해 서로 다른 서체를 쓰도록 Frontend에 지시했다. 아래 세 시나리오로 확인한다.

| ID | 대상 | 절차 | 기대 결과 |
|---|---|---|---|
| FONT-11 | 전 컴포넌트 — **콘텐츠 성격과 서체 일치 여부 전수 확인** | FONT-01~09 각 요소 + `SourceLink`의 한글 라벨 부분(아래 FONT-13 참고)의 `getComputedStyle().fontFamily`를 한 번에 표로 정리 | **한글(또는 한글이 섞일 수 있는) 콘텐츠를 담는 요소는 전부 `body`와 동일한 패밀리**(Button/Chip/Segment/TabBar/ListRow/NextActionCard 본문/BottomSheet 닫기/TextField/`SourceLink`의 "출처" 라벨 부분). **`var(--font-mono)`(JetBrains Mono)는 `NextActionCard`의 "NEXT" 캡션 한 곳으로만 한정**된다(**정정**: `SourceLink`의 도메인 부분은 mono 허용 목록에서 제외 — 이유는 아래 FONT-13 참고). 이 한 곳을 제외한 어디에서도 mono 패밀리가 나오면 실패로 기록한다(Chip이 여전히 mono라면 이 시나리오에서 실패로 잡힌다). |
| FONT-12 | `Chip` — 크기·굵기 | 미선택 상태는 문서 탭의 확장자 배지(앱 화면에 실제 렌더)에서 측정한다. **선택 상태는 앱 화면 어디에도 렌더되지 않으므로**(2026-08-28 확인) `ds-bundle/components/general/Chip/Chip.html`의 `Selectable` story(`selected=true`로 렌더된 "호주" 칩)에서 측정한다. 두 상태 모두 `getComputedStyle().fontSize`와 `getComputedStyle().fontWeight` 측정 | 미선택: `13px` / `500`. 선택: `13px` / `700`. (현재 코드의 `font-size: 12px`는 discussion.md 3.2절 `label` 규격인 13px과 다르므로, 수정 후 13px로 바뀌었는지도 함께 확인한다.) |
| FONT-13 | `SourceLink` — **한 요소 안에서 서체가 두 개로 섞이는 경우, 부분별로 따로 측정** | `SourceLink`가 렌더하는 "출처 {도메인}" 링크에서 "출처" 라벨 부분과 도메인 부분이 각각 별도 요소(예: `<span>`)로 분리돼 있는지 먼저 확인한 뒤, 두 부분의 `getComputedStyle().fontFamily`를 따로 측정 | **정정**: `SourceLink`는 "출처"(한글) 뒤에 도메인이 바로 이어지는 하나의 문구라, 링크 전체를 통째로 mono 처리하면 "출처"까지 깨진다. 라벨("출처") 부분은 `body`와 동일한 패밀리여야 하고, 도메인 부분만 `var(--font-mono)`여야 한다. 링크 전체(`<a>` 요소 자체)에 통짜로 하나의 `font-family`만 걸려 있고 내부에 분리된 요소가 없다면, 그 자체로 이 시나리오는 실패다(측정 이전에 마크업 구조부터 확인). |

**실행 상태**:
