## 0. 문서 목적과 전제

- 이 문서는 **아직 코드가 없는 시점**에 작성되었습니다. 실행 테스트는 하지 않았고, 구현 완료 후 아래 시나리오를 하나씩 수동(또는 자동화)으로 확인하는 용도입니다.
- 근거 우선순위: `discussion.md` 7절(동작 명세, 확정 사실) → 캔버스 05 섹션 스크립트(`Component` 클래스의 실제 로직, `WabiDesignSystem.dc.html:631~867`) → 캔버스 04 섹션(정적 컴포넌트 스펙). 캔버스의 색상·배치·모션은 그대로 따르되, 캔버스 상단의 라이트/다크·국가 전환 버튼(05 섹션 상단 pill 버튼)은 **디자인 캔버스 미리보기 전용 컨트롤**이며 실제 앱 UI가 아닙니다. 실제 앱에서 테마·국가는 discussion.md 7절대로 '나' 탭 설정에서 바꿉니다.
- `TASKS`/`GUIDE`/`PAIN`/`COUNTRIES`의 구체적 값(비자 심사 기간, 세율, 출국일 등)은 discussion.md 6.2절에 따라 **미확정 예시**입니다. 값 자체가 캔버스와 다르게 나와도 결함이 아니며, Research-team 산출물로 교체되었는지만 확인합니다. 아래 시나리오는 값이 아니라 **동작**을 검증합니다.
- 시나리오 ID는 `영역-번호` 형식이며, 회귀 테스트 시 체크리스트로 그대로 재사용할 수 있습니다.

| ID | 시나리오 | 절차 | 기대 결과 |

| DETAIL-02 | 뒤로 가기 | 상세 화면 상단 '‹' 클릭 | 상세가 닫히고 원래 목록 화면으로 돌아간다. |
| DETAIL-03 | 준비물 없음 처리 | 준비물(`items`)이 빈 항목인 할 일 상세 진입 | "준비물" 라벨과 목록 영역이 아예 표시되지 않는다(빈 배열이면 섹션 자체를 숨김, 캔버스 `detailHasItems` 로직). |
| DETAIL-04 | 완료 처리 CTA | 미완료 항목 상세에서 "완료로 표시하기" 클릭 | 해당 항목이 완료 처리되고 **상세 화면이 자동으로 닫힌다**(캔버스 `completeDetail`이 toggle 후 `detail: null`로 설정). 목록으로 돌아가면 해당 항목이 완료 스타일로 보인다. |
| DETAIL-05 | 완료 취소 CTA | 완료된 항목 상세 진입 | CTA 라벨이 "완료됨"(비활성 스타일, sunken 배경)으로 바뀌고, 그 아래 "완료 취소하기" 보조 버튼이 추가로 나타난다. |
| DETAIL-06 | ~~완료 취소 후 화면 유지~~ **→ 완료 취소 후 상세 닫힘으로 스펙 정정 (discussion.md 18.2절, 2026-08-28)** | 완료된 항목 상세에서 "완료 취소하기" 클릭 | **정정**: 이 시나리오는 원래 캔버스 동작(`undoDetail`이 `detail`을 null로 만들지 않음)을 근거로 "상세 유지"를 기대값으로 적었으나, 실제 빌드에서 사용자가 이를 결함으로 지적했다 — "완료로 표시하기"는 닫히는데 "완료 취소하기"만 열려 있는 것은 두 버튼이 같은 자리에 있는데 결과가 어긋나는 것이라는 지적이다. **새 기대값**: 항목이 미완료로 바뀌고 `completeDetail`과 똑같이 **상세 화면이 닫히며 이전 화면으로 돌아간다**(DETAIL-04와 이제 같은 동작). 상세로 돌아간 목록에서 그 항목이 미완료 스타일(취소선 해제 등)로 보이는지도 함께 확인한다. 이 정정 전 버전의 기대값(상세 유지)이 나오면 그것을 실패로 기록한다. |
| DETAIL-07 | 마감 색상 | 긴급(urgent)이고 미완료인 항목의 상세 진입 | 마감 텍스트가 `alert` 색으로 표시된다. 완료 처리하면 "완료됨" 텍스트로 바뀌며 alert 색이 아닌 기본 색(muted)으로 바뀐다. |

| ADD-02 | **제목이 비면 등록 버튼 비활성** | 제목 입력란을 비운 채(또는 공백만 입력) | "등록하기" 버튼이 비활성 스타일(연한 배경/muted 텍스트)로 표시되고 클릭해도 등록되지 않는다(공백 trim 후 빈 문자열이면 비활성 유지). |
| ADD-03 | 제목 입력 시 활성화 | 제목에 텍스트 입력 | 버튼이 활성 스타일(ink 배경/onInk 텍스트, 700 굵기)로 바뀐다. |
| ADD-04 | 시점 선택 | '출국 전' / '현지 정착' 클릭 | 선택된 쪽이 강조 스타일로 바뀐다. |
| ADD-05 | 마감 선택 | '오늘까지' / '이번 주' / '이번 달' / '도착 후' 중 선택 | 선택된 옵션만 강조되고 나머지는 해제된다(단일 선택). |
| ADD-06 | 등록 성공 시 목록 반영 | 제목 입력 + 시점/마감 선택 후 "등록하기" 클릭 | 시트가 닫히고, 새 항목이 선택한 시점의 할 일 목록 끝에 추가된다. 태그가 "{시점} · 직접 추가"로 표시된다. |
| ADD-07 | 등록 후 세그먼트 자동 전환 | 할 일 탭이 '출국 전' 세그먼트로 열려 있는 상태에서, 추가 시트에서 시점을 '현지 정착'으로 바꿔 등록 | 등록 완료 후 할 일 화면의 세그먼트가 자동으로 '현지 정착'으로 전환되어 방금 추가한 항목이 바로 보인다(캔버스 `submitTask`가 `phase: ph`로 상태를 함께 바꿈). |
| ADD-08 | **직접 추가한 할 일의 홈 노출 조건 — 노출되는 경우** | 마감을 '오늘까지' 또는 '이번 주'로 선택해 등록 | 홈 화면 "이번 주 할 일" 목록에 해당 항목이 함께 나타난다. |
| ADD-09 | **직접 추가한 할 일의 홈 노출 조건 — 노출되지 않는 경우** | 마감을 '이번 달' 또는 '도착 후'로 선택해 등록 | 홈 화면 "이번 주 할 일" 목록에 나타나지 않는다(할 일 탭 해당 세그먼트에서는 정상적으로 보임). |
| ADD-10 | 긴급 표시 연동 | 마감을 '오늘까지'로 선택해 등록 | 목록/홈에서 해당 항목이 긴급 항목 스타일(alert 테두리/텍스트, 7절 참고)로 표시된다(캔버스 `urgent: due === '오늘까지'`). '이번 주' 이하 다른 마감은 urgent가 아니다. |
| ADD-11 | 취소 | 제목을 입력한 뒤 "취소" 클릭 | 시트가 닫히고 항목이 추가되지 않는다. 다시 열면 입력값이 초기화되어 있다. |

## 11. 체크 원 vs 행 클릭 — 이벤트 분리 (교차 시나리오)

discussion.md 7절: "체크 토글은 행 전체가 아니라 체크 원에서만 발생하며, 행 클릭은 상세를 엽니다(이벤트 전파 차단)."

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| ROW-01 | 체크 원 클릭 — 상세 열리지 않음 | 홈/할 일 목록에서 체크 원(좌측 22px 원)만 정확히 클릭 | 완료 상태만 토글되고 상세 화면은 열리지 않는다. |
| ROW-02 | 행(제목/메타) 클릭 — 토글되지 않음 | 체크 원이 아닌 제목·메타·화살표 영역 클릭 | 상세 화면이 열리고, 완료 상태는 변경되지 않는다. |
| ROW-03 | 이벤트 전파 차단 검증 | 체크 원 클릭 시 이벤트 버블링으로 상세가 함께 열리는지 확인 | 체크 원 클릭 이벤트가 상위 행의 클릭 핸들러로 전파되지 않는다(`stopPropagation` 동작 확인, 개발자 도구로 이벤트 리스너 확인 가능하면 함께 확인). |
| ROW-04 | 연속 토글 | 체크 원을 빠르게 두 번 클릭 | 완료 → 미완료로 정확히 두 번 토글되며 중간에 상세가 열리지 않는다. |
| ROW-05 | 홈/할 일 화면 모두 동일 동작 | 홈의 "이번 주 할 일"과 할 일 탭 목록 각각에서 ROW-01~ROW-02 반복 | 두 화면 모두 동일하게 동작한다(공통 `ListRow` 컴포넌트 재사용 여부 확인). |

## 14. NEXT 카드 선택 규칙

discussion.md 7절: "NEXT 카드는 미완료 항목 중 첫 번째를 보여주고, 설명은 본문의 첫 문장만 씁니다." 캔버스 로직: `ALL.find(x => !done[x.id]) || ALL[0]`.

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| NEXT-01 | 첫 미완료 항목 노출 | 기본 데이터 상태로 홈 진입 | NEXT 카드 제목이 전체 목록(`TASKS` + 직접 추가한 할 일, phase 구분 없이 순서대로) 중 **가장 먼저 등장하는 미완료 항목**과 일치한다. |
| NEXT-02 | phase 무관 여부 | '현지 정착' 항목이 먼저 완료되고 '출국 전' 항목이 남아있는 상태 확인 | NEXT 카드는 phase로 필터링하지 않고 원본 배열 순서상 첫 미완료 항목을 그대로 보여준다(phase 우선순위가 없음에 유의). |
| NEXT-03 | 설명은 첫 문장만 | 본문이 여러 문장인 항목이 NEXT로 선택된 상태 | 카드 설명에는 본문 전체가 아니라 **마침표 기준 첫 문장**만 표시된다(캔버스 `next.body.split('.')[0] + '.'`). |
| NEXT-04 | 완료 처리 후 NEXT 갱신 | NEXT 카드에 뜬 항목을 완료 처리 | NEXT 카드가 즉시 그 다음 미완료 항목으로 교체된다. |
| NEXT-05 | 전체 완료 시 폴백 | 모든 항목을 완료 처리 | 미완료 항목이 없으므로 NEXT 카드는 목록의 첫 항목(`ALL[0]`)을 그대로 보여준다(빈 카드가 아님). CTA를 눌러도 이미 완료된 항목의 상세로 이동함을 확인한다. |
| NEXT-06 | CTA 동작 | NEXT 카드의 "지금 하기" 클릭 | 해당 항목의 상세 화면이 열린다. |
| NEXT-07 | 직접 추가한 할 일도 후보에 포함 | 마감이 이른(예: '오늘까지') 새 할 일을 원본 `TASKS`보다 먼저 등장하도록 추가할 수 있는지 확인 | 직접 추가한 할 일도 `ALL` 배열에 포함되어 NEXT 후보가 될 수 있다(원본 TASKS 뒤에 추가되므로, 실제로 NEXT가 되려면 그 앞의 모든 항목이 완료되어 있어야 함 — 배열 순서 규칙을 정확히 확인). |

## 15. 진행률 계산

discussion.md 7절: "진행률은 기본 할 일 + 직접 추가한 할 일을 합쳐 계산합니다." 캔버스: `ALL = TASKS.concat(custom)`.

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| PROG-01 | 홈 전체 진행률 초기값 | 초기 데이터 상태(완료 표시된 기본 항목 수 확인) | 홈 "준비 진행률" 라벨이 "완료 수 / 전체 수"와 정확히 일치하고, 프로그레스바 폭이 그 비율(%)과 일치한다. |
| PROG-02 | 기본 항목 완료 시 갱신 | 기본 `TASKS` 항목 하나를 완료 처리 | 분모(전체 수)는 변하지 않고 분자(완료 수)만 1 증가, 라벨/바 즉시 갱신. |
| PROG-03 | 직접 추가 시 분모 증가 | 할 일 추가 시트로 새 항목 등록 | 전체 수가 1 증가한다(완료 여부와 무관하게 분모에 포함). |
| PROG-04 | 직접 추가 항목 완료 시 분자 증가 | PROG-03에서 추가한 항목을 완료 처리 | 완료 수가 1 증가한다(기본 항목과 동일하게 취급됨을 확인). |
| PROG-05 | phase별 진행률과 전체 진행률 구분 | 할 일 탭에서 phase별 "n/m"과 홈의 전체 "n/m"을 동시에 비교 | 두 값은 서로 다른 모수를 쓴다(phase 진행률은 해당 phase 항목만, 홈 진행률은 전체 항목). 둘 다 직접 추가한 할 일을 포함해 재계산된다. |
| PROG-06 | 분모 0 방지(엣지 케이스) | 특정 phase에 항목이 하나도 없는 상태를 만들 수 있는지 확인(데이터 구조상 가능하다면) | 0으로 나누어 `NaN%`가 표시되지 않는다(캔버스 원본은 이 케이스를 방어하지 않으므로, 실제 데이터에서 발생 가능한지와 구현 시 방어 로직이 있는지 확인 필요). |

## 19. 빈 상태(빈 데이터) 시나리오

`src/Front/common/data/tasks.ts` 확인 결과, Research-team 조사 완료 전까지 `COUNTRIES`, `TASKS`, `GUIDE.pre`, `GUIDE.post`, `PAIN`가 모두 빈 배열입니다. 이는 "코드가 없어서"가 아니라 **데이터가 의도적으로 비어 있는 상태**이며, 조사 산출물이 도착하기 전까지 실제로 이 상태로 배포/미리보기될 수 있습니다. 따라서 이 절의 시나리오는 "나중에 값이 채워지면 저절로 해결되는 문제"로 넘기지 말고, 빈 배열 상태 자체에서 앱이 예외 없이 렌더되는지를 반드시 확인해야 합니다.

캔버스 05 섹션 원본 스크립트는 이 빈 상태를 가정하지 않고 만들어졌습니다(`ALL.find(x => !done[x.id]) || ALL[0]`처럼 배열이 비어 있으면 `undefined`가 나오는 로직, `doneCount / total`처럼 분모가 0이 될 수 있는 나눗셈 등). 그대로 포팅하면 런타임 에러나 `NaN`/`Infinity` 표시로 이어질 수 있으므로, 구현 시 이 분기들이 방어되었는지가 이 절의 핵심 확인 대상입니다.

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| EMPTY-01 | 홈 D-day 표시 | `COUNTRIES`/`TASKS` 빈 배열 상태로 홈 화면 진입 | 출국일 정보가 없으므로 "D-NaN", "D-undefined" 같은 값이 아니라 정의된 빈 상태 문구(예: "출국일을 설정해 주세요") 또는 안전한 placeholder가 표시된다. 콘솔에 런타임 에러가 없다. |
| EMPTY-02 | 홈 진행률 — 분모 0 방지 | 위 상태에서 홈 "준비 진행률" 블록 확인 | `doneCount=0, total=0`이 되어도 "NaN%"나 "Infinity%"가 렌더되지 않는다. "0 / 0"을 그대로 보여주거나 진행률 블록 자체를 빈 상태로 대체하는 두 방식 중 하나를 택하되, 아래 EMPTY-07(할 일 phase별 진행률)에도 동일한 방식이 일관되게 적용되는지 확인한다. |
| EMPTY-03 | NEXT 카드 — 후보 없음 | `TASKS`가 비어 있고 직접 추가한 할 일도 없는 최초 진입 상태에서 NEXT 카드 확인 | 원본 로직(`ALL.find(...) || ALL[0]`)을 그대로 포팅했다면 전체 배열이 비어 `next`가 `undefined`가 되어 `next.title` 등에 접근할 때 크래시할 수 있다. 크래시 없이 "지금 준비할 일이 없습니다" 류의 전용 빈 상태 카드가 표시되는지 확인한다 — Frontend 구현에서 이 분기가 빠지지 않았는지 특히 주의해서 본다. |
| EMPTY-04 | NEXT 카드 — CTA 비활성화 | EMPTY-03 상태에서 "지금 하기" 버튼 유무 확인 | 이동할 상세 항목이 없으므로 CTA가 숨겨지거나 비활성화되고, 존재하지 않는 항목의 상세로 이동을 시도하지 않는다. |
| EMPTY-05 | 이번 주 할 일 — 빈 목록 문구 | 홈 "이번 주 할 일" 섹션 확인 | 목록이 비어 있을 때 빈 여백만 남지 않고 "아직 할 일이 없습니다" 류의 빈 상태 문구가 보인다. |
| EMPTY-06 | 할 일 화면 — 세그먼트별 빈 목록 | 할 일 탭 진입 후 출국 전 / 현지 정착 세그먼트 각각 확인 | 두 세그먼트 모두 목록이 비어 있고 각각 빈 상태 문구가 표시된다. 세그먼트 전환 자체는 데이터 유무와 무관하게 정상 동작한다. |
| EMPTY-07 | 할 일 화면 — phase 진행률 | 세그먼트별 진행률("n/m", 프로그레스바) 확인 | EMPTY-02와 동일한 규칙으로 "0/0"이 그대로 보이거나 진행률 블록이 빈 상태로 대체되며, `NaN%` 폭의 프로그레스바가 렌더되지 않는다. |
| EMPTY-08 | 데이터 추가 시 정상 상태로 전환 | 빈 상태에서 할 일 추가 시트로 항목 1개 등록 | `TASKS`가 비어 있어도 추가 시트는 정상적으로 열리고 등록할 수 있다. 등록 후에는 진행률이 "1/1" 등으로, NEXT 카드도 방금 추가한 항목으로 정상 전환되어 EMPTY-01~07의 빈 상태 문구가 사라진다. |

### 20.5 클라이언트 날짜 계산 — 빌드 시점 고정 방지 (10.3절)

> discussion.md 10.3절: "오늘 날짜는 반드시 클라이언트에서 계산합니다. 이 라우트는 정적 프리렌더 대상이므로 서버 렌더 시점에 `new Date()`를 쓰면 빌드 시점 날짜로 고정되고, 하이드레이션 불일치도 발생합니다."

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| DAY-14 | 정적 HTML에 날짜가 박혀 있지 않음 | `next build` 산출물의 정적 프리렌더 HTML(서버가 실제로 응답하는 첫 HTML, "페이지 소스 보기"로 확인 가능)에서 D-day 값 확인 | 서버가 내려주는 HTML 자체에는 특정 날짜로 계산된 D-day 숫자가 박혀 있지 않아야 한다(첫 페인트에는 비어 있거나 placeholder이고, 클라이언트 마운트 후 `new Date()`로 계산되는 구조인지 소스 코드에서 함께 확인 — `useEffect`/클라이언트 컴포넌트 여부). |
| DAY-15 | 하이드레이션 불일치 없음 | 프로덕션 빌드(`next build && next start`)로 페이지를 브라우저에서 로드 | 콘솔에 React 하이드레이션 불일치 경고("Text content did not match", "Hydration failed" 등)가 발생하지 않는다. |
| DAY-16 | **빌드 후 하루 경과 재현 — 시스템/브라우저 시간 조작** | ① 빌드는 그대로 둔 채 OS 또는 브라우저의 시스템 시계를 하루 뒤로 바꾸고 새로고침하거나, ② Chrome DevTools의 Sensors 패널(또는 동급 기능)로 클라이언트 `Date`를 하루 뒤로 override한 뒤 새로고침 | D-day 값이 멈춰 있지 않고 새 "오늘" 기준으로 갱신된다(숫자가 1 감소하거나, DAY-07/08의 D-DAY↔D+1 경계를 넘어간다). 값이 그대로라면 날짜 계산이 서버·빌드 시점에 고정되어 있다는 뜻이므로 **실패로 기록**한다. |
| DAY-17 | 빌드 후 하루 경과 재현 — 재배포 없이 확인하는 대안 | 빌드 서버의 시스템 시간을 바꾸기 어려운 환경이라면, 한 번 빌드해 정적 HTML을 고정시킨 뒤 **서버는 그대로 두고 클라이언트 쪽에서만** DAY-16의 DevTools 시간 override(또는 브라우저 콘솔에서 `Date`를 하루 뒤로 mock)를 적용해 새로고침 | 서버를 재시작하거나 재배포하지 않아도 D-day가 클라이언트 쪽 "오늘"을 기준으로 다시 계산되어 표시된다. 이는 날짜 계산이 서버 렌더 시점이 아니라 브라우저 실행 시점에 일어난다는 것을 재배포 없이 증명하는 것이 핵심이다. |

- 출국일의 `localStorage` 저장 범위·경계는 이 QA 문서의 범위가 아니라 Security 검토서 2절을 따릅니다(discussion.md 10.3절 참고).

### 20.6 "D-0" 누출 방지 — 빈 상태와 출국 당일 표기가 섞이지 않는지 (discussion.md 10.2절 재확인, 2026-08-28 사용자 지적)

10.2절이 이미 정한 규칙이다 — "출국일이 입력되지 않았으면... 빈 상태 문구로 둡니다. 임의의 기본값을 넣지 않습니다"와 "출국 당일은 `D-DAY`". 실제 빌드에서 출국일 미입력 상태에 `D-0`처럼 그럴듯해 보이지만 틀린 기본값이 새어 나온 사례가 지적되어, 이 둘이 혼동되지 않는지 별도로 확인한다.

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| D0LEAK-01 | **출국일 미입력 시 "D-0" 누출 없음** | 출국일을 입력하지 않은 상태로 홈 화면의 D-day 자리 확인 | 빈 상태 문구(`'나' 화면에서 출국일을 입력하면 D-day가 표시됩니다.` 류)만 있고, `D-0`이라는 문자열이 어디에도 나타나지 않는다. 화면 전체 텍스트에서 정확히 `D-0` 문자열을 검색해 0건인지로 판정한다(육안으로는 "이 정도면 그럴듯하다"고 넘어가기 쉬운 값이라 문자열 검색으로 확인). |
| D0LEAK-02 | **출국 당일은 `D-DAY`, `D-0`이 아님** | 출국일을 오늘 날짜로 입력 | 정확히 `D-DAY`로 표시된다. `D-0`, `D0`, `D-0일` 같은 변형이 나오지 않는다(DAY-07과 같은 케이스지만, 이번엔 "D-0과 섞이지 않는가"라는 관점으로 문자열을 엄격히 대조한다). |
| D0LEAK-03 | **'나' 화면 출국일·비자 만료 줄도 미입력 시 그대로 빈 상태** | 출국일 미입력 상태로 '나' 화면의 출국일·비자 만료 두 줄 확인 | 두 줄 모두 빈 상태 문구다. `D-0`은 물론 `1970년 1월 1일`처럼 날짜 파싱 실패 시 흔히 새는 epoch 기본값이나, 오늘 날짜를 그대로 출국일인 것처럼 보여주는 값 등 **어떤 형태의 기본값도** 나타나지 않는다(DAY-05와 같은 확인을 "D-0 누출"이라는 구체적 관점에서 재확인). |

## 23. 출처 표시 (discussion.md 13절, 2026-08-28 지시)

데이터의 `sourceUrl`을 화면에 노출하는 기능입니다. 비자·세금·보험처럼 틀리면 실제 손해로 이어지는 정보이므로 원문을 확인할 수 있게 하는 것이 목적입니다. 정보 예산을 지키기 위해 **목록이 아니라 상세에서만** 노출한다는 것이 이 절 시나리오 전체의 전제입니다.

## 24. 폰트 상속 회귀 — 버튼·입력 요소 (2026-08-28 결함 발견, Frontend 수정 중)

`app/globals.css`가 `font-family`를 `body`에만 선언해 두었는데, `button`과 `input`은 브라우저 기본 UA 스타일시트상 폰트를 **부모로부터 상속하지 않는 요소**라 이 규칙이 적용되지 않는다. 그 결과 body는 Noto Sans KR로 렌더되는데 버튼류는 브라우저 기본 폰트(예: Arial)로 렌더되는 결함이 실제로 발견됐다(`getComputedStyle`로 직접 측정: body는 Noto Sans KR, `button`은 Arial).

**이 결함은 눈으로 보는 확인만으로는 잘 잡히지 않는 종류다.** Noto Sans KR과 시스템 기본 산세리프체는 한글·영숫자 렌더링이 육안으로는 비슷해 보일 수 있고, 화면 스크린샷만으로는 놓치기 쉽다. 그래서 아래 시나리오는 전부 **`getComputedStyle`로 실제 적용된 `font-family` 값을 읽어 `body`의 값과 문자열로 대조**하는 방식으로만 확인한다. 육안 확인은 보조 수단으로만 쓰고, 통과 판정의 근거로 쓰지 않는다.

측정 방법(모든 ID 공통): 헤드리스 브라우저에서 대상 요소를 얻어 `getComputedStyle(element).fontFamily`를 읽고, 같은 방식으로 얻은 `getComputedStyle(document.body).fontFamily`와 **완전히 동일한 문자열**인지 비교한다. 다르면(특히 대상 요소의 첫 번째 폰트가 `Arial`, `-apple-system`, `system-ui` 같은 브라우저 기본값으로 나오면) 실패로 기록한다.

| ID | 대상 | 절차 | 기대 결과 |
|---|---|---|---|

### FONT-11 · FONT-12 · FONT-13 — 한글 라벨이 mono 서체로 깨지는 결함 (2026-08-28 추가 발견, Chip 외 SourceLink도 해당)

FONT-02 재검토 과정에서, 상속 누락과는 별개로 **Chip 자체가 처음부터 `font-family: var(--font-mono)`를 명시하고 있어 한글 라벨(국가 선택 칩 등)이 깨지는 결함**이 추가로 발견됐다. Frontend에 discussion.md 3.2절의 `label` 규격(13px, 미선택 500 / 선택 700, 본문 서체)에 맞추도록 지시했다.

이어서 같은 종류의 결함이 **`SourceLink`에도 있다는 것이 정정 보고됐다**. `SourceLink`가 그리는 문구는 "출처 {도메인}" 형태로 앞에 한글 라벨("출처")이 붙는데, 링크 전체가 통째로 mono 처리돼 있었다면 도메인뿐 아니라 "출처"라는 한글까지 깨진다. 그래서 mono 허용 목록은 애초 생각했던 "`NextActionCard`의 NEXT 캡션과 `SourceLink`의 도메인" 두 곳이 아니라 **`NextActionCard`의 NEXT 캡션 한 곳으로만 좁혔고**, `SourceLink`는 "출처" 라벨(본문 서체)과 도메인(mono)을 요소 자체를 분리해 서로 다른 서체를 쓰도록 Frontend에 지시했다. 아래 세 시나리오로 확인한다.

| ID | 대상 | 절차 | 기대 결과 |
|---|---|---|---|
| FONT-11 | 전 컴포넌트 — **콘텐츠 성격과 서체 일치 여부 전수 확인** | FONT-01~09 각 요소 + `SourceLink`의 한글 라벨 부분(아래 FONT-13 참고)의 `getComputedStyle().fontFamily`를 한 번에 표로 정리 | **한글(또는 한글이 섞일 수 있는) 콘텐츠를 담는 요소는 전부 `body`와 동일한 패밀리**(Button/Chip/Segment/TabBar/ListRow/NextActionCard 본문/BottomSheet 닫기/TextField/`SourceLink`의 "출처" 라벨 부분). **`var(--font-mono)`(JetBrains Mono)는 `NextActionCard`의 "NEXT" 캡션 한 곳으로만 한정**된다(**정정**: `SourceLink`의 도메인 부분은 mono 허용 목록에서 제외 — 이유는 아래 FONT-13 참고). 이 한 곳을 제외한 어디에서도 mono 패밀리가 나오면 실패로 기록한다(Chip이 여전히 mono라면 이 시나리오에서 실패로 잡힌다). |
| FONT-12 | `Chip` — 크기·굵기 | 미선택 상태는 문서 탭의 확장자 배지(앱 화면에 실제 렌더)에서 측정한다. **선택 상태는 앱 화면 어디에도 렌더되지 않으므로**(2026-08-28 확인) `ds-bundle/components/general/Chip/Chip.html`의 `Selectable` story(`selected=true`로 렌더된 "호주" 칩)에서 측정한다. 두 상태 모두 `getComputedStyle().fontSize`와 `getComputedStyle().fontWeight` 측정 | 미선택: `13px` / `500`. 선택: `13px` / `700`. | FONT-13 | `SourceLink` — **한 요소 안에서 서체가 두 개로 섞이는 경우, 부분별로 따로 측정** | `SourceLink`가 렌더하는 "출처 {도메인}" 링크에서 "출처" 라벨 부분과 도메인 부분이 각각 별도 요소(예: `<span>`)로 분리돼 있는지 먼저 확인한 뒤, 두 부분의 `getComputedStyle().fontFamily`를 따로 측정 | **정정**: `SourceLink`는 "출처"(한글) 뒤에 도메인이 바로 이어지는 하나의 문구라, 링크 전체를 통째로 mono 처리하면 "출처"까지 깨진다. 라벨("출처") 부분은 `body`와 동일한 패밀리여야 하고, 도메인 부분만 `var(--font-mono)`여야 한다. 링크 전체(`<a>` 요소 자체)에 통짜로 하나의 `font-family`만 걸려 있고 내부에 분리된 요소가 없다면, 그 자체로 이 시나리오는 실패다(측정 이전에 마크업 구조부터 확인). |

## 25. 이용자 파일 저장 — IndexedDB (discussion.md 16절, 2026-08-28 지시, 구현 착수) — [취소: 2026-08-28. 파일 저장 기능 자체를 폐기하고 문서 탭을 메모 탭으로 바꾸기로 결정(discussion.md 16.1절 "폐기 이유" — 암호화·키 파쇄·보관기간·매직넘버 검사 등 이 앱 크기에 비해 딸려 오는 것이 너무 많았고, 대안(File System Access API)도 Safari·Firefox 미지원이라 채택 불가). 이 절 전체(25.1~25.11, KEY/CRYPTO/PURGE/DOCFILE/MAGIC/COPY-DOC 계열)는 실행하지 않는다. 삭제하지 않고 남겨 두는 이유는 같은 논의가 반복될 때 무엇을 검토했었는지 참고하기 위해서다. 대체 기능(메모) 시나리오는 26절.]

파일 추가 시트가 실제로 카메라/앨범/파일 선택을 받아 IndexedDB에 저장하도록 구현이 시작됐다. discussion.md 16절과 `Docs/State/SecurityReview.md` 3절이 정한 저장 방식·미리보기·실패 처리·카피 규칙을 근거로 시나리오를 준비한다. **이 문서 작성 시점에는 아직 코드가 없다.** 구현이 도착하면 실행하고 QAResult.md에 결과를 추가한다.

전제(16.1절): DB 이름 `wabi`, 오브젝트 스토어 `docs`, 키 `id`. 파일과 메타데이터가 **같은 레코드**에 있어야 하고(따로 나누면 한쪽만 지워졌을 때 불일치 발생), `localStorage`는 이 기능에 전혀 관여하지 않아야 한다.

> **갱신(2026-08-28, 16.8~16.10절 추가 · 보관 기간 30일→60일 재조정 · 키를 앱 공유 1개에서 파일별 1개로 재조정 · 매직 넘버 검사 추가)**: 암호화와 60일 보관 기간이 추가되면서 레코드 모양이 바뀌었다. `docs` 스토어 레코드에서 **평문으로 남는 필드는 `id`/`addedAt`/`byteLength` 세 개뿐**이다(**`purgeAt`은 두지 않는다** — 남은 일수는 저장해 두지 않고 `addedAt`에서 매번 다시 계산한다, 16.9절). 파일 이름·MIME·내용(그리고 서류 자체의 `expiresAt`도 — 16.8절의 평문 허용 목록에 없으므로)은 전부 암호화된 페이로드 안에 있어야 한다. `CryptoKey`는 별도 오브젝트 스토어 `keys`에 **파일마다 하나씩**(파일 `id`를 키로) 둔다 — 삭제 시 그 파일 전용 키까지 함께 지우는 암호학적 파쇄가 목적이다(25.10). 파일 선택 직후·암호화 이전에는 매직 넘버로 확장자 위장을 걸러낸다(25.11). 아래 25.1은 이 모든 갱신 이전 설계를 기준으로 처음 작성됐던 것이라 DOCFILE-01·DOCFILE-03을 함께 고쳤다. 암호화·보관 기간·키 분리·매직 넘버 자체의 상세 시나리오는 새로 추가한 25.7·25.8·25.10·25.11을 본다.

### 25.5 저장 실패 처리 (16.6절) — 재현이 어려우므로 두 가지 방법을 함께 적어둔다

discussion.md 16.6절: "용량 초과(`QuotaExceededError`)나 그 밖의 실패를 조용히 삼키지 않는다. 실패하면 이용자에게 알리고 목록에 항목을 추가하지 않는다." 실제 브라우저에서 저장 공간을 가득 채워 자연스럽게 실패를 유발하는 것은 시간이 오래 걸리고 재현성이 낮으므로, 아래 두 방법 중 하나(가능하면 둘 다)로 강제 재현한다.

**방법 A — CDP로 저장 쿼터를 강제로 낮춘다(자동화에 적합)**

Playwright(또는 다른 CDP 기반 도구)로 접속했다면 Chrome DevTools Protocol의 `Storage.overrideQuotaForOrigin`을 직접 호출해 이 오리진의 저장 쿼터를 매우 작은 값(예: 수백 바이트)으로 강제 설정할 수 있다.

```js
const cdp = await context.newCDPSession(page);
await cdp.send("Storage.overrideQuotaForOrigin", { origin: "http://localhost:3000", quotaSize: 200 });
```

이 상태에서 파일 추가를 시도하면 실제 `QuotaExceededError`가 자연스럽게 발생한다. 수동으로 확인할 때는 최신 Chrome DevTools의 Application 패널 → Storage 항목에 있는 "Simulate custom storage quota" 옵션(버전에 따라 위치가 다를 수 있음)으로 같은 효과를 낼 수 있다.

**방법 B — 저장 유틸 함수를 직접 호출해 예외를 강제로 던진다(단위 수준, 더 빠르고 결정적)**

`src/Front/common/storage/docFiles.ts`가 내부적으로 쓰는 IndexedDB API(`indexedDB.open`, 트랜잭션의 `objectStore.put` 등)를 페이지 컨텍스트에서 몽키패치해 저장 시점에 강제로 `QuotaExceededError`(또는 임의의 `DOMException`)를 던지거나 reject하게 만든 뒤, UI에서 실제로 파일 추가 흐름을 실행한다. 예:

```js
await page.evaluate(() => {
  const store = window.indexedDB; // 실제 스토리지 유틸 내부 접근 방식에 맞춰 조정
  // objectStore.put이 실행되는 시점에 예외를 던지도록 IDBObjectStore.prototype.put을 감싼다
  const origPut = IDBObjectStore.prototype.put;
  IDBObjectStore.prototype.put = function (...args) {
    throw new DOMException("강제 재현", "QuotaExceededError");
  };
});
```

두 방법 모두 아래 결과를 같은 기준으로 확인한다.

|---|---|---|---|
| DOCFILE-17 | 저장 실패 — 목록 미반영 | 방법 A 또는 B로 저장이 실패하는 상태를 만든 뒤 파일 추가를 시도 | 문서 목록에 새 항목이 추가되지 않는다(추가 전후 목록 개수가 동일). "절반만 반영된 상태"(예: 메타만 보이고 파일이 없는 행)가 생기지 않는다. |

### 25.7 암호화 (discussion.md 16.8절, 2026-08-28 추가 → 같은 날 보안 검토로 **키를 앱 공유 1개에서 파일마다 1개로 재조정**)

파일 내용·이름·MIME을 AES-GCM 256비트로 암호화하고, 키는 `extractable:false`로 만들어 꺼낼 수 없게 한다는 요구다. **갱신**: 키를 앱 전체가 공유하던 최초 설계가 보안 검토(`SecurityReview.md` 7-4절)로 바뀌어, **파일을 추가할 때마다 새 키를 만들어 파일별로 따로 저장**한다 — 삭제 시 그 파일 전용 키까지 함께 지우는 암호학적 파쇄(crypto-shredding)가 목적이다. 키 자체의 분리·파쇄 시나리오는 새로 추가한 25.10을 본다. "암호화했다고 주장하지만 실제로는 평문"인 경우가 가장 흔한 실패 형태이므로, 아래 시나리오는 전부 **개발자 도구/직접 조회로 실제 저장된 바이트와 키 객체를 확인**하는 방식으로만 판정한다.

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| CRYPTO-01 | 파일 내용이 평문으로 보이지 않음 | 텍스트를 육안으로 식별 가능한 파일(예: 알아볼 수 있는 문구가 박힌 이미지, 혹은 간단히 텍스트가 포함된 PDF)을 추가한 뒤, IndexedDB의 `docs` 레코드에서 암호문 필드를 꺼내 바이트를 직접 확인(`page.evaluate`로 `Uint8Array`를 문자열로 디코딩 시도, 또는 DevTools에서 raw 바이너리 프리뷰) | 원본 파일의 식별 가능한 바이트 패턴(매직 넘버, 텍스트 등)이 저장된 값에서 전혀 보이지 않는다. 평문 `Blob`을 그대로 넣었다면 이미지/PDF 매직 넘버(`\x89PNG`, `%PDF` 등)가 앞부분에 그대로 보이므로, 그 패턴이 없는지가 가장 간단한 반증 지점이다. |

### 25.8 보관 기간과 자동 삭제 (discussion.md 16.9절, 2026-08-28 추가 → 같은 날 30일에서 **60일로 재조정**) — 시스템 시각 조작이 어려우므로 대안 재현 방법을 함께 적어둔다

**갱신**: 보관 기간이 30일에서 **60일**로 바뀌었고, `purgeAt` 필드는 아예 없앴다. 레코드에는 평문 `addedAt`(등록 시점)만 두고, 남은 일수는 **저장해 두지 않고 화면에 보여줄 때마다 `addedAt`에서 다시 계산**한다(16.9절). 60일이 지난 파일이 실제로 지워지는지 확인하려면 60일을 기다리거나 시스템 시계를 바꿔야 하는데, 이 환경에서는 시스템 시각 변경이 쉽지 않다(다른 프로세스·서버 시각과 어긋나는 부작용이 생길 수 있음). 대신 **정상적으로 파일을 추가한 뒤, IndexedDB에 이미 저장된 그 레코드의 평문 필드 `addedAt`만 페이지 컨텍스트에서 직접 고쳐 과거로 조작**하는 방법을 쓴다. `addedAt`은 암호화 대상이 아닌 평문 필드이므로(16.8절), 암호문·IV·키를 전혀 건드리지 않고 이 값만 다시 쓸 수 있다.

```js
async function setAddedAtDaysAgo(page, days) {
  await page.evaluate(async (d) => {
    const db = await new Promise((resolve, reject) => {
      const req = indexedDB.open("wabi");
      req.onsuccess = () => resolve(req.result);
      req.onerror = () => reject(req.error);
    });
    const tx = db.transaction("docs", "readwrite");
    const store = tx.objectStore("docs");
    const all = await new Promise((resolve, reject) => {
      const req = store.getAll();
      req.onsuccess = () => resolve(req.result);
      req.onerror = () => reject(req.error);
    });
    // 방금 UI로 추가한 레코드(가장 최근 addedAt)를 찾아 d일 전으로 조작한다. purgeAt은 건드리지 않는다(존재하지 않아야 함).
    const record = all.sort((a, b) => b.addedAt - a.addedAt)[0];
    record.addedAt = Date.now() - d * 24 * 60 * 60 * 1000;
    store.put(record);
  }, days);
}
```

### 25.9 남은 일수 계산의 타임존 함정 — P-06과 같은 패턴 (discussion.md 16.9절 "P-06과 같은 함정이 여기에도 있습니다")

D-day 계산에서 실제로 발견됐던 결함(D-1, QAResult.md 1·2절)과 정확히 같은 함정이다 — "오늘"을 서버·빌드 시점의 `new Date()`로 계산하면 UTC보다 느린 시간대에서 하루씩 밀리고, 값이 빌드 시점에 고정돼 하이드레이션 불일치도 난다. discussion.md 16.9절이 명시적으로 "`computeDDay`가 `today`를 인자로 받는 순수 함수인 것과 같은 방식으로 만들라"고 지시했으므로, **같은 방법으로 재검증**한다.

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| PURGE-09 | 서버 렌더 시점에 남은 일수가 고정되지 않음 | 문서가 있는 상태에서 정적 프리렌더 HTML(`curl`로 받은 최초 응답, 또는 페이지 소스 보기)에 남은 일수 숫자가 박혀 있는지 확인 | IndexedDB는 클라이언트 전용이라 서버 렌더 시점에는 문서 목록 자체를 알 수 없으므로 원칙적으로 빈 상태여야 하지만, 혹시라도 남은 일수 계산 로직이 서버에서도 실행 가능한 형태(정적 임의값)로 새어 있는지 소스 검토로 교차 확인한다. |

### 25.10 파일별 키 — 암호학적 파쇄 (discussion.md 16.8·16.9절, 2026-08-28 보안 검토로 추가)

앱 전체가 키 하나를 공유하던 최초 설계를 "파일마다 새 키"로 바꾼 이유는, 파일을 지울 때 **그 파일 전용 키까지 함께 지워서** 디스크에 조각이 남아도 풀 수 있는 키가 이미 없게 만들기 위해서다(암호학적 파쇄). 이 목적 자체가 지켜지는지 — 키가 실제로 파일마다 다른지, 삭제·자동 스윕 때 정확히 그 파일의 키만 사라지는지 — 를 확인한다.

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| KEY-01 | 파일 2개 추가 시 `keys` 레코드 2개 | 서로 다른 파일 2개를 추가한 뒤 `keys` 스토어를 조회 | 레코드가 정확히 2개이고, 각각의 키(레코드 식별자)가 `docs`의 두 파일 `id`와 1:1로 대응한다. |
| KEY-02 | **두 키가 실제로 서로 다름** | `extractable:false`라 원시 바이트를 직접 비교할 수는 없으므로, **교차 복호화**로 간접 확인한다 — 파일 A의 IV·암호문을 파일 B의 `CryptoKey`로 `crypto.subtle.decrypt` 시도(`page.evaluate` 안에서 두 레코드의 키·IV·암호문을 가져와 서로 바꿔 넣는다) | 교차 복호화가 **실패한다**(`OperationError` 등으로 거부되거나 결과가 원문과 다른 쓰레기 바이트다). 성공해서 원문이 그대로 나오면 두 파일이 사실은 같은 키를 쓰고 있다는 뜻이므로 심각한 결함이다(암호학적 파쇄가 애초에 성립하지 않음). |
| KEY-03 | 삭제 시 그 파일의 키만 사라짐 | 파일 A, B 두 개를 추가한 뒤 A만 삭제(DOCFILE-06~08 흐름) | `docs`에서 A의 레코드가 사라지는 것과 **함께** `keys`에서도 A의 키 레코드가 사라진다. B의 `docs`·`keys` 레코드는 그대로 남는다. |
| KEY-04 | 같은 트랜잭션으로 지워짐 — 절반만 지워진 상태가 없음 | KEY-03 재현 직후(삭제 직후) `docs`와 `keys`를 각각 조회해 A의 흔적이 남아 있는지 확인. 가능하면 삭제 도중 강제로 페이지를 새로고침하는 것처럼 중간에 끼어드는 시도도 해본다 | A의 레코드가 `docs`에는 없는데 `keys`에는 남아 있거나, 반대로 `keys`에는 없는데 `docs`에는 남아 있는 **불일치 상태가 절대 관측되지 않는다**(16.9절 "같은 트랜잭션에서 함께 지웁니다" — 파일 레코드와 키 중 하나만 지워지면 안 됨). |
| KEY-05 | **60일 자동 스윕에서도 같은 원칙** | 25.8의 `setAddedAtDaysAgo(page, 61)` 방법으로 파일 A를 만료시키고, 만료되지 않은 파일 B와 함께 둔 상태에서 스윕을 발생시킨다(PURGE-02) | 스윕 후 A는 `docs`·`keys` 양쪽에서 모두 사라지고, B는 양쪽에 그대로 남는다. 이용자가 직접 삭제할 때(KEY-03)와 자동 스윕일 때(이 항목) 두 경로 모두 같은 원칙을 지키는지 각각 확인한다. |

### 25.11 매직 넘버 검사 (discussion.md 16.2절, 2026-08-28 보안 검토로 추가)

`accept` 속성은 파일 선택 대화상자의 필터일 뿐 강제가 아니므로, 확장자와 MIME을 PNG로 위장한 SVG가 그대로 들어올 수 있다는 것이 위협이다. 파일을 고른 직후, **암호화하기 전에** 앞부분 바이트로 PNG·JPEG·WebP·PDF 시그니처를 대조해 맞지 않으면 거부해야 한다.

**위장 파일 준비 방법**: `<svg xmlns="http://www.w3.org/2000/svg">...</svg>` 같은 평범한 SVG 텍스트를 만든 뒤, 브라우저 컨텍스트에서 `File` 객체를 직접 생성해 이름과 MIME만 PNG로 속인다(네이티브 OS 파일 선택 창은 헤드리스 자동화로 열 수 없으므로, `input[type=file]`에 `DataTransfer`로 파일 목록을 직접 주입하는 표준적인 방법을 쓴다).

```js
await page.evaluate(() => {
  const svgText = '<svg xmlns="http://www.w3.org/2000/svg"><script>alert(1)</script></svg>';
  const fakeFile = new File([svgText], "위장.png", { type: "image/png" });
  const dt = new DataTransfer();
  dt.items.add(fakeFile);
  const input = document.querySelector('input[type="file"]'); // 실제 렌더된 숨은 input 선택자로 조정
  input.files = dt.files;
  input.dispatchEvent(new Event("change", { bubbles: true }));
});
```

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| MAGIC-01 | **위장 파일 거부** | 위 스니펫으로 확장자·MIME만 `image/png`로 바꾼 SVG를 파일 선택 입력에 주입 | 파일이 거부된다 — 문서 목록에 새 항목이 추가되지 않고(DOCFILE-17과 같은 판정 기준), 이용자에게 실패했다는 사실이 전달된다. |
| MAGIC-02 | **검사가 암호화 이전에 일어남** | MAGIC-01 재현 직후 `docs`·`keys` 두 스토어를 모두 조회 | 거부된 파일에 대해서는 `docs`·`keys` 어느 스토어에도 어떤 흔적(암호화됐든 안 됐든)도 남지 않는다. 암호화 함수(`crypto.subtle.encrypt`) 호출 자체가 발생하지 않았는지 CRYPTO-09와 같은 스파이 방식으로 확인하면 더 확실하다 — 매직 넘버 검사를 통과하기 전에 암호화부터 실행되면, 확장자만 바꾼 SVG의 위험이 "암호화됐으니 안전하다"는 착각 속에 그대로 보존됐다가 나중에 복호화 시점에 재현된다(discussion.md 16.2절 "암호화는 내용 검증을 대신하지 않습니다"). |
| MAGIC-03 | 정상 파일은 그대로 통과 | 실제 PNG/JPEG/WebP/PDF 파일(매직 넘버가 정확한 것)을 추가 | 정상적으로 저장되고 목록에 나타난다(매직 넘버 검사가 정상 파일까지 오탐으로 막지 않는지 확인). |

**실행 상태**: **[취소]** 25.1~25.11 전체를 2026-08-28 기준 실행하지 않는다. 파일 저장 기능 자체가 폐기되고 메모 기능으로 대체됐다(위 절 제목의 취소 사유 참고). 이 절은 향후 파일 저장이 다시 논의될 때 참고용으로만 남긴다.

## 26. 메모 기능 — 문서 탭 대체 (discussion.md 16절 전면 재작성, 2026-08-28)

문서 탭이 메모 탭으로 바뀐다. 남이 만든 파일을 암호화해 보관하는 대신, 이용자가 직접 적은 텍스트를 `localStorage`에 저장하는 훨씬 가벼운 기능이다. 25절(파일 저장)의 무거운 장치 — IndexedDB, 암호화, 키 파쇄, 보관 기간, 매직 넘버 검사 — 는 전부 해당 없음이고, 이 절은 그것과 독립적으로 새로 작성한다.

> **갱신(2026-08-28, 캔버스 확인 후 정정) → 다시 갱신(2026-08-28, discussion.md 19.7절, 우측 패널 통일)**: 한때 메모 레코드를 `{ id, title, body, updatedAt }`(제목·본문 두 필드)로 정정했었으나, **우측 패널을 홈·메모 공통 하나로 통일하면서 제목 입력칸 자체가 없어져 다시 `{ id, body, updatedAt }`(본문 하나)로 되돌아갔다.** 목록의 제목 자리는 다시 "본문 첫 줄"이다(제목 필드 추가 이전 방식). 아래 MEMO-01·10·11·15는 이번 되돌림을 반영해 원래대로 고쳤다. **이미 `title` 필드가 들어간 레코드가 있을 수 있으므로**(제목·본문 버전이 잠깐 배포됐을 가능성), 그 하위 호환도 MEMO-18(신설)에서 확인한다. 데스크톱 우측 요약 패널은 이제 홈·메모가 완전히 같은 컴포넌트를 쓴다 — 29절 TPC-23/24 대신 아래에서 통일된 형태로 다룬다(29절 해당 부분은 무효 표시로 남긴다).

## 28. 클릭 가능해 보이는 요소의 실사용성 감사 — "있어 보이는 것"이 "실제로 있는지" (2026-08-28, 27절 결함에서 얻은 교훈)

27.1절의 결함(홈 국가 배지가 화살표까지 달고 있으면서 `span`이라 눌리지 않음)은 기존 QAPlan의 어떤 시나리오도 잡지 못했다. 지금까지의 시나리오는 전부 **"이 버튼을 누르면 무엇이 일어나야 하는가"**를 확인하는 것이었지, **"화살표·chevron·배지처럼 눌릴 것 같이 생긴 요소가 실제로 누를 수 있는 요소인가"**를 확인하는 시나리오가 없었다. 이 절은 그 빈틈을 메우기 위한 것으로, 특정 기능이 아니라 **앱 전체 화면을 훑는 감사(audit) 성격**이다. 새 화면이 추가될 때마다 이 절을 다시 돌리는 것이 적절하다.

**관점의 차이가 핵심이다**: "있는 기능이 동작하는가"가 아니라 "있어 보이는 것이 실제로 있는가"를 본다. 후자는 전자를 전제하지 않는다 — 화살표가 있다고 해서 그 뒤에 클릭 핸들러가 있다는 보장이 없다.

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| AFFORD-01 | **시각적 클릭 어포던스 전수 나열** | 홈·할 일·메모·나 4개 화면과 열려 있는 모든 시트(가이드·어려움·할 일 추가·메모 추가·메모 편집·국가 선택)를 각각 열어, 화살표 문자(`›`, `‹`, `▾`)를 포함하거나 chevron 모양 아이콘을 가진 모든 요소, 그리고 `Chip`처럼 배지 형태를 가진 모든 요소를 나열한다 | 화면마다 발견된 어포던스 후보 목록이 만들어진다(예: 홈의 국가 배지, 각 `ListRow`의 화살표, 가이드/어려움 목록 행의 화살표, `NextActionCard`의 진행 요약 화살표, 나 화면 설정 행의 화살표 등). |
| AFFORD-02 | **후보마다 실제 태그·핸들러 확인** | AFFORD-01에서 나열한 요소마다 DOM 태그를 확인(`button`, `a`, 또는 `role="button"`/`role="link"`이면서 `tabindex`가 있어 키보드로도 접근 가능한 요소인지) | 시각적으로 눌릴 것처럼 보이는 요소는 예외 없이 `button`/`a`이거나 그에 준하는 접근성을 갖춘 요소다. 순수 `span`/`div`인데 화살표나 배지 스타일만 입혀진 요소가 있으면 — 실제로 클릭했을 때 아무 반응이 없는지까지 확인한 뒤 — 결함으로 기록한다(27.1절 BADGE-01과 같은 성격의 결함). |
| AFFORD-03 | **실제 클릭해서 상태 변화 확인** | AFFORD-02에서 "버튼/링크"로 확인된 요소를 실제로 클릭(`dispatchEvent`) | 클릭 전후로 관찰 가능한 상태 변화(화면 전환, 시트 열림, 값 토글 등 그 요소의 존재 이유에 해당하는 변화)가 실제로 일어난다. 태그는 `button`인데 `onClick`이 비어 있거나 아무 효과가 없는 "형식만 갖춘" 어포던스도 이 단계에서 걸러진다. |
| AFFORD-04 | 순수 표시용 요소와의 구분 | 화살표나 클릭 스타일이 전혀 없는, 순수 정보 표시용 요소(예: 메타 텍스트, 캡션)를 대조군으로 확인 | 이런 요소들은애초에 클릭 가능해 보이도록 스타일링되어 있지 않다 — 즉 "클릭 가능해 보임"과 "클릭 불가능"이 스타일 수준에서부터 일관되게 구분되는지 확인한다(어포던스가 있는데 기능이 없는 것과, 애초에 어포던스가 없어서 혼동의 여지가 없는 것을 같은 감사에서 함께 점검). |
| AFFORD-05 | **회귀 재확인 — 이번에 고친 두 곳** | 27절의 BADGE-01·UNDO-01이 이 감사에서도 함께 걸리는지(홈 국가 배지가 이제 `button`으로, 완료 취소 버튼이 실제로 상세를 닫는 것으로) | 이번에 고친 두 곳이 이 감사 방법으로도 정상 통과함을 재확인한다 — 즉 이 감사 절차 자체가 실제로 이런 종류의 결함을 잡아낼 수 있다는 것의 검증이기도 하다. |

## 29. 반응형 — 태블릿 · PC (캔버스 06절 기준, discussion.md 11절 전면 재작성, 2026-08-28)

**21절을 대체한다.** 21절의 값은 캔버스를 확인하지 않고 임의로 정한 것이었고, 디자인 캔버스에 06절 "태블릿 · PC"가 실제로 있었다. 아래는 그 목업 수치를 그대로 옮긴 것이다 — discussion.md 11절이 근거다. ID는 21절의 `RESP-`와 혼동하지 않도록 `TPC-`(Tablet·PC)로 새로 붙인다.

전제: `≤ 743px` 모바일(1열 + 하단 탭바) / `744~1179px` 태블릿(아이콘 레일 + 본문 620px 중앙, 4화면 공통) / `≥ 1180px` 데스크톱(사이드바 236px 공통 + 화면마다 다른 나머지 구성). 태블릿 목업은 834×1000, 데스크톱 목업은 1280×800 기준.

> **정정(2026-08-28)**: 데스크톱 "본문 + 우측 요약 336px" 3단 구성은 **홈·메모 두 화면에만** 적용된다. '나' 화면은 캔버스 목업을 대조한 결과 우측 패널이 없는 사이드바+본문 620 중앙 1열이고(11.5절 정정), '할 일' 화면은 캔버스에 데스크톱 목업 자체가 없어 임의로 확장하지 않고 '나'와 같은 1열 형태로만 둔다(11.6절 신설). 이 정정을 짚지 않았다면 '나' 화면에 없어야 할 우측 패널을 만들 뻔했다는 것이 실제로 있었던 일이다 — 그래서 29.4절에 "패널이 있어야 하는 화면"과 "패널이 없어야 하는 화면"을 함께 다룬다.

> **정정(2026-08-28, 오탐 사례)**: "할 일 화면에 홈의 '내 메모' 패널이 남아 있다"는 결함이 보고됐다가, 재확인 결과 **실제로는 결함이 아니었던 것으로 정정됐다.** 원인은 사이드바의 '할 일' 탭에 미완료 개수 배지가 붙어 버튼 텍스트가 "할 일4"처럼 됐는데, 탭을 클릭하는 자동화 스크립트가 정확히 "할 일"과 일치하는 버튼을 찾다 실패했고, 그 실패를 조용히 넘긴 채 여전히 홈 화면에 머물러 있던 상태를 측정해 "할 일 화면의 결과"로 잘못 보고한 것이었다. **교훈**: 탭 전환을 트리거하는 시나리오는 **클릭이 실제로 성공했는지, 그리고 전환 후 화면이 의도한 화면이 맞는지(그 화면의 `h1` 텍스트 등으로)를 먼저 확인한 뒤에만** 이어지는 측정값을 신뢰해야 한다. "클릭을 시도했다"와 "올바른 화면에 도달했다"는 다른 것이다 — 아래 29.1~29.6의 모든 시나리오는 각 탭 전환 직후 이 확인을 거친 것을 전제로 한다.

### 29.4 데스크톱 화면별 구성 — 우측 패널이 있는 화면과 없는 화면

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| TPC-23 | ~~홈 우측 패널~~ **[무효: 2026-08-28, discussion.md 19.7절로 홈·메모 우측 패널이 하나로 통일됨]** | — | 이 행이 설명하던 "내 메모 + 새 메모 버튼 + 빠른 입력 + 목록" 구성은 더 이상 맞지 않는다(`+ 새 메모` 버튼 자체가 없어졌다). 통일된 패널 시나리오는 30.7절(PANELUNIFIED)을 본다. |
| TPC-24 | ~~메모 화면 우측 패널 — 미니 에디터~~ **[무효: 2026-08-28, 같은 이유]** | — | "WRITING 캡션 + 제목 입력 + 내용 입력 + 저장하기/삭제" 구성도 더 이상 맞지 않는다(제목 입력칸과 WRITING 캡션이 없어지고, 홈과 완전히 같은 컴포넌트를 쓴다). 30.7절(PANELUNIFIED)을 본다. |
| TPC-25 | **정정: '나' 화면은 우측 패널이 없음 — 사이드바 + 본문 620 중앙 1열** (discussion.md 11.5절 재확인, 2026-08-28) | 데스크톱 폭에서 '나' 화면 전체 레이아웃 확인 | 사이드바 236px + **본문 620px 중앙 정렬** 1열 구성이고, **우측 요약 패널이 존재하지 않는다**(태블릿과 같은 형태를 데스크톱에서도 그대로 씀). 본문 내용은 위에서 아래로: 프로필 카드(국가 워킹홀리데이 / 출국일 / 비자 만료 / `정보 수정`) → 요약 두 칸(`준비 진행률 8 / 14`, `저장한 메모 4`) → `설정`(화면 모드 라이트·다크, 알림, 국가 변경). |

| TPC-25b | **할 일 화면 — 캔버스 목업 없음, 임의 확장 금지** (discussion.md 11.6절, 2026-08-28) | 데스크톱 폭에서 할 일 화면 레이아웃 확인 | '나' 화면과 같은 형태 — 사이드바 236px + **본문 620px 중앙 정렬** 1열이고, **우측 패널이 없다**. 데스크톱 전용으로 새로 만들어진 컴포넌트나 정보 블록(예: 가로형 NEXT 카드, 우측 통계 패널 등 다른 화면의 데스크톱 확장을 흉내 낸 무언가)이 이 화면에만 임의로 추가되어 있지 않은지 특히 주의해서 본다 — discussion.md 11.6절이 "목업이 필요해지면 캔버스에 추가된 뒤에 구현합니다"라고 명시했으므로, 캔버스에 없는 것을 추측해 만들었다면 그 자체가 이번 지시를 어긴 것이다. |
| TPC-25c | **할 일 화면에 우측 패널이 생기지 않았는지 직접 확인** | 데스크톱 폭에서 할 일 화면의 DOM을 조사해 우측 요약에 해당하는 컨테이너(336px 폭, 좌측 1px `line` 경계를 가진 블록)가 존재하는지 검사 | TPC-25a와 같은 방식으로, 그런 컨테이너 자체가 DOM에 없다. '나' 화면과 마찬가지로 홈·메모의 우측 패널 클래스/구조가 이 화면에는 재사용되거나 새로 만들어져 있지 않은지 코드 검토로도 함께 확인한다. |

### 29.5 회귀 — 캔버스 확장 규칙 4가지 (11.2절)

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| TPC-26 | **본문 폭이 620px를 넘지 않음** | 태블릿(744~1179px 여러 값)과 데스크톱(1180px, 1440px, 1920px처럼 매우 넓은 값 포함) 각각에서 본문 **콘텐츠**(예: `NextActionCard`, 할 일 목록 등 실제 카드·행 요소) 실제 폭 측정 | 어떤 폭에서도 본문 콘텐츠가 620px를 넘지 않는다. 화면이 아무리 넓어져도 글줄이 계속 길어지지 않는지가 핵심(11.2절 "본문 폭은 620px에서 멈춥니다"). **측정 시 주의(2026-08-28 실행에서 확인)**: 홈·메모처럼 우측 336px 패널이 있는 화면은 `.main`(패딩을 포함한 flex 컨테이너, `flex:1`이라 그 자체 폭은 620보다 넓다 — 1280px 데스크톱에서 실측 708px)을 재면 안 된다. `.main`은 `padding: 46px 44px`를 갖고 있어 그 안의 실제 콘텐츠는 `708 - 44 - 44 = 620px`로 정확히 맞다. **콘텐츠 요소 자체**(카드·행)를 재야 이 시나리오의 의도(글줄이 안 길어지는지)를 올바르게 검증한다. **정정 근거 보강(2026-08-28, 11.1절 갱신)**: `.main`의 708px는 우연이 아니라 사양값이다 — discussion.md 11.1절이 "사이드바 236 + 본문 708 + 우측 336"이 1280px에서 정확히 맞아떨어진다고 명시했다(`236+708+336=1280`). 다만 셸 자체의 최대 폭은 1280이 아니라 **1440**으로 정해져 있다(같은 11.1절, 같은 날 재변경) — 1280을 넘으면 `.main`이 868까지 늘어나되 콘텐츠는 여전히 620이다. 아래 29.65절(MAXWIDTH)이 이 셸 전체 1440px 상한과 컨테이너/콘텐츠 구분을 별도로 다룬다. |
| TPC-27 | **우측 요약에 새 정보 없음 (우측 패널이 있는 홈·메모 두 화면만 해당)** | 데스크톱 우측 요약(30.7절 PANELUNIFIED로 통일된 홈·메모 공통 패널)의 각 항목이 다른 화면·탭에 이미 존재하는 내용인지 하나씩 대조 | 우측 요약의 모든 정보가 다른 곳(메모 탭 등)에도 동일하게 존재하는 것의 복제다. 우측 요약에서만 볼 수 있는, 다른 어디에도 없는 새로운 정보가 있으면 실패로 기록한다(11.2절 "정보를 추가하지 않습니다"). '나'·'할 일'은 애초에 우측 패널이 없어야 하므로 이 항목의 대상이 아니다 — 그 둘은 TPC-25a·TPC-25b로 별도 확인한다. |
| TPC-28 | **타이포 확장 범위 제한** | 모바일·태블릿·데스크톱 세 구간에서 D-day, 제목(예: 화면 타이틀 `h1`), 본문 텍스트의 `font-size`를 각각 측정 | **정정(2026-08-28 실행 후, 캔버스 목업 육안 대조로 확인)**: D-day는 세 구간에서 `60px → 72px → 88px`로 **태블릿에서도 한 번 더 커지는 3단계**다(discussion.md 11.2절 문장 "60→88"만으로는 태블릿 중간값이 있다는 게 안 드러나지만, 실제 구현과 캔버스 목업 둘 다 72px가 있다). **제목은 `24px → 30px`로 딱 한 번 커지되, 그 시점이 태블릿(744px)이다** — 데스크톱에서 처음 커진다고 적었던 최초 기대값이 틀렸다. 태블릿 목업(`Tablet · 834 × 1000 · 할 일`)을 모바일 목업과 육안으로 비교하면 제목이 이미 커져 있는 것이 보인다. **본문은 세 구간 모두 `15px`(또는 화면별 고정값)로 그대로**다. D-day·제목이 아닌 다른 텍스트(라벨, 캡션, 메타 등)까지 덩달아 커졌으면 실패로 기록한다. |
| TPC-29 | **터치 대상 48px 유지 + hover는 데스크톱 전용** | 태블릿 폭에서 탭·버튼 등 클릭 대상 크기 측정(최소 48×48px 유지 확인) + 태블릿과 데스크톱 각각에서 마우스 hover 시 스타일 변화 확인 | 태블릿에서도 터치 대상이 모바일과 같은 최소 48px를 유지한다. hover 상태(배경색 변화 등)는 **데스크톱에서만** 나타나고 태블릿에서는 나타나지 않는다(11.2절 "hover 상태는 데스크톱에서만 씁니다" — 터치 기기에서 hover가 남아 있으면 탭 후에도 hover 스타일이 눌어붙는 스티키 호버 문제로 이어질 수 있다). |

### 29.65 앱 셸 최대 폭 1440px (discussion.md 11.1절, 2026-08-28 추가 / 같은 날 1280→1440으로 재변경)

> **정정(2026-08-28)**: 이 절은 원래 최대 폭 1280 기준으로 쓰였다. discussion.md 11.1절이 다시
> 갱신되어 최대 폭이 **1440**으로 넓어졌다("처음 1280으로 정했다가 넓혔습니다"). 아래 표는 세
> 기준 폭(1280 / 1440 / 1920)에서의 기대값을 1440 상한 기준으로 다시 계산한 것이다.
>
> | 뷰포트 | 셸 폭 | 좌우 여백(각) |
> |---|---|---|
> | 1280 | 1280 (아직 상한 밑) | 0 |
> | 1440 | 1440 (상한에 정확히 도달) | 0 |
> | 1920 | 1440 (상한에서 멈춤) | 240 |
>
> 세 폭 모두에서 사이드바 236 · 우측 336 · 본문 **콘텐츠** 620은 고정이다. 다만 본문
> **컨테이너**(`.main`, `flex:1`)는 셸이 늘어나는 만큼 같이 늘어난다 — 1280에서는 708(=1280−236−336),
> 1440·1920에서는 868(=1440−236−336). **컨테이너가 868로 늘어도 그 안의 실제 콘텐츠는 여전히
> 620이어야 한다**는 것이 이번 갱신의 핵심 함정이다(TPC-26에서 이미 한 번 컨테이너와 콘텐츠를
> 헷갈려 오판할 뻔했던 것과 같은 종류 — 반드시 컨테이너와 콘텐츠를 나눠 잰다).

캔버스의 데스크톱 목업이 전부 1280×800으로 그려져 있고, 그 폭에서 사이드바 236 + 본문 708 + 우측 336이 정확히 맞아떨어진다(11.1절). 다만 최대 폭 자체는 목업 폭(1280)이 아니라 **1440**으로 정해졌다 — 1280을 넘어서면 본문 컨테이너(`.main`)가 868까지 함께 늘어나되, 그 안의 실제 콘텐츠는 620에 묶여 남는 공간이 여백으로 흡수된다. 창이 1440보다 더 넓어지면 **컨테이너까지 포함해 셸 전체가 1440에서 멈추고**, 더 넓은 창에서는 앱 셸 전체가 가운데 정렬된다. 이 절은 그 상한(1440)과, 1280~1440 구간에서 컨테이너만 늘고 콘텐츠는 안 느는 동작이 실제로 지켜지는지를 확인한다.

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| MAXWIDTH-01 | 1280px에서 셸 폭 = 1280, 여백 0 | 뷰포트 1280px에서 앱 셸(사이드바+본문+우측 패널을 감싸는 최상위 컨테이너) 실제 폭과 좌우 여백 측정 | 셸 폭 1280px, 좌우 여백 0(아직 1440 상한에 못 미치므로 뷰포트와 셸이 같다). |
| MAXWIDTH-02 | 1440px에서 셸 폭 = 1440, 여백 0 | 뷰포트 1440px에서 같은 셸 폭과 좌우 여백 측정 | 셸 폭 1440px(상한에 정확히 도달), 좌우 여백 0. |
| MAXWIDTH-03 | 1920px에서 셸 폭은 1440에서 멈춤 | 뷰포트 1920px에서 같은 셸 폭 측정 | 1920이 아니라 **1440px 그대로**다. 셸이 뷰포트를 따라 계속 늘어나면(1920까지) 실패로 기록한다. |
| MAXWIDTH-04 | 좌우 여백 균등 (가운데 정렬) | 1920px에서 셸의 좌측 여백과 우측 여백을 측정 | 두 여백이 같다(`(뷰포트 폭 − 1440) / 2`). 1920px에서는 좌우 각 240px가 기대값이다. 한쪽으로 치우쳐 있으면 실패로 기록한다. |
| MAXWIDTH-05 | 사이드바 236 · 우측 336 그대로 유지 | 1280/1440/1920px 세 폭 각각에서 사이드바 폭과 우측 요약 패널 폭 측정(홈·메모 화면) | 세 폭 모두에서 사이드바 236px, 우측 패널 336px로 변하지 않는다(셸이 1440에서 상한에 걸린 뒤에도 당연히 그래야 하지만, 셸 폭 검사와 별개로 각 요소도 직접 재서 확인한다). |
| MAXWIDTH-06 | **콘텐츠는 안 늘어나지만 컨테이너는 늘어남 — 이 절의 핵심** | 1280/1440/1920px 세 폭 각각에서 홈·메모의 `.main`(컨테이너) 폭과, 그 안의 실제 콘텐츠(`NextActionCard` 등) 폭을 함께 측정 | `.main` 컨테이너는 1280에서 **708px**, 1440·1920 두 폭 모두에서 **868px**(셸이 1440에서 멈추므로 두 폭에서 같은 값)로 커진다. 반면 그 안의 실제 콘텐츠는 세 폭 모두에서 **620px로 동일**하게 유지되어야 한다. 컨테이너(.main)만 재고 620을 넘는다고 오판하지 않도록 반드시 콘텐츠 요소를 따로 잰다(TPC-26과 같은 함정). 컨테이너가 커졌는데 콘텐츠까지 같이 커지면 "본문 폭은 620px에서 멈춘다"는 확장 규칙 위반이므로 실패로 기록한다. |
| MAXWIDTH-07 | 우측 패널이 없는 화면('나'·'할 일')도 셸 상한 안에서 동작 | 1280/1440/1920px 세 폭 각각에서 '나'·'할 일' 화면의 셸 폭과 사이드바+본문(620) 이후 남는 공간 확인 | discussion.md가 이 두 화면에 대해 명시하지 않은 부분이다 — 셸 자체는 여전히 1440 상한(다른 화면과 같은 셸을 공유하므로) 안에 있고, 사이드바(236)+본문(620)=856을 뺀 나머지(1440 기준 584px)가 빈 배경으로 남는지, 아니면 본문이 셸 안에서 재중앙 정렬되는지를 있는 그대로 관찰해 기록한다(정답이 정해져 있지 않으므로 "무엇이 실제로 일어나는가"를 사실대로 남기고, 뷰포트에 따라 이 여백이 커지지만 않으면 — 즉 1440 셸 상한 자체는 지켜지면 — 결함으로 보지 않는다). |

### 29.6 캔버스 목업과 실제 렌더 육안 대조 — 수치가 맞아도 배치가 다를 수 있다

지금까지의 TPC 시나리오는 전부 **수치**(폭, 높이, 간격, 폰트 크기)를 하나씩 재는 방식이었다. 그런데 개별 수치가 전부 맞아도 요소들의 **배치·순서·상대적 정렬**이 캔버스와 다를 수 있다 — 수치 기반 검사는 이런 차이를 잡지 못한다. `Docs/Design/WabiDesignSystem.dc.html` 06절("태블릿 · PC")에 실제 목업 7개가 있으므로, 그 목업을 스크린샷으로 뜨고 실제 렌더 결과도 같은 비율로 스크린샷을 떠서 **나란히 놓고 눈으로 대조**한다.

캔버스 06절의 목업 7개(각각 `font-size:13px;font-weight:700` 캡션으로 라벨이 붙어 있어 식별 가능):

| # | 라벨(캔버스 원문) | 대응 화면·구간 |
|---|---|---|
| 1 | `Desktop · 1280 × 800 · 홈` | 데스크톱(≥1180px), 홈 |
| 2 | `Desktop · 1280 × 800 · 메모` | 데스크톱, 메모 |
| 3 | `Desktop · 1280 × 800 · 나` | 데스크톱, 나 |
| 4 | `Tablet · 834 × 1000 · 할 일` | 태블릿(744~1179px), 할 일 |
| 5 | `Tablet · 834 × 1000 · 홈` | 태블릿, 홈 |
| 6 | `Tablet · 834 × 1000 · 메모` | 태블릿, 메모 |
| 7 | `Tablet · 834 × 1000 · 나` | 태블릿, 나 |

(데스크톱 "할 일" 목업이 없는 것은 11.6절대로 정상이다 — TPC-25b/25c가 이미 그 화면을 다룬다.)

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| VISUAL-01~07 | **목업 7개 각각 육안 대조** | 각 목업을 캔버스 파일에서 스크린샷으로 뜨고(헤드리스 브라우저로 `dc.html`을 열어 해당 목업 요소만 크롭), 실제 앱을 목업과 같은 뷰포트(1280×800 또는 834×1000)와 같은 화면·구간으로 띄워 동일하게 스크린샷을 뜬 뒤, 두 이미지를 나란히 놓고 확인 | 요소의 **배치 순서**(위→아래, 좌→우), **정렬**(좌측/중앙/우측 정렬 여부), **여백의 상대적 크기**, **줄바꿈 위치**가 목업과 실제 렌더에서 일치한다. 폭·높이 같은 절대 수치는 앞선 TPC 시나리오에서 이미 확인했으므로 여기서는 "숫자는 맞는데 그림이 다른" 경우를 잡는 데 집중한다 — 예: 사이드바 내비 항목의 세로 순서가 뒤바뀌었거나, 우측 요약의 메모 목록과 어려움 카드 순서가 캔버스와 반대이거나, 태블릿 레일의 탭 아이콘이 캔버스보다 위/아래로 치우쳐 있는 등. 차이를 발견하면 스크린샷 두 장과 함께 구체적으로 어느 요소가 어떻게 다른지 기록한다. |

**실행 상태(29절 전체, 29.1~29.6)**: 2026-08-28 실행 완료. 경계값·태블릿/데스크톱 세부 규격·패널 유무 4화면 전수·타이포 확장·본문 620 상한·육안 대조(3개 목업)까지 확인했고, 결함 없이 캔버스와 일치함을 확인했다(TPC-26·TPC-28의 최초 기대값 오류 2건은 실행 중 발견해 위 표에서 정정). 결과는 QAResult.md 참고.

## 30. 사용자 지적 수정 2차 (discussion.md 19절, 2026-08-28)

디자인 목업(캔버스)과 실제 렌더를 대조하며 사용자가 직접 찾아낸 결함 6건(19.1~19.6). Frontend가 수정 중이며, 수정본이 오면 아래를 실행한다.

### 30.1 우측 요약 패널이 전체 높이를 채우지 않음 (19.1절)

| ID | 시나리오 | 절차 | 기대 결과 |

### 30.5 D-day 캡션·숫자를 세로로, 바깥은 가로인 중첩 구조 (19.5절)

`호주 출국까지` 캡션과 `D-12` 숫자는 **세로**(캡션 위, 숫자 아래, `flex-direction: column`, `gap: 10px`)여야 하고, 그 세로 블록 전체가 진행률과 **가로**로 나란히 놓인다(`align-items: flex-end`, `gap: 40px`). 즉 바깥(캡션+숫자 블록 vs 진행률)은 가로, 안쪽(캡션 vs 숫자)은 세로인 중첩이다. 이 구조가 무너지면 88px(데스크톱)까지 커지는 숫자가 캡션에 밀려 어긋난다.

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| DDAYLAYOUT-01 | **안쪽 — 캡션·숫자 세로 배치** | 홈 화면에서 D-day 블록(캡션 `"{국가} 출국까지"` + 숫자 `"D-N"`을 감싸는 컨테이너)의 `flex-direction`과 두 자식의 상대 위치 확인 | `flex-direction: column`이고 캡션이 위, 숫자가 아래다. `gap`이 대략 10px 근방이다. |
