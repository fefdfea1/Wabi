## 1. `app/layout.tsx` 인라인 스크립트(`dangerouslySetInnerHTML`)

### 현재 상태: 안전

```ts
const THEME_INIT_SCRIPT = `(function(){try{var t=localStorage.getItem("theme");if(t)document.documentElement.setAttribute("data-theme",t)}catch(e){}})()`;
```

이 문자열은 **빌드 타임에 고정된 리터럴**이고, 어떤 변수도 보간(interpolation)하지 않습니다. `dangerouslySetInnerHTML`이 위험해지는 것은 그 안에 사용자 입력·쿼리 파라미터·쿠키·API 응답처럼 요청마다 달라질 수 있는 값을 문자열로 끼워 넣을 때입니다. 지금은 그런 값이 전혀 들어가지 않으므로 주입 지점이 없습니다.

### 주의할 조건 (앞으로 이 패턴을 건드릴 때)

`<script>` 태그에 넣는 `dangerouslySetInnerHTML`은 일반 `<div>`의 경우와 달리 **HTML 이스케이프가 아니라 JS 코드로 그대로 실행**됩니다. 그래서 나중에 누군가 "초기 국가값도 서버에서 내려주자", "쿠키로 저장된 테마를 SSR에 반영하자"는 이유로 이 문자열에 변수를 끼워 넣게 되면, 그 순간부터는 진짜 주입 지점이 됩니다. 예:

```ts
// 절대 이렇게 하지 않는다
const THEME_INIT_SCRIPT = `document.documentElement.setAttribute("data-theme","${theme}")`;
```

`theme` 값에 `";document.write('...')//` 같은 문자열이 들어가면 그대로 실행됩니다. `JSON.stringify()`만으로는 따옴표 이스케이프는 되지만 `</script>` 문자열이 값 안에 포함되면 브라우저 HTML 파서가 스크립트를 그 지점에서 끊어버려(`</script>` 조기 종료) 이후 내용이 마크업으로 해석되는 문제는 별도로 막아야 합니다.

**지금 문서에 못박아 둘 규칙**:
- 이 인라인 스크립트 문자열에는 앞으로도 **어떤 값도 보간하지 않는다**. 정적 리터럴로만 유지한다.
- 값을 넣어야 하는 상황이 생기면(예: 서버 렌더 시점 값 반영) 반드시 PM 승인을 거치고, `JSON.stringify(value).replace(/</g, "\\u003c")` 형태로 `<`를 이스케이프한 뒤에만 삽입한다.
- CSP(`Content-Security-Policy`)는 현재 `next.config.ts`에 설정이 없습니다. 정적 프리렌더 전용 앱이라 우선순위가 낮지만, 향후 사용자 입력을 화면에 그대로 렌더링하는 기능(예: 할 일 본문 미리보기)이 추가되면 `script-src 'self'` 수준의 헤더 도입을 재검토합니다.

## 2. localStorage에 보관하는 값의 범위

### 현재 상태

지금 코드가 실제로 저장하는 값은 `theme` 키 하나뿐입니다(`ThemeToggle.tsx`). `Task`/`Country` 타입(`domain.ts`)에도 이름·이메일·여권번호 같은 개인식별정보(PII) 필드는 없습니다 — `Task`는 `title/meta/tag/body/items` 등 앱 도메인 값만, `Country`는 국가 코드와 라벨뿐입니다.

discussion.md 6·7절 기준으로 앞으로 localStorage에 추가될 값은 세 종류입니다: 테마, 국가 선택, 직접 추가한 할 일. 이 세 가지는 서버로 전송되지 않고 기기 안에서만 쓰이므로 그 자체로는 적절합니다.

### 앞으로 지켜야 할 경계

1. **앱이 구조화된 필드로 개인식별정보를 요구하지 않는다.** "나" 탭에 여권번호·주민등록번호·실명 같은 필드를 구조화된 입력으로 추가하지 않습니다. 이 앱의 목적(D-day·할 일 진행)에는 그런 필드가 필요 없고, 만약 필요해지면 별도로 PM 승인을 받습니다.
2. **사용자가 자유 텍스트(할 일 제목/본문)에 스스로 민감한 내용을 적는 것은 앱이 막을 수 없고 막을 필요도 없습니다** — 서버로 전송되지 않는 한 위험 범위가 늘지 않기 때문입니다. 다만 이 전제(서버로 전송되지 않음)가 깨지는 순간 위험이 커지므로 아래 3번이 핵심입니다.

### 2-1. 추가 확인: 출국일 입력 필드는 경계 안쪽 (다음 차수 온보딩 대비)

product-team으로부터 "온보딩에 출국일 입력이 추가되면 위 1번 경계의 안쪽인지 바깥쪽인지" 확인 요청을 받아 판단합니다.

**결론: 경계 안쪽 — 허용.** 1번 규칙이 금지하는 것은 여권번호·주민등록번호·실명처럼 (a) 그 값 자체가 재사용 가능한 신원 증명 수단이고 (b) 이 앱의 핵심 기능에 꼭 필요하지도 않은 "신원 식별자"입니다. 출국일은 둘 다 해당하지 않습니다.

- discussion.md 1절이 "첫 화면은 D-day"라고 이미 확정했습니다. D-day 표시는 출국일 없이는 애초에 동작할 수 없는 이 앱의 핵심 기능이지, 부가적으로 수집하는 값이 아닙니다.
- 날짜 하나만으로는 특정 개인을 식별할 수 없습니다. 여권번호·주민등록번호처럼 그 값 자체가 신원 증명에 재사용될 수 있는 값과는 위험 등급이 다릅니다.
- discussion.md 9절은 "온보딩(국가·출국일 입력)"을 애초에 다음 차수 범위로 이미 계획해 두었습니다. 지금 새로 생기는 수집이 아니라 이미 승인된 범위 안의 값입니다.
- "서버로 나가지 않는다"는 이 앱 전체의 전제(discussion.md 9절)가 이 값에도 그대로 적용되고, 이 필드만 따로 예외적인 경로로 나갈 이유가 없습니다.

**허용하되 붙이는 조건:**

1. **확장 기준을 고정합니다.** 앞으로 "나" 탭에 필드가 추가될 때마다 "이 값 자체가 재사용 가능한 신원 증명 수단인가"를 기준으로 판단합니다. 날짜·국가처럼 그 자체로 개인을 특정하지 못하고 핵심 기능에 필요한 값은 허용, 여권번호·주민등록번호·실명류는 여전히 금지합니다(1번 규칙 유지). 판단이 애매한 필드가 생기면 추가 전에 Security에 다시 확인합니다.
2. **텔레메트리 규칙(3번)의 적용 대상에 출국일·비자 만료를 명시적으로 포함합니다.** 향후 분석·크래시 리포팅 SDK를 도입할 때, 페이로드에 국가·출국일·비자 만료 값이 섞이지 않는지 확인한 뒤에만 도입합니다.
3. **"하나의 객체로 묶어 저장하지 말 것"은 이 앱 구조에서는 실효성이 없는 조건이라 채택하지 않습니다.** localStorage는 같은 오리진의 코드라면 키를 몇 개로 나누든 전부 읽을 수 있어, 값을 여러 키로 쪼개는 것이 서버 DB의 컬럼 단위 접근 권한처럼 노출 범위를 좁혀주지 않습니다. 저장 시 객체를 하나로 묶을지 키를 나눌지는 Frontend가 편한 방식으로 정해도 됩니다.
4. **대신 실제로 조합 위험이 생기는 지점을 지정해 둡니다.** 향후 "내 정보 내보내기/백업/공유" 같은 기능이 추가되어 국가·출국일·비자 만료가 파일이나 링크 하나로 묶여 기기 밖으로 나가게 되는 순간이 진짜 위험 지점입니다. 그런 기능은 이번 허용 범위에 포함되지 않으며, 추가하기 전에 반드시 별도로 Security 검토와 PM 승인을 받습니다.
3. **분석·크래시 리포팅 SDK를 넣을 때가 실제 위험 지점입니다.** 지금은 없지만, 나중에 Sentry·GA 같은 SDK를 추가하면 이 SDK들은 종종 DOM 상태나 콘솔 로그를 통째로 캡처해 외부 서버로 보냅니다. 사용자가 할 일 제목에 적은 개인 정보가 이 경로로 조용히 유출될 수 있습니다. **어떤 형태로든 외부로 텔레메트리를 보내는 SDK를 추가할 때는, localStorage/상태 값이 페이로드에 섞이지 않는지 확인하고 PM 승인을 받는다**는 원칙을 지금 못박아 둡니다.
4. **폰트 로딩은 이미 올바른 방식입니다.** `next/font/google`은 빌드 타임에 폰트 파일을 자체 호스팅하므로 사용자가 페이지를 열 때마다 Google에 요청이 나가지 않습니다(`<link href="fonts.googleapis.com">`로 직접 불렀다면 매 방문마다 사용자 IP가 Google로 전달됩니다). 이 방식을 앞으로도 유지합니다.

## 3. 파일 추가 시트의 "기기에만 저장" 약속

### 현재 상태

`Docs/Design/WabiDesignSystem.dc.html:454`의 원본 문구는 다음과 같습니다.

> 서류는 기기에만 저장되며 만료일 알림에 사용됩니다.

discussion.md 9절은 "실제 파일 업로드와 기기 저장"을 이번 구현 범위에서 명시적으로 제외했고, 실제로 `DocsScreen.tsx`는 정적 placeholder이며 파일 추가 시트 자체가 아직 코드로 존재하지 않습니다. 따라서 지금 이 약속을 어기는 코드는 없습니다.

### 다음 차수 구현 전에 문서에 못박아야 할 제약

이 약속은 "업로드 기능을 안 만들면 지켜지는" 소극적인 약속이 아니라, 구현 방식에 따라 조용히 깨질 수 있는 약속입니다. 구현 착수 전에 아래를 TechSpec/설계 승인 절차에 명시하는 것을 권고합니다.

1. **서버 업로드 금지를 아키텍처 규칙으로 고정합니다.** 파일을 어떤 형태로든(백업 목적이라도) 외부 API·스토리지(S3, Firebase Storage, Cloudinary 등)로 전송하는 코드는 추가하지 않습니다. 이미 Architecture.md/TechSpec.md의 "백엔드·유료 서비스 도입 시 사용자 승인" 절차가 있으므로, 파일 업로드 기능 자체가 이 절차의 트리거임을 명시합니다.
2. **저장 매체로 localStorage를 쓰지 않습니다.** localStorage는 문자열 전용이고 브라우저별로 대략 5~10MB로 용량이 작으며 동기 API라 큰 base64 문자열을 넣으면 메인 스레드가 멈춥니다. 사진·PDF 원본은 **IndexedDB**(Blob/File 객체를 직접 저장)로 보관하도록 지금 결정해 둡니다. 나중에 localStorage로 먼저 만들고 IndexedDB로 옮기면 이미 저장된 사용자 데이터의 마이그레이션 문제가 생깁니다.
3. **텔레메트리 경유 유출을 같은 원칙으로 막습니다.** 2번 항목과 동일하게, 향후 에러 추적/애널리틱스 SDK가 파일 이름이나 파일 내용을 로그에 포함시키지 않는지 확인합니다. 파일 이름 자체에 개인정보가 들어갈 수 있습니다(예: "여권_홍길동.pdf").
4. **미리보기 구현 시 파일 내용을 안전하게 렌더링합니다.** 상세 화면에서 저장된 사진/PDF를 미리 보여줄 때는 `URL.createObjectURL(blob)`로 만든 URL을 `<img>`나 `sandbox` 속성이 있는 `<iframe>`에 씁니다. 사용자가 고른 파일이 SVG인 경우 `dangerouslySetInnerHTML`이나 SVG를 문서에 인라인으로 삽입하는 방식으로 미리보기를 만들지 않습니다 — SVG는 내부에 `<script>`를 포함할 수 있어 사용자 자신이 고른 파일이라도 인라인 삽입 시 그 안의 스크립트가 앱과 같은 오리진에서 실행됩니다.
5. **"저장" 약속의 한계를 카피에 정직하게 반영합니다.** 브라우저 저장소는 사용자가 브라우징 데이터를 지우거나(특히 iOS Safari는 장기 미사용 사이트의 저장 공간을 자동으로 비울 수 있습니다), 앱을 재설치하면 함께 사라집니다. "기기에만 저장"은 정확한 표현이지만 "안전하게 보관됩니다"처럼 영구 보존을 암시하는 문구로 확장하지 않습니다. 필요하면 설정 화면에 "브라우저 저장공간을 지우면 함께 삭제됩니다" 같은 안내를 추가하는 것을 고려합니다.

## 4. 저장소의 자격증명·비밀값과 `.gitignore`

### 확인 결과

- `.env`, `.env.local` 등 환경변수 파일은 현재 존재하지 않습니다.
- `package.json`/`package-lock.json`/소스 전체를 `api[_-]?key|secret|token|password|credential` 패턴으로 검색한 결과 하드코딩된 자격증명은 없습니다.
- 의존성은 `next`, `react`, `react-dom`(런타임)과 타입/컴파일러(devDependencies)뿐이라 API 키가 필요한 SDK 자체가 없습니다.
- `.gitignore`는 `node_modules/`, `.next/`, `out/`, `build/`, `.env`, `.env.local`, `.env*.local`, `npm-debug.log*`, `*.tsbuildinfo`, `next-env.d.ts`, `.DS_Store`를 포함하고 있어 이 시점 프로젝트 구성 기준으로는 충분합니다.
- 단, 이 디렉터리는 아직 **git 저장소로 초기화되어 있지 않습니다**(`.git` 없음). `.gitignore`는 `git init` 전까지는 아무 효과가 없으므로, 첫 커밋 전에 `git status`로 스테이징되는 파일을 한 번 확인하는 절차를 권고합니다(이 프로젝트 성격상 비밀값이 생길 여지는 작지만, 습관을 지금부터 들여둡니다).

### 지금 못박아 둘 구조적 제약

이 앱은 discussion.md 9절에 따라 백엔드(`src/Back`)가 없습니다. **백엔드가 없다는 것은 클라이언트 번들에 들어가는 모든 값이 사실상 전부 공개된다는 뜻입니다.** Next.js에서 서버 컴포넌트/API 라우트 없이 클라이언트 코드나 `NEXT_PUBLIC_` 환경변수에 넣은 값은 빌드 결과물에 그대로 노출됩니다. 따라서:

## 5. 외부 출처 링크 (`sourceUrl`, discussion.md 13절)

### 확인 결과

`sourceUrl`은 `src/Front/common/data/tasks.ts`에 개발자가 직접 타이핑한 하드코딩 문자열 상수이며, 이용자 입력이나 외부 응답에서 오는 값이 아닙니다. 지금 확인한 모든 값이 이미 `https://`로 시작하고, 대상은 각국 정부 기관(`immi.homeaffairs.gov.au`, `canada.ca`, `kr.emb-japan.go.jp` 등)과 조사로 신원이 확인된 통신사(`rogers.com`, `nttdocomo.co.jp`)입니다. 링크를 실제로 렌더링하는 컴포넌트(`SourceLink` 등)는 아직 구현되지 않았습니다(13절 스펙만 존재).

### 5-1. `target="_blank"` + `rel="noopener noreferrer"`로 충분한가

**충분합니다.** 이 조합이 막는 두 가지 문제와, 이 앱에 각각이 왜 들어맞는지는 다음과 같습니다.

- **`noopener`**: 새 탭에서 열린 페이지가 `window.opener`를 통해 원래 탭(Wabi)의 위치를 조작하는 "역탭내빙(reverse tabnabbing)"을 막습니다. 목적지가 공식 정부·통신사 사이트라 지금 당장 악의적으로 이 경로를 쓸 이유는 없지만, 도메인이 나중에 만료되어 제3자가 되사가는 등의 장기적 시나리오를 막아 주는 표준 방어이므로 계속 유지합니다.
- **`noreferrer`**: 이동할 때 `Referer` 헤더 자체를 보내지 않습니다. 최신 브라우저는 `noreferrer`가 `noopener`를 포함하지만, 구형 브라우저 호환을 위해 두 값을 함께 쓰는 지금 방식이 맞습니다.

리퍼러 유출 관점에서 추가로 걱정할 지점(URL에 쿼리 파라미터로 이용자 식별값을 붙이는 것)은 애초에 해당하지 않습니다 — `sourceUrl`은 정적 리터럴이라 요청마다 달라지는 이용자별 값이 붙을 수 없고, 지금 값 중 쿼리 파라미터가 있는 것(`?boardNo=100013`, `?idx=15206`, `?seq=353806`)도 전부 그 사이트 자체의 게시물 번호일 뿐 Wabi가 채워 넣는 값이 아닙니다.

다만 이번 기회에 다음 두 가지를 **권장(선택)**으로 덧붙입니다. 둘 다 "이 링크 하나"가 아니라 앞으로 생길 수 있는 다른 외부 링크까지 감싸는 안전망입니다.

1. `app/layout.tsx`에 `<meta name="referrer" content="strict-origin-when-cross-origin">`를 추가합니다. 최신 브라우저의 기본값과 같은 값이라 지금 동작은 바뀌지 않지만, 나중에 `rel` 속성을 깜빡한 `<a>`나 외부 이미지 태그가 추가돼도 리퍼러가 전체 URL이 아니라 출처(origin)까지만 나가도록 보장합니다.
2. 출처 링크는 반드시 공용 컴포넌트(`SourceLink`) 하나로만 렌더링하고, 화면마다 `<a>`를 따로 작성하지 않습니다. 13.2절의 `target`/`rel`/`aria-label` 규칙을 컴포넌트 한 곳에 고정해 두면, 나중에 어느 화면에서 속성 하나를 빠뜨리는 실수 자체가 나지 않습니다.

### 5-2. 앞으로 URL 목록에 값이 추가될 때 지켜야 할 제약

1. **하드코딩된 리터럴만 허용합니다.** `sourceUrl`은 데이터 파일(`tasks.ts` 등)의 TypeScript 문자열 리터럴로만 존재해야 하며, 이용자 입력·URL 쿼리 파라미터·API 응답·외부 fetch 결과에서 온 값을 이 자리에 저장하거나 렌더링하지 않습니다. "출처 URL을 서버에서 동적으로 받아온다"거나 "이용자가 직접 참고 링크를 추가한다"는 기능은 완전히 다른 위협 모델(주입 가능한 href, `javascript:` URI, 오픈 리다이렉트 악용)이 되므로, 그런 기능이 제안되면 이번 승인과 별개로 Security 검토를 다시 받습니다.
2. **`https://`만 허용합니다.** `http://`는 평문 전송이라 중간자가 응답 내용을 바꿔치기할 수 있어, "공식 출처"라는 신뢰 자체가 훼손됩니다. `TASKS_BY_COUNTRY`/`GUIDE_BY_COUNTRY`/`PAIN_BY_COUNTRY`/`COUNTRIES`를 순회하며 모든 `sourceUrl`이 `https://`로 시작하는지 확인하는 테스트를 하나 추가하는 것을 권장합니다 — 사람이 리뷰에서 놓쳐도 테스트가 잡아 줍니다.
3. **렌더링 컴포넌트에도 같은 방어를 한 겹 더 둡니다.** `SourceLink` 컴포넌트가 `href.startsWith("https://")`가 아닌 값은 아예 렌더하지 않도록 합니다. discussion.md 13.3절이 이미 "값이 없으면 줄 자체를 렌더하지 않는다"를 정해 두었으므로, "값이 있어도 `https://`가 아니면 렌더하지 않는다"로 같은 원칙을 자연스럽게 확장하면 됩니다. `javascript:`/`data:` 같은 스킴은 이 조건 하나로 함께 차단됩니다.
4. **출처는 실제로 확인된 1차 기관 도메인만 씁니다.** 정부 기관(`.gov`, `.go.kr`, 대사관)과 조사로 신원이 확인된 사업자 공식 도메인만 넣고, 단축 URL(bit.ly 등)이나 조사자가 직접 열어보지 않은 2차 정리 글은 넣지 않습니다. 단축 URL은 실제 목적지를 감춰 코드 리뷰 시점에 어디로 연결되는지 확인할 수 없게 만들고, 소유권이 바뀌면 조용히 다른 페이지(피싱 포함)로 뒤바뀔 수 있습니다.
5. **데이터 반영 시점에 사람이 한 번 더 열어 확인합니다.** Research-team 산출물을 `tasks.ts`에 옮길 때, 오탈자로 인한 유사 도메인 하드코딩(예: `.gov.au`를 `.gov.au.co`처럼 잘못 옮겨 적는 경우)을 잡기 위해 각 `sourceUrl`을 최소 한 번 직접 열어 실제로 그 기관 페이지가 맞는지 대조합니다.

### 5-3. 구현 검토 (`src/Front/common/component/SourceLink.tsx`)

Front-end가 구현을 마친 실제 코드를 확인했습니다. 구현 요지: `url`이 없거나 `new URL(url)`이 예외를 던지면 `null`을 반환하고, 통과하면 `target="_blank"` `rel="noopener noreferrer"`로 `<a>`를 렌더하며 링크 문구와 `aria-label`에 `hostname`을 넣습니다.

**질문 1 — `noopener noreferrer`로 충분한가**: 네, 5-1절의 결론이 그대로 적용됩니다. `url`이 전부 `tasks.ts`의 하드코딩 리터럴이라 요청마다 달라지는 이용자 식별값이 URL에 붙을 수 없고, 지금 값들의 쿼리 파라미터(`?boardNo=`, `?idx=`, `?seq=`)도 목적지 사이트 자체의 게시물 번호일 뿐입니다. 추가 조치는 필요 없습니다. (5-1절에서 권장했던 `<meta name="referrer">` 전역 안전망과 `SourceLink` 단일 컴포넌트화는 이미 컴포넌트가 하나로 존재하므로 두 번째는 충족되었고, 첫 번째는 아직 `app/layout.tsx`에 추가되지 않았습니다 — 선택 사항이라 필수는 아닙니다.)

**질문 2 — 앞으로 지켜야 할 제약, 특히 https 전용·이용자 입력 금지**: 5-2절에서 정한 원칙(하드코딩 리터럴만 허용, `https://`만 허용)은 여전히 유효합니다. 다만 실제 코드를 보니 **이 원칙이 컴포넌트 안에서는 전혀 강제되고 있지 않습니다.** `new URL()`은 문법적으로 올바른 절대 URL이면 스킴이 무엇이든(`http:`, `javascript:`, `data:`, `mailto:`, `file:` 등) 예외 없이 통과시킵니다. 즉 지금 안전한 이유는 코드가 막아서가 아니라 "누군가 `tasks.ts`에 이상한 값을 타이핑하지 않았다"는 데이터 쪽 규율에만 의존하고 있습니다. 이는 1절에서 지적한 인라인 스크립트 패턴과 같은 종류의 위험입니다 — 지금은 안전하지만 전제(하드코딩 리터럴만 들어온다)가 깨지는 순간(예: 이 컴포넌트를 나중에 이용자가 입력한 링크나 API로 받아온 값에 재사용하는 경우) 조용히 `javascript:` URI 실행 같은 실제 위험으로 바뀝니다.

**권고 (코드 반영 요청)**: `SourceLink`가 파싱 성공 여부만 보지 말고 스킴까지 직접 검사하도록 한 줄을 추가합니다.

```ts
let parsed: URL;
try {
  parsed = new URL(url);
} catch {
  return null;
}
if (parsed.protocol !== "https:") return null;
```

이렇게 하면 "https만 허용"이라는 규칙이 데이터 작성자의 규율이 아니라 컴포넌트 자체의 방어로 바뀌어, 이 컴포넌트가 나중에 다른 목적으로 재사용되거나 데이터 파일에 실수로 잘못된 스킴 값이 들어가도 화면에 렌더링되지 않습니다. 이용자 입력·API 응답을 이 자리에 넣지 않는다는 규칙은 여전히 컴파일러가 강제할 수 없는 관례이므로, `SourceLinkProps`의 `url` 옆에 "반드시 `common/data`의 하드코딩 상수에서만 전달할 것, 이용자 입력이나 fetch 결과를 직접 연결하지 말 것"이라는 주석을 남겨 두는 것을 권장합니다.

**질문 3 — hostname을 그대로 노출하는 것이 오인을 유발할 수 있는가**:

- **기본 구조는 안전합니다.** `domain`은 링크가 실제로 이동할 `url`과 같은 값에서 뽑아내므로, "화면에는 A 도메인이라고 쓰여 있는데 실제로는 B로 이동한다"는 식의 텍스트-목적지 불일치(전형적인 피싱 링크 패턴)가 구조적으로 발생할 수 없습니다.
- **국제화 도메인(IDN) 동형이의어 공격에도 이 구현이 유리합니다.** `URL.hostname`은 비ASCII 문자가 섞인 도메인을 유니코드 그대로 보여주지 않고 퓨니코드(`xn--...`)로 반환하므로, 키릴 문자로 라틴 알파벳을 흉내 낸 유사 도메인이 있어도 그럴듯한 모양 대신 못 보던 `xn--` 문자열로 나타나 오히려 눈에 띕니다.
- **다만 두 가지 표시상의 허점이 있습니다.**
  1. `javascript:`나 `mailto:` 처럼 authority(호스트) 자체가 없는 스킴은 `hostname`이 빈 문자열입니다. 지금 코드는 이 경우를 걸러내지 않아 "출처 " 처럼 도메인이 안 보이는데도 신뢰를 주는 "출처" 접두어가 붙은 링크가 그대로 렌더링될 수 있습니다. 위 프로토콜 검사(질문 2 권고)를 추가하면 이 경우도 함께 차단됩니다.
  2. 스킴이 `https:`이고 파싱도 정상이지만 **도메인 자체가 오탈자나 사칭인 경우**(예: 실제로는 `evil.com`인데 `immi.homeaffairs.gov.au.evil.com`처럼 기대하는 문자열로 시작하는 서브도메인/접미사)는 `URL.hostname`이 정직하게 그 값을 그대로 보여주기 때문에 컴포넌트가 막을 수 없습니다. 이는 컴포넌트의 결함이 아니라 **데이터 입력 시점의 문제**이므로, 5-2절 5번 권고(반영 시 사람이 직접 열어 대조)에 더해 다음을 추가로 권장합니다: `tasks.ts`에 실제 존재하는 `sourceUrl` 전체를 대상으로, 호스트명이 국가별로 미리 정해 둔 소수의 승인된 도메인 목록(`immi.homeaffairs.gov.au`, `whic.mofa.go.kr`, `www.kr.emb-japan.go.jp`, `canada.ca`의 하위 도메인 등)에 속하는지 확인하는 테스트를 추가합니다. 이 목록은 국가 수·기관 수가 적어 유지 비용이 작고, 사람이 놓친 오탈자·사칭 도메인을 기계적으로 잡아낼 수 있습니다.

### 확인 결과: 아직 구현되지 않았습니다

요청받은 5가지(①외부 전송 코드 부재 ②localStorage에 파일/파일명 미포함 ③미리보기가 objectURL+img/sandbox iframe만 사용하고 인라인 삽입 없음 ④objectURL 해제 ⑤카피가 영구 보존을 암시하지 않음)는 **실제 코드를 확인해야 판단할 수 있는 항목**인데, 지금 저장소를 확인한 결과 아직 코드가 없습니다.

- `src/Front/overlay/component/AddFileSheet.tsx`는 여전히 16절 이전 버전입니다 — "실제 카메라/파일 피커 연동 없이 문서 목록에 플레이스홀더 항목만 추가한다"는 주석이 그대로 있고, 시트 문구도 16.7절이 고치기로 한 옛 문장("...만료일 알림에 사용됩니다")이 그대로 남아 있습니다.
- `src/Front/docs/component/DocsScreen.tsx`도 "미리보기는 이번 범위 밖"이라는 옛 주석 그대로이고, IndexedDB에서 읽어오는 코드가 없습니다.
- 16.1절이 지정한 `src/Front/common/storage/docFiles.ts` 파일 자체가 존재하지 않습니다.
- `package.json`에 새 의존성도 추가되지 않았습니다(16.1절 "새 의존성 추가 금지"는 지금은 자동으로 지켜지고 있는 상태이지만, 아직 아무것도 구현되지 않았기 때문이기도 합니다).

파일 최종 수정 시각을 비교해도 `discussion.md`(16절 추가)가 `AddFileSheet.tsx`/`DocsScreen.tsx`보다 나중입니다 — 명세가 구현보다 먼저 나온 정상적인 순서이고, 아직 구현이 명세를 따라가지 못한 상태입니다. **존재하지 않는 코드를 검토한 것처럼 결과를 적어 드릴 수는 없으므로, 5가지 항목은 구현이 실제로 올라온 뒤 다시 요청해 주시면 코드 기준으로 하나씩 확인하겠습니다.** 그때 특히 확인할 지점을 미리 적어 둡니다.

- ① 전송 코드 부재: `fetch`/`XMLHttpRequest`/`navigator.sendBeacon` 등으로 파일 Blob이나 그 내용을 어디로도 보내지 않는지 전체 diff를 훑습니다.
- ② localStorage 미포함: `docFiles.ts`의 메타데이터 레코드(`{ id, name, mime, size, addedAt, expiresAt?, blob }`)가 16.1절대로 IndexedDB 한 곳에만 있고, `localStorage.setItem`에 파일명·메타 어느 것도 섞여 들어가지 않는지 확인합니다.
- ③ 미리보기: `URL.createObjectURL` 결과만 `<img>`/`sandbox` `<iframe>`에 쓰고, `dangerouslySetInnerHTML`이나 텍스트를 파싱해 DOM에 직접 넣는 경로가 없는지 확인합니다.
- ④ objectURL 해제: 미리보기 컴포넌트의 `useEffect` 클린업(또는 화면 전환 시점)에서 `URL.revokeObjectURL`이 생성한 URL마다 정확히 한 번 호출되는지, 특히 목록을 다시 그릴 때(리렌더링) 이전 objectURL이 새로 생성한 것으로 계속 대체되면서 예전 것이 해제되지 않고 누적되지 않는지 확인합니다.
- ⑤ 카피: 시트 문구가 16.7절이 정한 "서류는 이 기기에만 저장됩니다."로 바뀌었는지, "안전하게 보관됩니다"류의 영구 보존 암시 표현이 새로 추가되지 않았는지 확인합니다.

### `accept`에서 SVG를 빼는 것만으로 충분한가 — 판단

**충분하지 않습니다.** 지적하신 대로 `accept`는 파일 선택 대화상자가 어떤 파일을 보여줄지 걸러 주는 UI 힌트일 뿐이고, 실제로 넘어오는 `File` 객체의 내용을 검사하거나 강제하지 않습니다. 구체적으로:

- **확장자·MIME은 신뢰할 수 없는 값입니다.** `File.type`은 브라우저가 파일 확장자를 보고 추측한 값이지 실제 바이트 내용을 읽어서 판정한 값이 아닙니다. `evil.svg`를 `evil.png`로 이름만 바꿔 저장한 파일을 고르면, `accept="image/png,..."` 필터도 통과하고 `File.type`도 `image/png`로 보고될 수 있지만 실제 바이트는 여전히 SVG(XML + 잠재적 `<script>`)입니다.
- 이 앱은 16.5절에서 이미 이미지를 `<img>`로 미리보기하기로 했습니다. `<img src="blob:...">`에 넣을 Blob의 렌더링 방식은 브라우저가 Blob에 붙은 선언된 MIME 타입을 기준으로 판단하는 경우가 대부분이라 확장자만 바꾼 SVG는 이미지 디코딩에 실패해 깨진 이미지로 그칠 가능성이 높지만, 이는 브라우저 구현에 따라 갈리는 동작이라 **코드가 스스로 보장할 수 있는 성질이 아닙니다.** "우연히 안전할 수도 있다"에 의존하지 않는 편이 맞습니다.
- 따라서 확장자/`accept`/`File.type` 중 어느 것도 신뢰하지 않고, **파일의 실제 바이트(매직 넘버)를 직접 확인하는 검사를 추가하는 것을 권고합니다.**

**권고하는 구체적 방식** (16.1절의 "새 의존성 추가 금지" 원칙과 동일하게, 라이브러리 없이 구현 가능합니다):

파일을 IndexedDB에 저장하기 전에 `file.slice(0, 12).arrayBuffer()`로 앞부분 몇 바이트만 읽어 다음 시그니처와 대조합니다.

| 허용 형식 | 매직 넘버(hex) |
|---|---|
| PNG | `89 50 4E 47` |
| JPEG | `FF D8 FF` |
| WebP | `52 49 46 46 .. .. .. .. 57 45 42 50` (`RIFF`...`WEBP`) |
| PDF | `25 50 44 46` (`%PDF`) |

이 중 하나와도 일치하지 않으면 16.6절의 "저장 실패 처리" 흐름을 그대로 재사용해(조용히 삼키지 않고 실패를 알리고 목록에 추가하지 않음) 거부합니다. 이렇게 하면 SVG뿐 아니라 확장자를 무엇으로 바꿔치기하든 — 실행 파일, HTML, 다른 미확인 형식 — 실제로 이 네 형식이 아닌 바이트는 전부 같은 경로로 걸러집니다. `accept` 속성과 `File.type` 사전 검사는 (사용자 대다수에게는) 잘못된 파일을 고르지 않도록 돕는 UX 장치로 유지하되, **최종 방어선은 매직 넘버 검사**로 둡니다.

이 권고는 discussion.md 16.2절에 반영이 필요한 스펙 변경이므로, Security가 직접 코드나 명세를 고치지 않고 이 문서에만 기록합니다. PM/Architecture가 16.2절에 매직 넘버 검사 요구사항을 추가할지 결정해 주십시오.

## 7. [취소됨] 파일 암호화와 보관 기간 (discussion.md 구 16.8~16.10절)

> **취소 사유**: 6절과 같은 이유로 파일 저장 기능 자체가 폐기되어 암호화·파일별 키·60일 보관·매직 넘버 검사 명세가 discussion.md에서 모두 삭제됨. 이 절도 삭제하지 않고 남겨 둡니다.

### 확인 결과: 이번에도 코드가 아직 명세를 따라가지 못했습니다

`src/Front/common/storage/docFiles.ts`와 `DocFileRecord` 타입(`src/Front/common/types/domain.ts`)을 확인했습니다. 지금 코드는 16.1~16.7 단계의 구현입니다 — `Blob`을 평문으로 그대로 저장하고, `name`/`mime`/`size`가 암호화 없이 레코드에 그대로 있으며, `keys` 오브젝트 스토어도 없고 AES-GCM 관련 코드(`crypto.subtle.*`)도 저장소 전체에서 검색되지 않습니다. `expiresAt`(서류 자체의 만료일, 16.3절)은 있지만 `purgeAt`(보관 기한, 16.9절)이나 60일 자동 삭제 스윕도 아직 없습니다. 그래서 아래 답변은 **명세(16.8~16.10절, 그리고 대화 중 60일·`purgeAt` 폐지로 갱신된 버전) 자체에 대한 판단**이며, 실제 구현이 올라오면 이 절의 결론을 기준으로 코드가 정확히 일치하는지 다시 확인하겠습니다.

### 7-1. 이 키 보관 방식이 막는 위협과 막지 못하는 위협

기기 분실·공유, 개발자 도구 열람, 확장 프로그램은 막고 같은 오리진 스크립트는 막지 못한다는 판단은 방향은 맞지만, 두 항목에 조건을 붙여야 정확합니다. 기준이 되는 원칙은 하나입니다 — **"이 앱과 같은 자바스크립트 실행 환경(같은 오리진의 실행 컨텍스트) 안에서 코드를 돌릴 수 있는가"**입니다. 그럴 수 있으면 `extractable: false`여도 막지 못합니다. `decrypt` 사용 권한 자체는 그대로 살아 있어서, 키 값을 꺼내지는 못해도 그 키로 복호화를 "시키는" 것은 언제든 가능하기 때문입니다.

| 위협 | 실제로 막히는가 | 이유 |
|---|---|---|
| 같은 오리진에서 실행되는 XSS | 막지 못함 (판단하신 대로) | 페이지 컨텍스트에서 `crypto.subtle.decrypt`를 그대로 호출할 수 있음 |
| **이 오리진에 대해 광범위한 권한(모든 사이트 읽기/쓰기 등)을 가진 확장 프로그램** | **막지 못함 — 원 판단과 다름** | 그런 확장의 콘텐츠 스크립트는 "격리된 world"라도 페이지와 같은 오리진의 `indexedDB`·`crypto.subtle`에 접근할 수 있습니다. 같은 DB를 열어 `keys` 스토어의 `CryptoKey`를 구조적 복제로 받아 `decrypt`를 호출하면 그대로 복호화됩니다. **막히는 것은 이 오리진에 대한 권한이 아예 없는 확장 프로그램뿐**이며, 그건 암호화 여부와 무관하게 애초에 스토리지 접근 자체가 불가능해서 막히는 것입니다 |
| **개발자 도구** | **"열람"과 "콘솔 실행"을 나눠야 함** | Application 탭에서 IndexedDB 값을 눈으로 보는 것은 암호문만 보이므로 막힙니다. 하지만 **콘솔은 페이지의 실행 컨텍스트 그 자체**라, 콘솔에 `indexedDB`를 열어 키를 꺼내고 `decrypt`를 호출하는 몇 줄만 입력하면 기기를 손에 쥔 사람이 전부 복호화할 수 있습니다. 즉 "무심코 값을 들여다보는 것"은 막지만 "직접 코드를 짤 의지가 있는 사람"은 막지 못합니다 |
| 기기 분실·공유 (원 판단대로) | **부분적으로만 막힘** | 이 방식이 실제로 막는 것은 "브라우저를 정상적으로 켜지 않고 디스크의 IndexedDB 백엔드 파일을 직접 열어 보는 경우"(포렌식 추출, 프로필 폴더를 다른 기기로 복사해 파일 뷰어로 열어보는 경우 등)입니다. **습득하거나 같이 쓰는 사람이 잠금 해제된 상태로 브라우저를 열고 Wabi 화면에 정상적으로 들어가면, 이 앱에 별도의 앱 내 잠금(비밀번호·생체인증)이 없으므로 파일이 그대로 보입니다.** "분실·공유를 막는다"는 표현은 "디스크를 직접 뒤지는 경우"로 좁혀 이해해야 하고, "습득자가 그냥 앱을 열어보는 경우"까지 막아 준다고 팀 내에서 오해하면 안 됩니다 |
| 공급망 공격(향후 추가되는 의존성이 악성이거나 취약한 경우) | 막지 못함 (추가로 짚어야 할 항목) | 새로 추가되는 npm 패키지도 결국 같은 오리진의 1st-party 코드로 실행되므로 XSS와 같은 범주입니다. 16.1·16.8절이 이미 "새 의존성 추가 금지"를 원칙으로 삼고 있는 이유가 기능 단순화뿐 아니라 이 위협도 줄여 준다는 점을 문서에 명시해 둘 가치가 있습니다 |
| 기기 자체의 브라우저 동기화(예: 크롬 동기화)로 다른 기기에 전파 | 해당 없음(안심 가능) | Chrome/Firefox 동기화는 기본적으로 IndexedDB/`localStorage`를 기기 간 동기화하지 않습니다. "기기에만 저장"이라는 약속이 이 경로로 깨지지는 않습니다 |

**결론**: 판단하신 네 가지(기기 분실·공유·개발자 도구·확장 프로그램은 막고, 같은 오리진 스크립트는 못 막음) 중 "같은 오리진 스크립트를 못 막는다"는 정확합니다. 나머지 세 가지는 전부 "능동적으로 그 오리진의 실행 컨텍스트에서 코드를 실행할 수 있는가"라는 같은 축으로 다시 나눠야 합니다 — 그 축을 넘으면(광범위한 권한의 확장, 콘솔 조작, 잠금 해제된 기기에서 앱을 정상적으로 여는 것) 암호화가 막아 주지 못합니다.

### 7-2. 평문으로 남기는 필드가 정보를 흘리는가 (갱신: `id` / `addedAt` / `byteLength` 세 가지, `purgeAt` 폐지·60일로 변경 반영)

| 필드 | 판단 |
|---|---|
| `id` | `id` 자체가 순차 증가하는 값이 아니라 무작위(예: UUID)라면 아무 정보도 새지 않습니다. 순차 값이면 "지금까지 몇 건을 추가했는지"라는 아주 약한 메타데이터만 드러나며, 이 앱의 성격상(개인용, 서버 없음) 심각하지 않습니다. 그래도 무작위 값을 쓰는 편이 더 낫다고 권고합니다 |
| `addedAt` | 각 서류를 추가한 시각의 목록이 남아, "언제 무언가를 추가했는지"의 타임라인이 드러납니다. 무엇을 추가했는지는 드러내지 않으므로 낮은 수준의 메타데이터 누출이고, 목록 정렬·보관 기한 계산에 필요한 값이라 불가피합니다. `purgeAt`을 없애고 `addedAt + 60일`로 계산하는 쪽이 오히려 더 낫습니다 — 이전에는 `purgeAt`이 `addedAt`에서 파생된 완전히 중복인 값이라 추가 정보는 없었지만, 필드 자체를 없애 저장 스키마를 줄인 것은 "필요한 최소한만 평문으로 남긴다"는 16.8절 원칙에 더 잘 맞습니다 |
| **`byteLength`** | **질문하신 대로, 파일 종류를 완전히는 아니지만 어느 정도 추정하게 만드는 신호입니다.** 암호화는 내용을 감추지만 **길이를 감추지는 않습니다** — AES-GCM 암호문 길이는 평문 길이에 16바이트 인증 태그를 더한 값과 거의 같아서, `byteLength`를 알면 원본 파일 크기를 사실상 그대로 아는 것과 같습니다. 이걸로 무엇을 알 수 있는가: (1) 개인이 찍은 사진처럼 크기 편차가 큰 파일은 크기만으로 정확한 종류를 알기 어렵지만 "수 KB면 문서, 수 MB면 사진일 가능성이 높다" 정도의 거친 추정은 가능합니다. (2) 이 앱의 실제 쓰임새(정부기관 공식 PDF 서식처럼 다수 이용자가 동일한 템플릿을 내려받아 채우는 문서)를 고려하면, 특정 공식 서식 파일들은 크기가 좁은 대역에 몰릴 수 있어 "이 크기대라면 십중팔구 어떤 특정 서류다"라는 더 구체적인 추정이 이론적으로 가능합니다. 다만 이 신호를 실제로 쓰려면 공격자가 **암호화 키 없이 평문 메타데이터만 볼 수 있는 위치**(=7-1절의 "디스크를 직접 뒤지는" 위협 등급)에 있어야 하는데, 그 등급의 공격자는 애초에 이름·MIME도 못 보므로 상대적으로 낮은 등급의 부가 정보입니다. **결론: 완전히 무해하지는 않은 낮은 심각도의 부가 신호이며, 지금 설계 그대로 진행해도 괜찮습니다.** 더 낮추고 싶다면 저장 전 크기를 64KB 단위 등으로 올림(padding)해 정확한 크기를 감추는 방법이 있지만, 이 앱의 위협 모델(서버 없음, 개인용) 대비 과한 엔지니어링일 수 있어 필수로 권고하지는 않습니다 |

### 7-3. IV 관리와 암호문 저장 형태에서 흔한 실수

1. **IV 재사용 — 특히 "묶어서 한 번에 암호화"가 깨지는 경우.** 16.8절이 이름·MIME·내용을 하나의 페이로드로 묶어 한 번에 암호화하기로 한 것은 정확히 이 실수를 피하는 설계입니다. 나중에 코드가 편의상 이름/‌MIME/내용을 각각 별도의 `encrypt()` 호출로 나누면서 같은 `iv` 변수를 그대로 재사용하면 그 순간 AES-GCM의 안전성이 깨집니다 — **하나의 레코드에는 반드시 하나의 `encrypt()` 호출, 하나의 새 IV**라는 규칙을 코드 리뷰 체크리스트에 넣어 두는 것을 권장합니다.
2. **IV와 암호문의 쓰기 원자성.** IV를 암호문과 별도 필드/별도 스토어에 두고 각각 다른 시점에 쓰면, 저장 도중 오류(용량 초과 등, 16.6절)가 나서 한쪽만 쓰이는 상태가 생길 수 있습니다. IV와 암호문(그리고 인증 태그 — WebCrypto의 `encrypt()`가 반환하는 `ArrayBuffer`에 이미 포함되어 있어 따로 다룰 필요가 없습니다)은 **같은 레코드, 같은 `put()` 트랜잭션 안에** 두어 부분 반영이 애초에 불가능하게 합니다.
3. **여러 필드를 하나로 묶을 때의 프레이밍(구분자) 버그.** 이름·MIME·내용을 문자열 결합(`name + 구분자 + mime + 구분자 + content`)으로 이어 붙이면, 이름이나 MIME 값에 우연히 구분자와 같은 바이트가 들어 있을 때 복호화 후 파싱이 틀어질 수 있습니다. 보안 취약점은 아니지만 흔한 구현 버그이므로, 길이-접두(length-prefixed) 방식(`[이름 길이 2바이트][이름][MIME 길이 2바이트][MIME][파일 내용]`)처럼 파싱이 모호하지 않은 프레이밍을 권장합니다.
4. **복호화 실패를 조용히 삼키지 않기.** GCM은 태그 검증에 실패하면 `decrypt()`가 예외를 던집니다(변조·손상 감지). 16.6절의 "실패를 조용히 삼키지 않는다" 원칙을 복호화 실패에도 그대로 적용해, 특정 파일의 복호화가 실패하면 그 파일에 한해 이용자에게 실패를 알리고 목록 전체가 조용히 비거나 죽지 않게 합니다.
5. **base64 왕복 금지.** 16.1절이 `Blob`을 base64로 부풀리지 않기로 한 것과 같은 이유로, IV와 암호문도 base64 문자열로 바꿨다가 되돌리는 과정을 넣지 않습니다. `ArrayBuffer`/`Uint8Array`로 그대로 저장·비교하면 인코딩 왕복에서 흔히 나오는 패딩·인코딩 실수를 원천적으로 피할 수 있습니다.
6. **평문 로그 금지.** 개발 중 디버깅용으로 복호화된 이름·내용이나 키·IV를 `console.log`로 남기는 습관적인 실수를 피합니다. 배포 코드에 이런 로그가 하나라도 남으면 암호화 설계 전체의 의미가 없어집니다.
7. (참고, 조치 불필요) 키 하나로 암호화할 수 있는 횟수 상한(96비트 무작위 IV 기준 약 2^32회)은 개인용 문서 저장 앱이 실제로 쌓을 파일 수(많아야 수백 건)에 비해 도달할 일이 없는 한도이므로 신경 쓰지 않아도 됩니다.

### 7-4. 자동 삭제가 실제로 데이터를 지우는가

**정직하게 답하면, "레코드 삭제"와 "디스크에서 완전히 사라짐"은 다른 이야기입니다.** `IDBObjectStore.delete()`는 논리적 삭제입니다. 실제 저장 엔진(Chrome 계열은 LevelDB 기반)은 지워진 레코드가 차지하던 공간을 즉시 덮어쓰지 않고 나중에 내부 압축(compaction) 시점에 회수하며, 그 아래의 SSD/플래시 저장장치 역시 "삭제"를 마모 평준화·TRIM으로 나중에 비동기 처리합니다. 즉 **60일이 지나 앱이 목록에서 지운 뒤에도, 그 파일의 원래 바이트가 디스크 여유 공간에 한동안 남아 있을 수 있습니다.** 이건 Wabi만의 문제가 아니라 `localStorage`·일반 파일시스템·대부분의 앱이 공통으로 갖는 한계입니다.

**다만 암호화가 이 문제를 상당히 완화합니다.** 남아 있는 바이트는 평문이 아니라 암호문이라, 그 바이트를 포렌식으로 복구해도 대응하는 키가 없으면 무의미합니다. 그래서 진짜 질문은 "삭제된 파일의 암호문을 나중에 복구할 수 있는 키가 여전히 살아 있는가"입니다. 여기서 **16.8절 명세를 명확히 해야 할 지점이 있습니다** — 키를 파일마다 하나씩 두는지, 앱 전체가 공유하는 키 하나를 두는지가 명시되어 있지 않습니다("같은 DB의 별도 스토어 `keys`에 둡니다"만 있고 "파일마다"라는 말은 IV에만 붙어 있습니다).

- **키를 앱 전체가 공유하면**: 파일을 지워도 그 파일을 복호화할 수 있었던 키는 다른 파일들을 위해 계속 살아 있습니다. 디스크에 남은 옛 암호문 조각이 나중에 포렌식으로 복구되면, 그 시점에도 살아 있는 공유 키로 여전히 복호화될 수 있습니다 — **"60일 뒤 삭제"가 암호학적으로는 완전한 삭제를 보장하지 못합니다.**
- **키를 파일마다 하나씩(레코드의 `id`로 키를 매핑) 두면**: 60일 자동 삭제 시점에 그 파일의 레코드와 **그 파일 전용 키를 함께** 지우는 것으로 "암호학적 파쇄(crypto-shredding)"가 됩니다. 디스크에 암호문 조각이 남아 있어도, 그걸 풀 수 있는 유일한 키가 이미 함께 삭제되어(그리고 그 키도 결국 같은 디스크 잔존 문제를 겪지만, `extractable:false`로 저장된 키는 브라우저가 내부적으로 프로필/운영체제 수준의 보호로 감싸 두는 경우가 일반적이라 원시 키 바이트로 바로 복구되지 않습니다) 사실상 복구 불가능해집니다.

**권고**: 파일마다 별도의 키를 쓰는 방식으로 16.8절을 명확히 하고, 60일 자동 삭제 스윕(16.9절)이 파일 레코드와 그 파일의 키를 **같은 트랜잭션에서 함께** 지우도록 구현합니다. 이렇게 해야 "60일이 지나면 삭제된다"는 약속이 논리적 삭제 수준이 아니라 암호학적으로 뒷받침됩니다. 이 결정은 Security가 직접 코드나 명세를 고치지 않고 이 문서에 권고로만 남기며, 반영 여부는 PM/Architecture가 정합니다.

**이용자에게는 어떻게 설명해야 하는가**: 16.10절 카피("영구 보관용이 아닙니다... 브라우저 저장공간을 지우면 함께 사라집니다")는 이미 적절히 절제되어 있습니다. 여기서 더 나아가 "완전히 삭제됩니다", "복구할 수 없이 지워집니다"처럼 포렌식 수준의 삭제까지 보장하는 듯한 표현은 **추가하지 않는 것을 권고합니다** — 위에서 설명한 대로 디스크 잔존 가능성 자체는 어떤 저장 방식으로도 100% 배제할 수 없기 때문입니다. "앱에서 더 이상 보이지 않고 열람할 수 없게 됩니다" 수준의 정직한 표현이면 충분하고, 이는 일반적인 소비자 앱(사진 앱, 메모 앱 등)의 삭제 안내 수준과 같아 이 앱만 유별나게 더 강한 약속을 할 필요는 없습니다.

### 7-5. (재확인) SVG를 `accept`에서 빼는 것만으로 충분한가

이전 판단이 그대로 유지되며, 암호화가 추가되어도 결론은 바뀌지 않습니다. **암호화는 내용 검증을 대신하지 않습니다** — 확장자만 바꾼 SVG를 그대로 암호화해서 저장하면, 나중에 복호화해 `<img>`로 미리보기할 때 원래 있던 위험(내용이 실제로는 SVG라 내부 `<script>`가 실행될 가능성)이 그대로 재현됩니다. 즉 매직 넘버 검사(PNG/JPEG/WebP/PDF 시그니처 대조)는 **암호화하기 이전, 파일을 고른 직후**에 반드시 이뤄져야 하고, "이미 암호화해서 안전하게 넣었으니 검증은 생략해도 된다"는 판단으로 이어지면 안 됩니다. 구체적인 시그니처 값과 구현 방식은 이전 절(6절)에 이미 적어 두었습니다.

## 8. 메모 기능 (discussion.md 16절, 파일 저장 대체)

### 확인 결과

아직 구현 전입니다(`Memo` 관련 컴포넌트·저장 유틸 없음). 명세 기준으로 판단합니다. 레코드는 `{ id, body, updatedAt }`이고 `localStorage`에 테마·출국일·직접 추가한 할 일과 같은 자리에 저장하며, 암호화는 넣지 않기로 했습니다.

### 암호화를 넣지 않은 판단은 타당한가 — 타당합니다

몇 가지 이유가 겹칩니다.

- **이 데이터는 새로운 위험 범주가 아닙니다.** 메모 본문은 자유 텍스트라는 점에서, 이미 2절에서 다룬 할 일 제목·본문과 성격이 같습니다 — "이용자가 스스로 적는 민감할 수 있는 텍스트를 서버로 보내지 않고 기기에만 두는" 기존 원칙을 그대로 적용하면 됩니다. 새 예외를 만들 필요가 없습니다.
- **암호화가 막아 줬을 위협이 애초에 좁습니다.** 7-1절에서 이미 정리했듯, 이런 방식의 암호화는 "브라우저를 정상적으로 켜지 않고 디스크를 직접 뒤지는 경우"만 막고, 같은 오리진 스크립트·광범위한 권한의 확장 프로그램·개발자 도구 콘솔·**잠금 해제된 기기를 그대로 열어 보는 경우**는 막지 못합니다. 이 앱에는 앱 차원의 로그인·잠금이 없으므로, 메모 화면에서 가장 현실적인 노출 경로는 정확히 "습득하거나 같이 쓰는 사람이 기기를 열어 메모 탭을 누르는 것"이고, 이건 암호화를 넣어도 그대로 노출됩니다. 즉 암호화의 실제 방어 범위와 이 화면의 실제 위험이 거의 겹치지 않습니다.
- **오히려 암호화가 잘못된 안도감을 줄 수 있습니다.** "암호화되어 있다"는 문구가 붙으면 이용자가 "그럼 계좌번호를 적어도 되겠다"고 판단할 위험이 있는데, 방금 말한 대로 잠금 해제된 기기를 통한 열람은 여전히 막지 못하므로 이건 실제보다 과장된 안전감입니다. 안 하느니만 못한 경우입니다.
- 파일 저장이 취소된 이유(암호화·키 관리·보관 정책이 앱 크기 대비 과도)와 메모에 암호화를 안 넣는 이유는 사실 다른 이유입니다 — 파일 쪽은 "구현 비용 대비 효용이 낮아서"였고, 메모 쪽은 "이 앱 구조(로그인 없음)에서는 암호화 자체의 방어 범위가 애초에 좁아서"입니다. 결과는 같지만 근거는 구분해 두는 것이 나중에 "그럼 로그인 기능이 생기면 다시 검토해야 하는가"를 판단할 때 도움이 됩니다 — **답은 예입니다.** 앱 차원의 잠금(비밀번호·생체인증)이 나중에 추가되면 암호화가 막아 주는 범위와 이 화면의 실제 위험이 겹치게 되므로, 그 시점에는 암호화 도입을 다시 검토할 가치가 있습니다.

### 화면 문구 안내가 필요한가 — 필요합니다

계좌번호·여권번호 같은 것을 적을 가능성은 실제로 높습니다. 메모 화면은 "기억해 둘 것을 적어 두세요"라고 자유 작성을 권하는 화면이라, 구조화된 필드가 없는 할 일 제목보다 오히려 더 길고 사적인 내용을 유도합니다. 다만 두 가지를 구분해야 합니다.

- **16.4절이 이미 "강한 경고를 두지 않는다"고 정한 것은 데이터 영속성(브라우저 저장공간을 지우면 사라진다는 것)에 대한 이야기입니다.** 지금 권고하는 것은 그것과 다른 종류입니다 — **무엇을 적을지에 대한 가벼운 안내**이지, 저장 방식에 대한 경고가 아닙니다. 그래서 16.4절의 기존 결정과 충돌하지 않습니다.
- 문구는 `alert` 색이나 경고 아이콘 없이, 다른 안내 한 줄과 같은 `caption`/`muted` 스타일로 얹는 것을 권장합니다(2절 카피 규칙대로 존댓말·한 문장·감탄사 없이). 예: `계좌번호나 여권번호 같은 정보는 적지 않는 것을 권합니다.` 이 문구는 추가·편집 시트(16.3절)에 두어 실제로 타이핑하기 직전에 보이게 합니다.
- 이 문구는 강제가 아니라 안내이므로 입력을 막거나 검사하지 않습니다(개인정보를 감지해 자동으로 막으려는 시도는 오탐이 많고 이 앱 규모에 과도한 엔지니어링입니다).
