# Wabi 구현 계획서

## 0. 출처와 범위

- **원본**: `Docs/Design/WabiDesignSystem.dc.html` (Claude Design 프로젝트 `cc00ea2b-15f8-4984-a1f1-3739f99ec91b`에서 내려받은 사본)
- **디자인 명세**(색상·타이포·간격·컴포넌트·화면 구성·모션)는 원본 캔버스가 확정된 사실이므로 그대로 따릅니다. 임의로 바꾸지 않습니다.
- **제품 콘텐츠**(비자·세금·보험·계약 등 현실 정보)는 캔버스에 적혀 있더라도 확정된 사실이 아니라 화면을 채우기 위한 예시입니다. 직접 조사해 확인한 값으로 교체한 뒤에만 코드에 넣습니다. 조사는 Research-team에 의뢰했습니다.
- 원본은 디자인 시스템(01~04 섹션)과 **동작하는 프로토타입**(05 섹션)을 함께 담고 있습니다. 두 가지를 모두 구현합니다.

## 1. 제품 정의

워킹홀리데이를 준비하는 사람과 현지에 도착한 사람을 위한 모바일 우선 앱입니다. 할 일은 많지만 한 번에 알아야 할 것은 언제나 하나뿐이라는 전제로 설계되었습니다.

- 대상: 출국 전 준비 단계, 현지 정착 단계
- 첫 화면은 D-day
- 다국가 지원 (호주 / 캐나다 / 일본)
- 존댓말, 간결한 카피

## 2. 설계 원칙 (구현 시 반드시 지킬 것)

1. **한 화면에 블록 3~4개**. 그 이상 필요하면 다음 화면으로 넘깁니다. 목록은 3줄까지 보여주고 나머지는 '전체 보기'로 감춥니다.
2. **시선 순서를 고정합니다**. 위에서 아래로 상태 → 다음 행동 → 목록 → 탭바. 화면이 바뀌어도 이 순서는 바뀌지 않습니다.
3. **색이 아니라 크기로 강조합니다**. 팔레트는 무채색 하나뿐이고, 중요도는 타이포 크기·여백·잉크 대비로만 표현합니다. 유채색은 마감 임박 한 곳에만 쓰는 `alert` 하나로 제한합니다.

## 6. 데이터

데이터는 화면 코드와 분리해 `src/Front/common/data`(또는 Architecture가 정한 위치)에 둡니다.

### 6.1 구조 (캔버스에서 확정)

| 상수 | 구조 |
|---|---|
| `COUNTRIES` | 국가 코드별 `label / depart / visa` |
| `TASKS` | `id / phase(pre·post) / title / meta / week / urgent / tag / body / items / done` |
| `GUIDE` | 상황(`pre`·`post`)별 문항 배열, 각 문항은 `title / body / points` |
| `PAIN` | `num / when / title / body / points` |

분량 기준: `TASKS` 9건(pre 4 · post 5), `GUIDE` 상황별 5문항, `PAIN` 6건.

### 6.2 값 (조사 후 확정)

캔버스에 들어 있는 값 — 비자 심사 3주, 세금 번호가 없을 때 최고 세율, 계좌 개설 도착 후 3일 내, 보험 증서 요구 여부, 국가별 출국일과 비자 만료일 등 — 은 **확인되지 않은 예시**입니다. 다음 순서로 처리합니다.

1. Research-team에 국가별(호주·캐나다·일본) 실무 정보를 공식 출처 기준으로 의뢰합니다. 산출물은 `/home/fefdfea/FF/Organize/Research-team/Research-team/Result/Data/` 아래 JSON입니다.
2. 조사 결과가 도착하면 그 값으로 `TASKS` · `GUIDE` · `PAIN`을 다시 씁니다. 각 항목에는 출처 URL을 함께 보관합니다.
3. 조사로 확인되지 않은 항목은 임의로 채우지 않고 화면에서 뺍니다.
4. Front-end는 조사 결과가 오기 전까지 데이터 구조와 화면만 구현하고, 값은 조사 산출물로 주입받는 형태로 설계합니다.

`COUNTRIES`는 국가별로 다른 실제 요건을 담게 되므로, 세 국가가 같은 할 일 목록을 공유하던 캔버스 구조를 국가별 할 일 목록으로 확장해야 합니다.

## 7. 동작 명세

- 탭 이동 시 열려 있던 상세는 닫습니다.
- 체크 토글은 행 전체가 아니라 체크 원에서만 발생하며, 행 클릭은 상세를 엽니다 (이벤트 전파 차단).
- 완료 항목: 제목 `muted` + 취소선, 메타는 '완료'로 바뀝니다.
- 긴급 항목(`urgent`이고 미완료): 체크 테두리와 메타 글자가 `alert`.
- NEXT 카드는 미완료 항목 중 첫 번째를 보여주고, 설명은 본문의 첫 문장만 씁니다.
- 진행률은 기본 할 일 + 직접 추가한 할 일을 합쳐 계산합니다.
- 직접 추가한 할 일은 마감이 '오늘까지' 또는 '이번 주'이면 홈의 '이번 주 할 일'에 함께 나옵니다.
- 테마와 국가는 '나' 탭 설정에서 바꿀 수 있습니다.

## 8. 카피 규칙

1. 존댓말, 한 문장. 감탄사와 느낌표는 쓰지 않습니다.
2. 행동 버튼은 동사로 끝냅니다. "지금 하기", "가입하기", "예약하기".
3. 마감은 상대 표현으로. "오늘까지", "도착 후 3일 내".
4. 숫자는 단위와 붙여 씁니다. "8 / 14", "D-12".

## 10. 출국일 입력 (사용자 승인 2026-08-28)

D-day와 비자 만료일은 조사로 확인할 수 있는 사실이 아니라 이용자마다 다른 개인 값입니다. 캔버스가 `COUNTRIES`에 하드코딩해 둔 출국일과 비자 만료일은 쓰지 않고, 다음과 같이 입력받아 산출합니다.

### 10.1 입력 위치

'나' 화면의 설정 목록에 **출국일** 항목을 추가합니다. 기존 3개(화면 모드 · 알림 · 국가 변경)와 같은 60px 행 형식을 따르고, 값이 없으면 우측에 '입력하기'를, 있으면 선택한 날짜를 보여줍니다.

날짜 선택은 브라우저 기본 `input[type=date]`를 씁니다. 외부 의존성이 없고 모바일에서 OS 기본 날짜 선택기가 뜨며 키보드 접근성이 확보됩니다.

### 10.2 산출 규칙

- **D-day** = 출국일 − 오늘. 출국 당일은 `D-DAY`, 지난 뒤에는 `D+n`으로 표시합니다.
- **비자 만료일** = 출국일 + 국가별 체류 허용 기간(조사로 확인된 값). 해당 국가의 체류 허용 기간이 조사로 확인되지 않았다면 비자 만료일 줄을 표시하지 않습니다.
- **출국일이 입력되지 않았으면 홈의 D-day 자리에 `D-0`을 기본으로 보여줍니다** (사용자 지시 2026-08-28). 이전에는 "'나' 화면에서 출국일을 입력하면 D-day가 표시됩니다"라는 빈 상태 문구를 두었으나, 첫 화면이 비어 보이지 않도록 기본값을 표시하는 쪽으로 바꿉니다.
  - `D-0`은 **출국일이 없는 상태**의 표시이고, 출국일을 입력한 뒤 출국 당일이 되면 `D-DAY`가 나옵니다. 두 표기가 다르므로 섞지 마세요.
- 반면 '나' 화면의 출국일·비자 만료일 줄은 **그대로 빈 상태로 둡니다.** 여기는 실제 값을 보여주는 자리라 임의의 기본값을 넣으면 거짓이 됩니다. D-day 자리만 예외입니다.

### 10.3 구현 시 주의

- **오늘 날짜는 반드시 클라이언트에서 계산합니다.** 이 라우트는 정적 프리렌더 대상이므로 서버 렌더 시점에 `new Date()`를 쓰면 빌드 시점 날짜로 고정되고, 하이드레이션 불일치도 발생합니다.
- 출국일은 `localStorage`에 저장합니다. 저장 범위 경계는 Security 검토서 2절을 따릅니다.

| `744 ~ 1179px` 태블릿 | 아이콘 레일 + 본문 620px 중앙 |
| `≥ 1180px` 데스크톱 | 사이드바 + 본문 + 우측 요약. **레이아웃 최대 폭 1440** |

**최대 폭은 1440입니다** (사용자 지시 2026-08-28. 처음 1280으로 정했다가 넓혔습니다). 1180 이상에서 데스크톱 레이아웃으로 전환하되, 앱 전체 폭은 **1440에서 멈추고 그보다 넓은 창에서는 가운데 정렬**합니다.

폭이 늘어나도 **좌우 패널과 본문 콘텐츠는 고정입니다.**

| 요소 | 폭 |
|---|---|
| 좌측 사이드바 | 236 고정 |
| 우측 요약 패널 | 336 고정 |
| 본문 **콘텐츠** | 620 상한 유지 |
| 본문 **컨테이너** | 남는 폭을 가져가고, 그 안에서 콘텐츠 620을 가운데 정렬 |

1440에서는 본문 컨테이너가 868이 되는데, 콘텐츠까지 868로 늘리면 확장 규칙 "본문 폭은 620px에서 멈춥니다"를 어깁니다. **남는 폭은 여백으로 둡니다.** 이 구분은 QA가 이미 한 번 오판할 뻔한 지점이라(TPC-26) 컨테이너와 콘텐츠를 나눠 재야 합니다.

### 11.2 확장 규칙 (캔버스 원문)

- **본문 폭은 620px에서 멈춥니다.** 넓어진 화면에서 글줄이 길어지지 않게 합니다.
  - 데스크톱에서 이 값을 확인할 때는 **컨테이너가 아니라 그 안의 실제 콘텐츠를 재야 합니다.** 홈·메모의 본문 컨테이너는 `flex: 1`이라 708px이고, 좌우 패딩 44px씩을 뺀 콘텐츠가 620px입니다. 컨테이너를 재면 620 초과로 오판합니다.
- **정보를 추가하지 않습니다.** 데스크톱 우측 요약은 다른 화면에 이미 있는 내용을 옮겨 놓은 것뿐입니다.
- **타이포만 한 단계 키웁니다.** D-day 60 → 88, 제목 24 → 30, 본문 15는 그대로 둡니다.
  - 두 값의 **적용 구간이 다릅니다**(QA가 캔버스 목업 대조로 확인). D-day는 모바일 60 · 태블릿 72 · 데스크톱 88로 **3단계**이고, 제목은 모바일 24 · **태블릿부터 30**으로 2단계입니다. 제목을 데스크톱에서만 키우면 태블릿이 캔버스와 어긋납니다.
- **터치와 커서를 함께 지원합니다.** 태블릿의 탭 대상은 모바일과 같은 최소 48px를 유지하고, hover 상태는 데스크톱에서만 씁니다.

> 한 줄 요약(캔버스): 모바일은 순서로, 데스크톱은 배치로 같은 우선순위를 만듭니다. 화면이 커져도 사용자가 먼저 보는 것은 언제나 D-day와 NEXT 하나입니다.

화면마다 다릅니다. **새 정보를 만들지 않고 다른 화면의 내용을 옮겨 놓습니다.**

| 할 일 | 캔버스에 데스크톱 목업이 없습니다. 아래 11.6절 참고 |

### 11.6 캔버스에 목업이 없는 화면

데스크톱 `할 일`은 캔버스에 목업이 없습니다. **임의로 만들지 말고** 다음 원칙으로만 처리합니다.

## 13. 출처 표시 (사용자 지시 2026-08-28)

데이터의 `sourceUrl`을 화면에 노출합니다. 비자·세금·보험처럼 틀리면 이용자가 실제로 손해를 보는 정보이므로, 이용자가 원문을 직접 확인할 수 있어야 합니다.

### 13.1 노출 위치

정보 예산을 지키기 위해 **목록에는 넣지 않고 상세에서만** 보여줍니다.

| 위치 | 표시 지점 |
|---|---|
| 할 일 상세 화면 | 준비물 목록 아래 |
| 가이드 답변 | 대처법 목록 아래 |
| 어려움 답변 | 대처법 목록 아래 |
| '나' 화면 국가 정보 카드 | 비자 만료일 줄 아래 |

홈·할 일·문서 화면의 목록 행에는 넣지 않습니다. "한 화면에 블록 3~4개" 원칙과 64px 행 높이가 무너집니다.

### 13.2 형식

- caption 규격을 따릅니다. JetBrains Mono 11px, 색은 `muted`.
- 링크 문구는 `출처`만 쓰지 않고 **도메인을 함께 보여줍니다**. 화면에서도 어디서 온 정보인지 알 수 있고, 스크린리더로 링크만 훑을 때도 구분됩니다. 예: `출처 immi.homeaffairs.gov.au`
- 외부로 나가는 링크이므로 `target="_blank"`와 `rel="noopener noreferrer"`를 함께 붙입니다.
- 새 탭으로 열린다는 사실을 스크린리더에 알리기 위해 `aria-label`에 이를 포함합니다.
- 새 색상 토큰을 만들지 않습니다. `muted`를 그대로 쓰고 호버 시 `text`로 올립니다.

### 13.3 값이 없을 때

`sourceUrl`은 선택 필드입니다. 값이 없으면 **줄 자체를 렌더하지 않습니다.** 빈 링크나 '출처 없음' 같은 문구를 넣지 않습니다. 현재 `jp-move-in` 한 건이 여기에 해당합니다. 사실은 조사로 확인됐지만 원문 URL이 기록되지 않은 경우입니다.

## 14. 이용자 파일 저장 (폐기 — 16절로 대체)

> **폐기됨 (2026-08-28)** — 파일 저장 기능 자체를 만들지 않기로 했습니다. 사유와 대체안은 16절을 보십시오.
> 아래 원칙은 나중에 파일 저장을 다시 논의할 때를 위해 남겨 둡니다.

이용자가 추가한 파일을 저장하게 된다면 **IndexedDB에 `Blob`으로** 저장하고 `localStorage`에는 넣지 않습니다. `localStorage`는 문자열만 담을 수 있어 base64로 부풀려야 하고 용량 한도가 5MB 안팎이며 동기 API라 큰 값을 다루는 동안 화면이 멈춥니다.

`localStorage`는 테마·국가·출국일·메모처럼 짧은 값에만 씁니다. 현재 저장 중인 값이 전부 여기에 해당합니다.

## 16. 문서 탭을 메모 탭으로 (사용자 지시 2026-08-28)

**이용자 파일 저장 기능은 만들지 않습니다.** 앞서 이 절에 있던 IndexedDB 저장·AES-GCM 암호화·파일별 키·60일 보관·매직 넘버 검사 명세는 전부 폐기합니다.

### 16.1 폐기 이유

파일 저장은 이 앱의 크기에 비해 딸려 오는 것이 너무 많았습니다. 암호화, 키 파쇄, 보관 기간 약속과 실제 삭제, 위장 파일 검사, 미리보기 샌드박스까지 붙었고 그중 어느 하나만 빠져도 이용자에게 한 약속이 깨지는 구조였습니다.

이용자 로컬 파일 경로를 참조하는 방식(File System Access API의 `showOpenFilePicker`)도 검토했으나 **Safari가 데스크톱·iOS 모두 미지원, Firefox 미지원, 표준 상태도 experimental**입니다(MDN browser-compat-data 직접 확인). 모바일 우선인 이 앱에서 iOS 이용자가 기능을 아예 못 쓰게 되므로 채택할 수 없습니다.

서류 정보 자체는 이미 할 일 상세의 "준비물"이 전달하고 있어 정보 전달 목적에는 구멍이 없습니다.

### 16.2 대신 넣는 것: 메모

문서 탭 자리에 **이용자가 직접 적는 메모**를 둡니다. 남이 만든 파일을 보관하는 것이 아니라 이용자가 스스로 적어 두는 것이라, 앞의 무거운 장치들이 필요 없습니다.

- 탭 라벨을 `문서`에서 `메모`로 바꿉니다. `TabBar`의 아이콘과 위치, 4탭 구성은 그대로입니다.
- 메모 한 편은 **제목과 본문**입니다. 캔버스 데스크톱 메모 목업이 제목 입력과 내용 입력을 나눠 두고 있고, 목록도 제목 + 부제(내용 요약) + 날짜로 그립니다. (이전 명세는 본문 하나였으나 캔버스 확인 후 정정)
- 저장은 `localStorage`입니다. 테마·출국일·직접 추가한 할 일과 같은 자리에 둡니다. 짧은 텍스트라 IndexedDB가 필요 없습니다.
- 레코드: `{ id, title, body, updatedAt }`.

### 16.3 화면

- **목록**: 제목 + 내용 한 줄 요약 + 날짜입니다. 최근 수정 순으로 정렬합니다.
- **추가·편집**: `BottomSheet` 안에서 합니다. 여러 줄을 입력해야 하므로 **`TextArea` 컴포넌트를 `common/component`에 새로 만듭니다.** `TextField`의 규격(radius 14, `sunken` 배경, 1.5px `line` 테두리, 15px)을 그대로 따르되 높이만 늘리고 세로 리사이즈를 막습니다.
- **삭제**: 목록 행에서 삭제할 수 있게 하고 확인을 한 번 받습니다.
- **빈 상태**: `아직 적어 둔 메모가 없습니다.`

### 16.4 카피

파일 저장 시절의 문구는 전부 걷어냅니다. "기기에만 저장", "60일 후 자동 삭제", "만료일 알림" 같은 표현이 남아 있으면 안 됩니다.

- 화면 안내 한 줄: `기억해 둘 것을 적어 두세요. 이 기기에만 저장됩니다.`
- **추가·편집 시트 안내 한 줄** (`SecurityReview.md` 9절 권고): `계좌번호나 여권번호처럼 민감한 정보는 적지 않기를 권합니다.`

메모는 평문으로 저장합니다. 로그인도 앱 잠금도 없는 구조에서는 암호화를 넣어도 실질적인 보호가 되지 않기 때문입니다(파일 저장에서 확인한 것과 같은 이유). 이용자가 무엇을 적을지 통제할 수 없으므로 막는 대신 알려주는 쪽을 택합니다. 앱 잠금 기능이 생기면 그때 재검토합니다.

`localStorage`도 브라우저 저장공간을 지우면 사라지므로 영구 보존을 암시하지 않습니다. 다만 이용자가 직접 적은 짧은 글이라 파일 때처럼 강한 경고는 두지 않습니다.

## 17. `SourceLink` 스킴 검사 (`SecurityReview.md` 9절)

`SourceLink`가 URL 스킴을 검사하지 않아 `https` 전용 규칙이 데이터 규율에만 의존하고 있습니다. 조사 결과에 `http` URL이 섞이면 그대로 렌더됩니다.

`new URL(url).protocol`이 `"https:"`가 아니면 **아무것도 렌더하지 않습니다.** 파싱 실패 시 `null`을 반환하는 기존 처리와 같은 방식입니다. 데이터에 잘못된 값이 들어와도 화면이 막아 주게 합니다.

## 18. 사용자 지적 수정 (2026-08-28)

### 18.1 홈 헤더의 국가 표시가 눌리지 않음

현재 `HomeScreen`의 국가 표시는 `<span className={styles.countryBadge}>{countryLabel} ▾</span>`입니다. **`▾`를 달아 눌릴 것처럼 보이는데 `button`이 아니고 핸들러도 없습니다.** 가짜 클릭 어포던스입니다.

`Chip` 컴포넌트가 `onClick`이 없으면 `button`이 아니라 `span`으로 렌더해 이 문제를 피하도록 설계돼 있는데, 헤더 배지는 그 원칙을 따르지 않았습니다.

**고치는 방향**: 실제로 국가를 바꿀 수 있게 만듭니다.

- `button`으로 바꾸고 누르면 국가 선택 시트를 엽니다.
- 시트는 `BottomSheet` 안에 `Chip`을 국가 수만큼 놓습니다. 선택된 국가만 `selected`입니다.
- 고르면 국가가 바뀌고 시트가 닫힙니다. '나' 화면의 국가 변경과 같은 상태를 씁니다.
- 국가를 바꾸면 열려 있던 상세는 닫습니다(7절 탭 이동 규칙과 같은 이유 — 이전 국가의 할 일이 유효하지 않습니다).

### 18.2 완료 취소 후 상세가 닫히지 않음

`undoDetail`이 완료만 취소하고 상세를 열어 둡니다. `completeDetail`은 처리 후 상세를 닫습니다. 두 버튼이 같은 자리에 있는데 한쪽만 화면을 벗어나 동작이 어긋납니다.

**고치는 방향**: `undoDetail`도 `completeDetail`처럼 상세를 닫고 이전 화면으로 돌아갑니다. 두 동작 모두 "이 항목에 대한 처리를 끝냈다"는 뜻이므로 결과가 같아야 합니다.

## 19. 사용자 지적 수정 2차 (2026-08-28)

### 19.1 우측 요약 패널이 전체 높이를 채우지 않음

데스크톱 1280×900에서 `aside`의 실측 높이가 556px입니다. 좌측 사이드바는 `100dvh`로 화면을 채우는데 우측만 내용 높이에 맞춰 잘립니다. 캔버스 목업은 좌우 패널이 같은 높이로 화면을 채웁니다.

우측 패널도 화면 높이를 채우고, 내용이 넘치면 패널 안에서 스크롤합니다. 하단에 `margin-top: auto`로 붙는 요소(홈의 어려움 카드)가 실제로 바닥에 붙으려면 이 높이가 전제입니다.

### 19.2 `+ 새 메모`가 등록과 모달을 동시에 실행

지금은 누르면 메모가 등록되면서 동시에 다른 모달이 뜹니다. **누르면 바로 등록만 되게 합니다.** 모달을 띄우지 않습니다.

우측 패널에는 이미 바로 적는 입력창이 있으므로, 거기 적고 `+ 새 메모`를 누르면 그 내용이 등록되고 입력창이 비워지는 흐름이면 충분합니다.

### 19.3 할 일 마감을 캘린더로 직접 고르기

지금은 `오늘까지 · 이번 주 · 이번 달 · 도착 후` 네 개의 고정 선택지뿐입니다. 이용자가 원하는 날짜를 직접 고를 수 있어야 합니다.

- 할 일 추가 시트의 마감 입력을 **날짜 선택**으로 바꿉니다. `TextField`의 `type="date"`를 그대로 씁니다(출국일 입력과 같은 방식, 10.1절).
- 기존 고정 선택지는 빠른 입력으로 남겨도 되지만, 날짜를 직접 고르는 경로가 반드시 있어야 합니다.
- 목록의 마감 표시는 카피 규칙(4절)대로 상대 표현을 유지합니다. 고른 날짜를 `오늘까지`·`3일 남음` 같은 형태로 환산해 보여줍니다.
- **오늘 날짜에 의존하므로 P-06과 같은 함정이 있습니다.** 환산은 반드시 클라이언트 effect 안에서 하고, `wabiLogic.ts`의 순수 함수로 빼 TZ 회귀 테스트를 붙입니다.

### 19.4 우측 패널에서 메모 삭제

우측 요약 패널의 메모 목록에서 바로 지울 수 있어야 합니다.

- 행에 마우스를 올리면 **휴지통 아이콘이 나타납니다.** 평소에는 보이지 않습니다.
- hover는 데스크톱 전용입니다(11.2절 확장 규칙). 터치 환경에서는 이 패널 자체가 없으므로 문제되지 않습니다.
- 삭제 전 확인을 받습니다. 문구는 16.10절 기준을 따릅니다.
- 아이콘만 있는 버튼이므로 `aria-label`을 반드시 답니다.

### 19.5 D-day 캡션과 숫자를 세로로

`호주 출국까지` 캡션과 `D-12`가 가로로 나란히 놓여 있습니다. 캔버스는 **세로**입니다 — 캡션이 위, 숫자가 아래이고 `flex-direction: column`에 `gap: 10px`입니다.

그 세로 블록이 진행률과 나란히 놓여 가로 행을 이룹니다(`align-items: flex-end`, `gap: 40px`). 즉 바깥은 가로, 안쪽 D-day 블록은 세로입니다. 이 중첩이 바뀌면 88px 숫자가 캡션에 밀려 위치가 어긋납니다.

### 19.6 기본 화면 모드를 다크로

앱의 기본값을 **다크 모드**로 바꿉니다 (사용자 지시 2026-08-28).

- `app/layout.tsx`의 `<html data-theme="light">`를 `dark`로 바꿉니다.
- 이용자가 '나' 화면에서 고른 값이 `localStorage`에 있으면 그것이 우선합니다. 인라인 스크립트의 동작은 그대로입니다(3절).
- 저장된 값이 없을 때만 다크가 기본입니다.

### 19.7 우측 패널을 하나로 통일 (사용자 지시 2026-08-28)

지금은 홈과 메모의 우측 336 패널이 서로 다릅니다. 홈은 `내 메모` + `+ 새 메모` + 빠른 입력 + 목록이고, 메모는 `WRITING` + 제목 입력 + 내용 입력 + `저장하기`/`삭제`입니다. **하나로 합칩니다.**

통일된 우측 패널의 구성입니다.

| 요소 | 내용 |
|---|---|
| 제목 | `내 메모` — `WRITING` 캡션은 없앱니다 |
| 입력 | **본문만.** 제목 입력칸을 제거합니다 |
| 등록 | `저장하기` 버튼 하나. **`+ 새 메모` 버튼은 없앱니다** |
| 목록 | 메모 목록. 행에 마우스를 올리면 휴지통(19.4절) |
| 홈 전용 | 하단(`margin-top: auto`)에 `먼저 간 사람들이 힘들어한 것` 카드 |

홈과 메모 화면이 같은 컴포넌트를 씁니다. 홈에만 하단 어려움 카드가 붙는 차이뿐입니다.

**메모 레코드에서 제목이 빠집니다.** 16.2절에서 캔버스 목업을 근거로 `title`을 추가했으나, 입력칸을 없애면 채울 방법이 없습니다.

- 목록의 제목 자리는 **본문 첫 줄**을 한 줄로 잘라 씁니다(제목 추가 이전의 방식으로 되돌립니다).
- 저장 레코드는 `{ id, body, updatedAt }`입니다. 이미 `title`이 들어간 레코드가 있을 수 있으므로 읽을 때 무시하고 깨지지 않게만 처리합니다.
- 캔버스 메모 목업은 제목과 내용을 나눠 두지만 **사용자 지시가 캔버스보다 우선합니다.**

### 19.8 '나' 화면의 정보 수정과 출국일 행

**정보 수정 버튼이 눌리지 않는 것처럼 보입니다.** 코드상 `button`이고 핸들러도 있지만, 하는 일이 설정 영역으로 스크롤하는 것뿐입니다. 데스크톱에서는 프로필 카드와 설정이 한 화면에 다 보여 스크롤할 곳이 없으므로 눌러도 아무 일이 일어나지 않습니다.

- 눌렀을 때 **눈에 보이는 반응**이 있어야 합니다. 설정의 출국일 입력에 포커스를 주는 편이 낫습니다. 스크롤이 필요한 구간에서는 스크롤도 함께 합니다.
- 그래도 데스크톱에서 할 일이 마땅치 않다면 이 버튼을 없애는 편이 낫습니다. **아무 일도 하지 않는 버튼을 두지 않습니다** — Chip이 `onClick` 없으면 `button`으로 렌더하지 않는 원칙과 같습니다.

**출국일은 행 전체를 눌러 설정합니다.** 지금은 값 텍스트 부분만 눌립니다.

- 행 전체가 클릭 대상이 되도록 `<label>`로 감싸거나, 날짜 입력을 행 전체 크기로 깔고 시각적으로만 감춥니다.
- 최소 48px 터치 영역을 유지합니다.
- 다른 설정 행(국가 변경 등)도 같은 방식으로 행 전체가 눌리게 통일합니다. 한 화면에서 어떤 행은 전체가 눌리고 어떤 행은 텍스트만 눌리면 어색합니다.

### 19.9 `+ 새 메모` 버튼 정리

`+ 새 메모` 버튼이 두 곳에 있었습니다. 우측 패널과 메모 화면 본문입니다.

- **우측 패널의 버튼은 없앱니다**(19.7절). 패널 자체가 적는 곳이므로 `저장하기` 하나면 충분합니다.
- **메모 화면 본문의 버튼**은 지금 누르면 편집 시트가 열립니다. 우측 패널이 있는 데스크톱에서는 적는 곳이 이미 화면에 있는데 그 위로 시트가 또 뜨는 셈이라 어색합니다.
  - 우측 패널이 있는 구간(데스크톱)에서는 **시트를 열지 말고 패널의 입력창에 포커스**를 줍니다.
  - 우측 패널이 없는 구간(모바일·태블릿)에서는 지금처럼 시트를 엽니다. 거기서는 시트가 유일한 입력 수단입니다.

### 19.10 사이드바 접기와 우측 패널 접기 (사용자 지시 2026-08-28)

**좌측 사이드바 접기 버튼이 동작하지 않습니다.** 캔버스 목업에 접기 아이콘이 그려져 있어 마크업은 있지만, 정적 목업이라 동작이 정의돼 있지 않다는 이유로 `span` + `aria-hidden`으로만 두었습니다. 보이는데 눌리지 않는 가짜 어포던스입니다(국가 배지와 같은 문제).

- `button`으로 만들고 누르면 좌측 사이드바가 **236 ↔ 88 아이콘 레일**로 접히고 펴집니다. 88 레일은 태블릿에서 이미 쓰는 형태이므로 새 시각 언어를 만들지 않습니다.
- 접힌 상태에서는 라벨이 사라지고 아이콘만 남습니다. 접기 버튼의 화살표 방향이 상태에 따라 바뀝니다.
- `aria-label`과 `aria-expanded`를 답니다.
- 선택 상태를 `localStorage`에 남겨 다시 방문해도 유지합니다.

**메모 탭에서는 우측 패널이 기본으로 접혀 있습니다.** 메모 화면은 본문이 이미 메모 목록과 입력을 담고 있어, 우측에 같은 기능이 또 있으면 중복입니다.

- 우측 패널에도 접기·펼치기 토글을 둡니다.
- **메모 탭은 기본이 접힌 상태**, 홈은 기본이 펼친 상태입니다.
- 접힌 상태는 얇은 띠와 펼치기 버튼만 남깁니다. 완전히 없애지 않는 이유는 이용자가 다시 펼 수 있어야 하기 때문입니다.
- 이 상태도 `localStorage`에 남깁니다. 다만 화면별로 따로 기억합니다 — 홈에서 접었다고 메모에서 펴지면 안 됩니다.

## 20. 사용자 지적 수정 3차 (2026-08-28)

### 20.1 메모 화면에서는 우측 패널을 쓰지 않습니다

19.10절에서 "메모 탭은 기본이 접힌 상태"로 했는데, 접기 토글이 남아 있어 펼 수 있습니다. **메모 화면에서는 우측 패널 자체를 쓰지 않습니다.**

- 메모 화면에서 우측 패널과 그 접기·펼치기 버튼을 **모두 없앱니다.** 접힌 띠도 남기지 않습니다.
- 본문이 이미 목록과 입력을 담고 있어 우측에 같은 기능이 있을 이유가 없습니다.
- 홈에서는 지금처럼 펼친 상태로 둡니다.

### 20.2 사이드바 접기 아이콘 교체와 애니메이션

- 지금 아이콘(세로 막대 + `‹`)이 거의 보이지 않습니다. **눈에 들어오는 다른 아이콘으로 바꿉니다.**
- 접히고 펴질 때 **부드러운 애니메이션**을 넣습니다. 폭이 236 ↔ 88로 뚝 끊기지 않게 합니다.
- 우측 패널도 화면을 옮길 때 **자연스럽게 닫히고 열립니다.** 메모로 들어가면 닫히고 다른 탭으로 나오면 열립니다.

### 20.3 모달 등장 애니메이션 통일

**아래에서 위로 올라오며 페이드 인**하는 방식으로 통일합니다. 지금은 구간마다 다릅니다.

- 모바일: 지금의 바텀 시트 그대로(이미 아래에서 올라옴).
- **태블릿 이상: 아래에서 위로 올라오는 슬라이드 + 페이드.** 11.4절의 "데스크톱은 위에서 8px 내려오며 페이드"를 대체합니다. 위치(모바일 전폭 하단 · 태블릿 620 하단 중앙 · 데스크톱 480 중앙)는 그대로 두고 **등장 방식만** 바꿉니다.
- **눌렀을 때 뜨는 모달은 전부 같은 방식**을 씁니다. 가이드, 국가 선택, 할 일 추가, 메모 편집, 할 일 상세를 포함해 예외를 두지 않습니다.
- 캔버스 11.4절의 데스크톱 등장 방식과 다르지만 **사용자 지시가 캔버스보다 우선합니다.**

### 20.4 '나' 탭을 '프로필'로

- 탭 라벨을 `나`에서 **`프로필`**로 바꿉니다. 좌측 사이드바·아이콘 레일·하단 탭바 모두 같은 라벨을 씁니다.
- 탭 id는 `me`를 그대로 둡니다. 저장된 상태와 어긋나지 않게 하기 위해서입니다.
- 캔버스는 `나`이지만 사용자 지시가 우선합니다.

### 20.5 프로필 카드 정리

- **`정보 수정` 버튼을 없앱니다.** 눌렀을 때 출국일 달력이 열리는 것이 이름과 맞지 않습니다.
- 대신 **프로필(아바타)을 누를 수 있게** 합니다. 프로필 사진을 바꾸는 자리입니다.
- **프로필 카드 안의 출처 링크(`SourceLink`)를 삭제합니다.**

### 20.6 프로필 사진 (사용자 지시 2026-08-28)

프로필(아바타)을 누르면 사진을 바꿀 수 있습니다. **저장은 `localStorage`입니다.** 16절에서 접은 파일 저장(IndexedDB·암호화·보관 기간)을 다시 들이지 않습니다.

**전제: 저장 전에 반드시 축소합니다.** 이것이 성립 조건입니다.

- 원본을 그대로 넣으면 안 됩니다. `localStorage`는 문자열 전용이라 base64로 약 33% 부풀고, 한도가 오리진당 5MB 안팎이며 테마·출국일·메모와 나눠 씁니다. 폰 카메라 사진(2~5MB)은 base64로 3~7MB가 되어 한도를 바로 넘기고, 동기 API라 쓰는 동안 화면이 멈춥니다.
- 처리 순서: 파일 선택 → `<img>`로 읽기 → `canvas`에 **정사각 크롭 + 256×256 축소** → `toDataURL("image/webp", 0.8)` → 그 data URL만 저장.
- 결과는 대체로 10~30KB이고 base64로도 40KB를 넘지 않습니다. **원본은 저장하지 않습니다.**
- 받는 형식은 `image/png`, `image/jpeg`, `image/webp`입니다. SVG는 받지 않습니다.
  - 저장하는 것이 원본이 아니라 캔버스로 다시 그린 래스터 결과이므로 16절의 매직 넘버 검증만큼 무겁게 갈 필요는 없습니다. `accept`와 `img.onerror` 처리로 충분합니다.
- **디코드 전에 파일 크기 상한을 둡니다(예: 20~30MB).** 지나치게 큰 치수로 인코딩된 이미지는 축소 이전의 디코드·드로잉 단계에서 메모리·CPU가 튀어 탭이 멈추거나 튕길 수 있습니다(`SecurityReview.md` 9-1절). 상한을 넘으면 축소를 시도하지 않고 바로 실패로 처리합니다.
- 저장 실패(용량 초과 등)를 조용히 삼키지 않습니다. 실패하면 이용자에게 알리고 이전 아바타를 유지합니다.
- 사진이 없으면 지금처럼 국가 라벨 첫 글자를 씁니다. 사진을 지우는 수단도 함께 둡니다.
- **프로필 사진도 텔레메트리 SDK 규칙(`SecurityReview.md` 2절 3번)의 적용 대상입니다.** 향후 분석·크래시 리포팅 SDK를 도입할 때 이 사진이 페이로드에 섞이지 않는지 반드시 확인합니다. 얼굴 사진은 텍스트 메모보다 화면에서 훨씬 눈에 띄는 개인정보라, 화면을 그대로 녹화하는 세션 리플레이형 도구가 있다면 텍스트보다 훨씬 쉽게 캡처됩니다.

### 20.7 20절 반영 후 남은 세 가지 (PM 검증 2026-08-28)

**1. 메모 화면에서 우측 패널이 1px 남습니다.** `width: 0`으로 접어도 `border-left: 1px`이 그대로 남아 실측 폭이 1px입니다. 20.1절은 "접힌 띠도 남기지 않습니다"이므로 완전히 0이어야 합니다. 접힌 상태에서는 테두리도 함께 없앱니다.

**2. 프로필 화면의 제목이 아직 `나`입니다.** 탭 라벨은 `프로필`로 바뀌었는데 화면 `h1`은 `나`입니다. 한 화면 안에서 탭과 제목이 다르면 어색합니다. `h1`도 `프로필`로 맞춥니다.

**3. 홈 화면에 `h1`이 없습니다.** 나머지 세 화면은 각각 `할 일`·`메모`·`프로필`이라는 `h1`이 있는데 홈만 없습니다. 스크린리더로 훑을 때 홈만 제목이 잡히지 않고, 화면 제목으로 위치를 파악하는 흐름이 끊깁니다.

- 시각적으로 큰 제목을 새로 넣으라는 뜻이 아닙니다. 정보 예산(한 화면에 블록 3~4개)은 그대로 지킵니다.
- 이미 있는 브랜드 영역의 `Wabi`를 `h1`으로 올리거나, 화면 제목을 `h1`으로 두되 시각적으로만 감추는 방식(`sr-only`) 중에 택합니다.

### 20.8 사이드바 접기 버튼이 순간이동하듯 움직임 (PM 원인 규명 2026-08-28)

접고 펼 때 버튼이 부드럽게 움직이지 않고 튑니다. 실측한 좌표입니다.

```
접기 전  x=179 y=26
+60ms   x=87  y=63   ← y가 한 번에 37px 점프
+700ms  x=27  y=68
transition-property: transform
```

**원인**: 전환 대상이 `transform`뿐인데, 실제 위치 변화는 **레이아웃에서 나옵니다.** 사이드바가 236에서 88로 줄면 브랜드 줄이 재배치되고(라벨이 사라지며 버튼이 다음 줄로 밀림) 그 위치 변화는 애니메이션되지 않습니다. 레이아웃으로 움직이는 것은 전환할 수 없습니다.

**고치는 방향**: 버튼의 위치가 브랜드 줄의 재배치에 끌려다니지 않게 합니다.

- 버튼을 사이드바 기준으로 위치를 고정합니다(예: `position: absolute`로 상단 우측에 고정). 그러면 접힌 폭·펼친 폭에 따라 x만 바뀌고 y는 변하지 않습니다.
- 라벨(`Wabi`)은 사라질 때 폭이 줄거나 페이드되게 하되, 그 변화가 버튼을 밀지 않도록 합니다.
- 접힌 상태에서 브랜드 로고와 버튼이 겹치지 않게 배치를 확인합니다.

### 20.9 모달 애니메이션이 전부 동작하지 않음 (PM 원인 규명 2026-08-28)

**증상**: 사용자가 "아직 모달 등의 애니메이션이 없다"고 지적했습니다. 실측해 보니 가이드 모달을 연 지 120ms 뒤(0.22s 애니메이션의 중간)인데 `opacity: 1`, `transform: none`으로 이미 최종 상태였습니다.

**원인 — CSS Modules의 키프레임 스코프**입니다.

- `@keyframes`가 전부 `app/globals.css`에 **전역**으로 정의돼 있습니다(`wabiSheetUp`, `wabiFadeIn`, `wabiSlideIn`, `wabiModalRiseIn`).
- 참조는 전부 `.module.css` 안에 있습니다(`BottomSheet`, `GuideSheet`, `PainSheet`, `TaskDetailScreen`).
- **CSS Modules는 `.module.css` 안의 `animation-name`을 자동으로 스코프 처리합니다.** `wabiModalRiseIn`이 `BottomSheet-module__해시__wabiModalRiseIn`으로 바뀌는데 그 이름의 키프레임은 없습니다.
- 브라우저는 존재하지 않는 애니메이션 이름을 **오류 없이 무시**합니다. 그래서 지금까지 드러나지 않았습니다.

`wabiSheetUp`·`wabiFadeIn`·`wabiSlideIn`도 같은 구조이므로 **시트 애니메이션은 처음부터 한 번도 동작한 적이 없습니다.** 정적 스크린샷으로는 최종 상태만 보여 QA도 잡지 못했습니다.

**고치는 방향**은 둘 중 하나입니다.

1. 키프레임을 참조하는 `.module.css` 안으로 옮깁니다. 스코프가 맞아떨어집니다. 여러 모듈이 같은 키프레임을 쓰면 중복이 생깁니다.
2. 전역 정의를 유지하되 모듈에서 `animation-name: global(wabiSheetUp)`처럼 전역임을 명시합니다.

어느 쪽이든 **고친 뒤에는 반드시 실행 중에 측정해 확인합니다.** 애니메이션 중간 시점의 `opacity`나 `transform`이 최종값과 달라야 실제로 동작하는 것입니다.

### 20.10 사이드바 라벨이 즉시 사라짐

접기 버튼을 누르면 라벨이 부드럽게 사라지지 않고 즉시 없어집니다. 실측하니 60ms 시점에 이미 `display: none`이었습니다.

`transition: all`이 걸려 있지만 **`display`는 전환할 수 없는 속성**입니다. `display: none`은 단계 없이 즉시 적용됩니다.

`display` 대신 `opacity`와 `width`(또는 `max-width`)로 줄여 전환 대상이 되게 합니다. 접힌 뒤에도 자리를 차지하지 않아야 하므로 폭을 0으로 만드는 것이 함께 필요합니다.

### 20.11 사용자 지적 4차 (2026-08-28)

**1. 시트가 올라오는 속도가 너무 빠릅니다.** 할 일을 눌러 상세가 올라올 때 애니메이션이 눈에 남지 않습니다. 지속 시간을 늘립니다. 20.9절을 고쳐 애니메이션이 실제로 동작하게 된 뒤 체감으로 맞춥니다.

**2. 바깥 영역을 눌러도 닫힙니다.** 시트·모달이 열렸을 때 딤 영역을 클릭하거나 터치하면 닫힙니다. 닫기 버튼을 반드시 눌러야 하는 지금 방식은 번거롭습니다.
- `BottomSheet`에는 이미 딤 버튼이 있으므로 모든 시트가 같은 동작을 하는지 확인합니다. 할 일 상세처럼 시트가 아닌 전체 화면 오버레이도 포함합니다.
- 닫기 버튼은 그대로 둡니다. 키보드 사용자에게 필요합니다. `Escape`도 계속 동작해야 합니다.
- **누른 지점과 놓은 지점이 모두 딤 요소일 때만 닫습니다(`pointerdown`/`pointerup` 또는 `mousedown`/`mouseup` 둘 다 딤 요소).** "놓인 지점이 딤 요소인가"만 보면, 시트 안의 텍스트를 드래그로 선택하다가 포인터가 딤 영역까지 밀려나 놓였을 때 오탐으로 닫힙니다(`SecurityReview.md` 9-3절 1번).
- **닫는 경로(닫기 버튼·`Escape`·딤 클릭) 세 가지 모두 포커스가 시트를 연 트리거 요소로 복귀해야 합니다.** 경로마다 다르게 동작하면 스크린리더·키보드 사용자가 화면에서 위치를 잃습니다(`SecurityReview.md` 9-3절 2번).

**3. 날짜 입력은 칸 전체를 눌러 달력이 열립니다.** 지금은 오른쪽 달력 아이콘을 정확히 눌러야만 열립니다.
- 대상은 두 곳입니다. 할 일 추가 시트의 마감 입력과 '나'(프로필) 화면의 출국일 행입니다.
- **`<label>`로 감싸는 것만으로는 부족합니다.** 라벨 클릭은 입력에 포커스를 줄 뿐이고, 네이티브 날짜 입력은 포커스만으로 달력을 열지 않습니다. 그래서 출국일 행이 눌러도 아무 반응이 없습니다.
- 행이나 칸을 누르면 `input.showPicker()`를 호출합니다. 미지원 브라우저에서는 포커스로 대체합니다(정보 수정 버튼에 이미 쓰인 방식).

**4. 다크모드에서 달력 아이콘이 배경과 구분되지 않습니다.** 네이티브 날짜 입력의 아이콘은 브라우저가 그리는 것이라 CSS로 직접 색을 바꿀 수 없습니다.
- `color-scheme`을 선언합니다. `[data-theme="dark"]`에 `color-scheme: dark`, 라이트에 `color-scheme: light`를 둡니다.
- 이 한 줄로 날짜 입력 아이콘뿐 아니라 스크롤바·기본 폼 컨트롤이 모두 테마에 맞게 렌더됩니다. 현재 어디에도 선언돼 있지 않습니다.

### 20.12 사용자 지적 5차 (2026-08-28)

**1. 닫힐 때도 애니메이션이 필요합니다.** 할 일 상세가 올라올 때는 슬라이드가 보이는데 닫힐 때는 즉시 사라집니다. 열림과 닫힘이 어긋납니다.

- CSS 애니메이션은 요소가 붙을 때만 실행됩니다. 닫는 순간 바로 언마운트하면 나가는 애니메이션이 돌 틈이 없습니다.
- **닫는 중 상태를 두고, 나가는 애니메이션이 끝난 뒤에 언마운트합니다.** `animationend`를 기다리거나 지속 시간만큼 지연시킵니다.
- 시트·모달·상세 화면 모두 같은 방식으로 통일합니다. 들어올 때와 대칭인 방향으로 나갑니다(아래에서 올라왔으면 아래로 내려갑니다).
- 딤 배경도 함께 페이드 아웃합니다.

**2. 캘린더가 '출국일' 텍스트를 가립니다.** 원인은 날짜 입력의 위치입니다.

- 지금 `.dateInput`은 `width: 1px; height: 1px; clip: rect(0,0,0,0)`로 화면에서 감춰져 있습니다. 스크린리더용으로 감추는 흔한 방식입니다.

### 20.13 사용자 지적 6차 (2026-08-28)

**1. 시트 안에서 스크롤이 되지 않습니다.** 모바일에서 '먼저 간 사람들이 힘들어한 것' 답변을 열고 스크롤하면 움직이지 않습니다.

- 고친 뒤 **실제 휠·터치 이벤트로 확인합니다.** `scrollTop`을 코드로 대입하는 방식은 포인터 처리를 우회해서 이 결함을 잡지 못합니다.

**2. 누르는 중·마우스를 올린 상태를 눈으로 알 수 있어야 합니다.** 지금은 어디를 누르고 있는지 표시가 없습니다.

**3. `+` 버튼이 너무 큽니다.** 모바일에서 할 일 탭과 메모 탭의 추가 버튼 크기를 **절반으로** 줄입니다. 최소 터치 영역 48×48px은 유지하고 아이콘만 줄입니다.

**7. 모바일에서는 모든 탭에 헤더를 둡니다.** 지금은 홈에만 있습니다.

- 브랜드(`W` + `Wabi`)와 가이드 버튼, 국가 전환이 모든 탭에서 같은 자리에 보입니다.

- 데스크톱은 지금처럼 헤더가 없습니다. 사이드바가 그 역할을 합니다(11.4절).

- 출국일 입력에는 적용하지 않습니다. 이미 출국한 사람이 과거 날짜를 넣을 수 있어야 합니다.

## 21. 직접 추가한 할 일의 삭제와 정렬 (2026-08-28)

사용자가 "할 일 삭제 버튼이 없네 추가해줘 그리고 가장 최근에 만든일을 상단에 오도록 배치하고"라고 지시했습니다.

### 21.1 먼저 고쳐야 할 것 — 직접 추가한 할 일이 저장되지 않습니다

`useWabiApp.ts`의 `customTasks`는 `useState`일 뿐 **어디에도 저장되지 않습니다.** 이용자가 할 일을 추가하고 새로고침하면 사라집니다. `notes.ts` 주석은 "직접 추가한 할 일과 같은 자리"(localStorage)라고 적어두었지만 실제로 구현된 적이 없습니다.

저장이 되지 않으면 "가장 최근에 만든 순" 정렬은 한 세션 안에서만 의미가 있으므로, 정렬보다 이것이 먼저입니다.

- 저장 위치는 **localStorage** 입니다. 키는 `wabi:custom-tasks`, `notes.ts`와 같은 방식(`normalize`로 손상된 레코드를 걸러내고 실패해도 빈 배열로 되돌아오는 형태)을 따릅니다.
- 보안 검토 2절 기준 안에 있습니다. 이용자가 직접 적는 짧은 자유 텍스트이고, 앱이 요구하는 구조화된 신원 식별자가 아니며, 서버로 전송되지 않습니다.
- **국가별로 나눠 저장합니다.** 지금 상태(`Record<CountryCode, Task[]>`)를 유지합니다.

### 21.2 `createdAt` 필드를 추가합니다

정렬 기준이 필요합니다. 추가 시점의 ISO 문자열을 `createdAt`에 넣습니다. 이 값은 **정렬에만 쓰고 화면에 표시하지 않습니다** — 마감일(`dueDate`)과 혼동될 수 있기 때문입니다.

`createdAt`이 없는 레코드(저장 기능 이전에 만들어진 것은 없지만, 손상되었거나 손으로 넣은 경우)는 가장 오래된 것으로 취급해 순서만 뒤로 밀고 버리지 않습니다.

### 21.3 정렬 — 최근에 만든 것이 위로

`allTasks`는 지금 `countryTasks.concat(countryCustomTasks)`라 직접 추가한 할 일이 **맨 아래**에 붙습니다. 반대로 바꿉니다.

- **직접 추가한 할 일이 기본 제공 할 일보다 위**에 옵니다.
- 직접 추가한 할 일끼리는 **`createdAt` 내림차순** — 가장 최근에 만든 것이 맨 위입니다.
- 기본 제공 할 일의 기존 순서는 **그대로 둡니다.** 조사해서 넣은 준비 순서라 임의로 섞으면 안 됩니다.

이 정렬은 할 일 목록 화면에 적용합니다. `pickNextTask`(다음 할 일 카드)와 완료 개수 계산은 **영향을 받지 않아야 합니다** — 그쪽은 마감일과 긴급도로 고르는 별개 규칙입니다.

### 21.4 삭제 버튼

**직접 추가한 할 일에만** 삭제 버튼이 붙습니다. 기본 제공 할 일은 조사해서 넣은 내용이라 삭제 대상이 아닙니다. 필요 없으면 완료로 넘기면 됩니다.

- 위치는 **할 일 상세 화면(`TaskDetailScreen`)** 입니다. 목록 행에 직접 두면 완료 토글 옆에 파괴적 동작이 붙어 잘못 누르기 쉽습니다.
- 삭제는 **확인을 거칩니다.** 기존 삭제 확인 시트를 재사용하고, 딤 클릭은 취소와 같습니다(20.11-2절).
- 삭제한 뒤에는 상세 화면을 닫고 **목록으로 돌아옵니다.** 사라진 항목의 상세 화면에 남아 있으면 안 됩니다.
- 삭제 버튼은 파괴적 동작이므로 `--alert` 색을 씁니다. 다만 화면에서 가장 눈에 띄는 요소가 되지 않도록 채움이 아닌 테두리 형태로 둡니다.

### 21.5 확인할 것

- 할 일을 추가하고 **새로고침해도 남아 있는지**
- 방금 만든 할 일이 **목록 맨 위**에 오는지, 두 개를 연달아 만들면 나중 것이 위인지
- 기본 제공 할 일의 순서가 **바뀌지 않았는지**
- 삭제 후 목록으로 **돌아오는지**, 새로고침해도 **되살아나지 않는지**
- 국가를 바꿨을 때 **그 국가의 할 일만** 보이는지
- 기본 제공 할 일에는 삭제 버튼이 **없는지**

### 21.6 화면 모드 토글의 hover는 색을 바꾸지 않습니다 (2026-08-28)

사용자가 "화면 모드 hover시 color가 달라지는데 이거 없애"라고 지시했습니다. 처음에 hover 규칙을 통째로 지웠더니 "color 바뀌는 것만 빼라고 했더니 hover 효과까지 빠지면 어떻게"라고 다시 지적했습니다.

**hover에는 반응하되, 색으로 반응하지 않습니다.** 두 지시를 모두 만족하는 방법은 색이 아닌 다른 수단으로 피드백을 주는 것뿐입니다. 헤더 버튼에 이미 쓰고 있는 어휘(20.14절, "약간 scale을 줄였다가 놓으면 되돌아온다")를 그대로 씁니다.

| 상태 | 화면 모드 토글 |
|---|---|
| 평상시 | `scale(1)` |
| hover | `scale(0.97)` — **색 변화 없음** |
| 누름(active) | `scale(0.94)` + 행 배경 `--sunken` |
| 키보드 포커스 | 행 배경 `--sunken` |

`prefers-reduced-motion`이 켜져 있으면 `transform`과 `transition`을 모두 끕니다.

`:focus-visible`은 지우지 않습니다. 키보드 이용자가 지금 어디에 있는지 아는 **유일한 단서**라, hover 지시를 이유로 함께 없애면 키보드로 쓸 수 없게 됩니다.

**다른 설정 행(국가 변경·출국일)의 hover 배경은 그대로 둡니다.** 그쪽은 눌러도 화면 전체 색이 뒤집히지 않아 같은 문제가 없습니다.

#### 함께 고친 결함 — 토글 배경이 라벨을 덮고 있었습니다

실측하다 발견했습니다. `.toggle`은 행 전체를 덮는 `position:absolute; inset:0` 오버레이입니다(20.15절). 여기에 배경을 칠하면 **뒤에 있는 "화면 모드" 라벨을 가립니다** — 라벨 중앙에서 `elementFromPoint`를 부르면 라벨이 아니라 토글이 돌아옵니다. 눌렀을 때 라벨이 사라지고 있었습니다.

배경은 **행이 그립니다.** `.settingRowDate`가 `opacity:0` 입력을 다루는 방식(20.13절 2번)과 같은 해법입니다. 다만 `.toggle`은 다른 CSS 모듈이라 해시된 클래스명을 `MeScreen.module.css`에서 쓸 수 없으므로, 요소 선택자로 짚습니다.

```css
.settingRow:has(button:active),
.settingRow:has(button:focus-visible) { background: var(--sunken); }
```

이 행에 든 버튼은 토글 하나뿐이라 요소 선택자로 충분합니다.

### 21.7 설정 행에 좌우 여백을 줍니다 (2026-08-28)

사용자가 "프로필 설정 들 좌우 패딩 약간씩 줘서 여유있게 만들어"라고 지시했습니다.

설정 행 네 종류(`.settingRow` `.settingRowStatic` `.settingRowButton` `.settingRowDate`)의 좌우 패딩이 모두 `0`이라 라벨과 값이 행 끝에 붙어 있었습니다. **`padding: 0 14px`** 를 넣습니다.

"설정" 소제목(`.settingsHeading`, 744px 이상에서만 보임)에도 같은 값을 넣어 라벨과 세로선을 맞춥니다.

배경(눌림·hover)과 밑줄은 **행 전체 너비를 유지합니다.** 패딩은 안쪽 내용만 들여쓰고 행 자체를 좁히지 않습니다.

## 22. 기본 제공 할 일에서 지어낸 일정 정보를 뺍니다 (2026-08-28)

사용자가 "홈이랑 할 일에 하드코딩 된 정보들 전부 제거해"라고 지시했고, 범위를 "이번 주 할 일에 하드 코딩 된 정보들을 제거해", 이어서 "할 일에도 똑같은 정보가 들어가 있으니까 그 정보들도 제거하고"로 좁혔습니다.

### 22.1 무엇이 문제인가

`meta`는 **마감 표시 자리**입니다. 직접 추가한 할 일에서는 `deriveDueDisplay`가 오늘 날짜와 마감일을 비교해 `"3일 남음"` `"오늘까지"` `"마감 지남"`을 넣습니다.

그런데 기본 제공 할 일은 같은 자리에 마감과 무관한 문구를 박아두었습니다.

| 필드 | 기본 제공 할 일에 박혀 있는 값 | 문제 |
|---|---|---|
| `meta` | `"만 18~30세"` `"비자 조건 8501"` `"개설 후 20일 이내 신원 확인"` | 마감 표시 자리에 마감이 아닌 문구가 들어갑니다 |
| `week` | `true`/`false` | 왜 이번 주인지 아무 계산이 없습니다 |
| `urgent` | `true`/`false` | 왜 긴급한지 아무 근거가 없습니다 |

이 세 값이 홈의 "이번 주 할 일"과 할 일 탭 목록에 **똑같이** 나타납니다. 홈의 "이번 주 할 일"은 `allTasks.filter((task) => task.week)`라, 지어낸 플래그가 그대로 목록이 됩니다.

### 22.2 어떻게 고치는가

**기본 제공 할 일에서 `meta`·`week`·`urgent`를 없앱니다.** 세 값은 마감일이 있을 때만 계산해서 나옵니다.

- `Task` 타입에서 `meta`·`week`·`urgent`를 **선택 항목**으로 바꿉니다.
- 기본 제공 데이터(`AU_TASKS` `CA_TASKS` `JP_TASKS`)에서 세 필드를 지웁니다.
- **`title`·`body`·`items`·`sourceUrl`·`tag`·`phase`는 그대로 둡니다.** 조사해서 출처까지 붙인 내용이고, 지어낸 값이 아닙니다.
- 홈의 "이번 주 할 일"은 **마감일로 계산**합니다. `week` 플래그를 읽지 말고 `dueDate`가 있는 할 일만 `deriveDueDisplay`로 판정합니다. 마감일이 없는 기본 제공 할 일은 이 목록에 뜨지 않습니다.
- 목록 행과 상세 화면에서 `meta`가 없으면 **그 자리를 비웁니다.** 빈 문자열이나 대체 문구를 넣지 않습니다.
- `urgent`가 없으면 강조 색을 쓰지 않습니다.

### 22.3 영향

- 홈의 "이번 주 할 일"은 이용자가 **마감일을 넣어 직접 추가한 할 일**만 보여줍니다. 없으면 기존 빈 상태 문구("이번 주 할 일이 없습니다")가 그대로 나옵니다.
- 진행률(`doneCount / total`)은 **바뀌지 않습니다.** 기본 제공 할 일은 목록에 그대로 있고 완료 표시도 됩니다.
- `pickNextTask`는 완료되지 않은 첫 할 일을 고를 뿐 `week`·`urgent`를 보지 않으므로 영향이 없습니다.
- `customTasks.ts`의 `normalize`는 저장된 레코드에 세 필드가 없을 수 있음을 이미 다뤄야 합니다.

### 22.4 확인할 것

- 홈의 "이번 주 할 일"에 기본 제공 할 일이 **하나도 없는지**
- 마감일을 넣어 할 일을 만들면 그것만 "이번 주 할 일"에 뜨는지, 8일 뒤로 넣으면 안 뜨는지
- 할 일 탭 목록에서 기본 제공 할 일의 **오른쪽 마감 자리가 비어 있는지**, 빈 문자열 흔적이나 여백 붕괴가 없는지
- 기본 제공 할 일에 **긴급 강조 색이 사라졌는지**
- 진행률 분모가 **그대로인지**
- 상세 화면에서 기본 제공 할 일의 본문·준비물·출처가 **그대로 남아 있는지**

### 22.5 이용자가 직접 고른 "이번 주"는 남깁니다 (2026-08-28)

22.2절에서 "이번 주 할 일"을 `dueDate`가 있는 할 일로만 한정했더니, **캘린더로 날짜를 고르지 않고 "이번 주"·"오늘까지" 같은 고정 선택지로 만든 직접 추가 할 일이 목록에서 빠집니다.** `dueDate`가 없기 때문입니다.

이건 22절이 노린 것이 아닙니다. 없애려던 것은 **아무도 고르지 않았는데 데이터에 박혀 있던 값**이고, 이용자가 "이번 주"를 직접 골라 만든 할 일은 **이용자 본인의 선언**입니다. 남겨야 합니다.

판정 기준을 값의 **출처**로 바꿉니다.

| 출처 | 이번 주 할 일에 뜨는가 |
|---|---|
| `dueDate`가 있어 `deriveDueDisplay`가 계산한 `week` | 뜹니다 |
| 이용자가 고정 선택지에서 "이번 주"·"오늘까지"를 직접 고름 | **뜹니다** |
| 기본 제공 데이터에 박혀 있던 `week: true` | 뜨지 않습니다 (22절에서 필드 자체를 지웠으므로 자연히 해당 없음) |

기본 제공 할 일에는 `week` 필드가 아예 없으므로, `task.week === true`를 그대로 읽어도 기본 제공 항목은 걸러집니다. **`dueDate` 유무를 추가 조건으로 걸 필요가 없습니다.**

확인할 것: 캘린더로 3일 뒤를 고른 할 일과 고정 선택지 "이번 주"로 만든 할 일이 **둘 다** 뜨는지, 고정 선택지 "다음 주 이후"로 만든 할 일과 기본 제공 할 일은 **뜨지 않는지**.

## 23. 조사한 할 일은 목록이 아니라 추천으로 (2026-08-28)

사용자가 "할 일 추가에는 출국 전 반드시 해야 하는 일을 나타내자"라고 지시했고, 기존 목록은 "목록에선 빼고 추천으로만"으로 정했습니다.

지금까지 조사해 넣은 할 일은 앱을 열면 **이미 내 목록에 들어와 있었습니다.** 고른 적도 없는데 진행률의 분모가 되고 완료 대상이 됩니다. 앞으로는 이용자가 **고를 때만** 목록에 들어갑니다.

### 23.1 무엇이 바뀌는가

| | 지금 | 바뀐 뒤 |
|---|---|---|
| 할 일 탭 첫 화면 | 조사한 할 일이 채워져 있음 | **비어 있음** |
| 조사한 할 일의 자리 | 목록 | **"할 일 추가" 안의 추천** |
| 진행률 분모 | 조사한 할 일 개수 | **이용자가 고른 개수** |
| 목록에 들어오는 경로 | 처음부터 있음 | 추천에서 고르거나 직접 적음 |

### 23.2 추천 목록

"할 일 추가" 시트에 추천을 붙입니다.

- **지금 고른 단계에 맞는 것만 보여줍니다.** 시트에 이미 출국 전 / 현지 정착 선택이 있으므로(`addTaskPhase`), 그 값에 맞는 항목만 추립니다. 출국 전을 고르면 출국 전 필수 항목이 뜹니다.
- **현재 국가의 항목만** 보여줍니다.
- **이미 내 목록에 있는 항목은 추천에서 감춥니다.** 같은 것이 두 번 들어가지 않아야 합니다.
- 추천이 하나도 남지 않으면 추천 영역 자체를 **그리지 않습니다.** 빈 자리나 대체 문구를 만들지 않습니다.

### 23.3 추천에서 고르면 어떻게 들어오는가

고른 항목은 **이용자의 할 일이 됩니다.** 조사한 내용은 그대로 따라옵니다.

- `title`·`body`·`items`·`sourceUrl`·`tag`·`phase`를 **그대로 복사**합니다. 출처 링크가 따라와야 상세 화면에서 근거를 볼 수 있습니다.
- `meta`·`week`·`urgent`는 **넣지 않습니다**(22절). 이용자가 마감일이나 고정 선택지를 함께 고르면 그때 계산해 붙입니다.
- `createdAt`은 **고른 시각**입니다. 그래야 21절의 "최근에 만든 것이 위" 정렬에 맞게 들어갑니다.
- `id`는 원본 항목의 id를 **그대로 씁니다.** 이미 추가했는지 판별하는 기준이 되고, 국가별로 이미 구분되어 있습니다.
- 저장 위치는 21절과 같은 `wabi:custom-tasks`입니다. 새 저장소를 만들지 않습니다.
- **삭제할 수 있습니다.** 추천에서 왔든 직접 적었든 이용자가 넣은 것이므로 21.4절의 삭제 버튼이 그대로 붙습니다. 삭제하면 추천 목록에 다시 나타납니다.

### 23.4 빈 상태

할 일 탭과 홈이 처음에는 비어 있습니다. 기존 문구("등록된 할 일이 없습니다", "아직 등록된 할 일이 없습니다", "이번 주 할 일이 없습니다")를 그대로 쓰되, 할 일 탭에서는 **무엇을 하면 되는지 한 줄로 알려줍니다.** 새 화면이나 별도 안내 카드를 만들지 않습니다 — 문구 한 줄이면 충분합니다.

### 23.5 건드리지 않는 것

- **가이드 시트**와 홈의 **"먼저 간 사람들이 힘들어한 것"** 은 그대로 둡니다. 목록에 미리 들어와 있던 것이 아니라 읽는 정보라, 이번 지시의 대상이 아닙니다.
- 조사 데이터(`AU_TASKS`·`CA_TASKS`·`JP_TASKS`)는 **지우지 않습니다.** 목록의 초기값이 아니라 추천의 원본으로 자리를 옮깁니다.
- 국가 전환·진행률 계산 방식·정렬 규칙(21.3절)은 그대로입니다.

### 23.6 확인할 것

- 저장소를 비우고 처음 열었을 때 할 일 탭과 홈이 **비어 있는지**, 진행률이 0/0인지
- "할 일 추가"에서 출국 전을 고르면 **출국 전 항목만**, 현지 정착을 고르면 **현지 정착 항목만** 추천되는지
- 추천에서 하나 고르면 목록 **맨 위**에 들어오는지, 상세에서 **본문·준비물·출처**가 보이는지
- 방금 추가한 항목이 추천 목록에서 **사라지는지**, 삭제하면 **다시 나타나는지**
- 국가를 바꾸면 그 국가의 추천만 뜨는지
- 추천을 전부 추가하면 추천 영역이 **사라지는지**(빈 자리가 남지 않는지)
- 새로고침해도 고른 항목이 **남아 있는지**

### 23.7 저장한 할 일에서 출처 링크가 사라집니다 (PM 실측, 2026-08-28)

`customTasks.ts`의 `normalizeTask`가 **`sourceUrl`을 읽어 오지 않습니다.** 저장할 때는 들어가는데 읽을 때 버려집니다.

```
저장된 레코드의 키: id phase title tag body items done sourceUrl createdAt
normalizeTask가 만드는 객체: id phase title meta week urgent tag body items done dueDate createdAt
```

그래서 추천에서 할 일을 고른 **직후에는 상세 화면에 출처 링크가 보이지만(1개), 새로고침하면 사라집니다(0개).** 메모리에 있던 객체가 저장소에서 다시 읽은 객체로 바뀌기 때문입니다.

23.3절이 "출처 링크가 따라와야 상세 화면에서 근거를 볼 수 있다"고 적은 것이 지켜지지 않습니다. 조사한 내용을 근거와 함께 보여주는 것이 이 앱의 목적이므로, 링크가 하루 만에 사라지면 남은 것은 출처 없는 주장뿐입니다.

`normalizeTask`에 `sourceUrl`을 추가합니다. `SourceLink`가 https가 아닌 값을 이미 걸러내므로(17절) 문자열이면 그대로 통과시켜도 됩니다.

**확인은 반드시 새로고침한 뒤에 합니다.** 추가 직후에는 메모리의 객체를 그대로 쓰기 때문에 결함이 드러나지 않습니다.

## 24. 메모 저장 안정성과 프로필 상호작용 (2026-08-28)

### 24.1 메모 저장 실패가 조용히 묻힙니다

`writeStoredNotes`의 `catch`가 비어 있습니다. 용량 한도를 넘거나 프라이빗 모드로 저장이 막히면 **화면에는 메모가 보이는데 실제로는 저장되지 않은 상태**가 됩니다. 새로고침해야 사라진 것을 압니다.

메모는 개수 제한이 없는 유일한 데이터라 한도에 닿을 수 있는 것도 메모뿐입니다.

`writeStoredAvatar`와 같은 방식으로 고칩니다.

- `writeStoredNotes`가 **성공 여부를 돌려줍니다.**
- 실패하면 **알리고, 입력 내용을 지우지 않습니다.** 이용자가 방금 쓴 글을 잃지 않아야 합니다.
- 저장에 실패했으면 화면의 목록도 **바꾸지 않습니다.** 저장되지 않은 것이 저장된 것처럼 보이면 안 됩니다.
- 메모 작성(`saveNote`), 빠른 작성(`quickAddNote`), 삭제(`deleteNote`) 세 곳 모두 해당합니다.

`writeStoredCustomTasks`도 같은 문제를 안고 있으면 함께 고칩니다.

### 24.2 메모 id가 겹칠 수 있습니다

`note-${Date.now()}`라서 같은 밀리초에 두 개가 만들어지면 id가 겹칩니다. 그러면 하나를 지울 때 `filter`가 **둘 다 지웁니다.**

`crypto.randomUUID()`를 씁니다. 다만 이 함수는 **보안 컨텍스트(https 또는 localhost)에서만** 있으므로, 없을 때는 시각과 난수를 섞은 값으로 물러섭니다. 직접 추가한 할 일의 id도 같은 방식이면 함께 고칩니다(추천에서 온 항목은 원본 id를 그대로 쓰므로 해당하지 않습니다).

### 24.3 프로필 화면에 blur 반응을 넣습니다

사용자가 "프로필에 hover나 active시 약간 약간 blur를 추가해서 효과를 주고"라고 지시했습니다. "약간 약간"이라고 두 번 말한 만큼 **아주 옅게** 넣습니다.

대상에 따라 다르게 씁니다. **글자에 `filter: blur()`를 걸면 렌더링이 깨진 것처럼 보이기 때문입니다.**

| 대상 | hover·active 반응 |
|---|---|
| 프로필 사진(아바타) | `filter: blur()` — 사진이라 옅게 흐려져도 자연스럽고, 누르면 바꿀 수 있다는 느낌을 줍니다 |
| 설정 행·이름 등 글자가 있는 요소 | **번지는 그림자**(`box-shadow`, 오프셋 없이 blur 반경만) — 글자는 또렷하게 두고 테두리만 부드럽게 번집니다 |

- 아바타는 hover에서 더 옅게, active에서 조금 더 흐리게 합니다. 값은 1px을 넘지 않습니다.
- 기존 반응(눌림 배경, 화면 모드 토글의 scale)은 **그대로 두고 그 위에 더합니다.** 21.6절에서 정한 "화면 모드는 hover에서 색을 바꾸지 않는다"는 유지됩니다 — 번지는 그림자는 색 변화가 아닙니다.
- `prefers-reduced-motion`에서는 전환을 끕니다.

### 24.4 출국일은 과거 날짜도 고를 수 있습니다 (철회, 2026-08-28)

사용자가 처음에 "출국일 설정도 과거는 설정 불가능하게해"라고 했다가, **이미 출국해서 현지 정착 단계에 있는 이용자가 자신의 출국일을 넣을 수 없게 된다**는 점을 확인하고 "출국일은 과거날짜도 포함하는게 맞네 그렇게해줘"로 되돌렸습니다.

**출국일 입력에 `min`을 넣지 않습니다.** `AddTaskSheet`의 기존 주석("출국일 입력에는 적용하지 않는다 — 이미 출국한 사람은 과거 날짜를 넣어야 하기 때문이다")이 옳았으므로 그대로 둡니다.

할 일 마감 입력의 `min=오늘`은 **그대로 유지합니다**(20.13절 8번). 앞으로 할 일은 과거에 마감될 수 없지만, 출국일은 이미 지나갔을 수 있다는 차이입니다.

### 24.5 확인할 것

- 저장소를 가득 채운 상태에서 메모를 쓰면 **알림이 뜨고 입력이 남아 있는지**, 목록에 가짜로 추가되지 않는지
- 메모를 아주 빠르게 연속으로 만들었을 때 id가 **모두 다른지**, 하나를 지울 때 하나만 지워지는지
- 프로필 사진에 마우스를 올리면 **아주 옅게 흐려지는지**, 누르면 조금 더 흐려지는지
- 설정 행에서 **글자가 흐려지지 않는지**(번지는 그림자만 보이는지)
- 화면 모드 토글이 여전히 hover에서 **색을 바꾸지 않는지**(21.6절)
- 출국일 달력에서 **어제 이전이 눌리지 않는지**, 오늘은 고를 수 있는지

### 24.6 화면 모드 행에는 hover 반응이 아예 없습니다 (2026-08-28)

사용자가 "프로필 hover시 shadow로 효과라도 줘 너무 아무것도 없어"라고 했습니다. 확인해 보니 실제로 아무것도 없습니다.

| 행 | 지금 hover 반응 |
|---|---|
| 화면 모드 (`.settingRow`) | **없음.** hover 규칙 자체가 없습니다 |
| 알림 (`.settingRowStatic`) | 없음 (누를 수 없는 행이라 정상) |
| 국가 변경 (`.settingRowButton`) | `--sunken` 배경 |
| 출국일 (`.settingRowDate`) | `--sunken` 배경 |

21.6절에서 화면 모드의 hover 배경을 뺀 뒤 남은 것은 토글 글자의 `scale(0.97)`뿐인데, **텍스트만 있는 요소의 3퍼센트 축소는 눈에 잡히지 않습니다.** 색을 쓰지 않는 대체 수단을 골랐지만 그 수단이 너무 약했습니다.

24.3절의 번지는 그림자를 **화면 모드 행에도 반드시 적용합니다.** 그리고 눈에 띄는 세기여야 합니다 — "약간 약간"은 blur 반경이 과하지 않아야 한다는 뜻이지, 반응이 없는 것처럼 보이라는 뜻이 아닙니다.

21.6절의 규칙은 그대로입니다: 화면 모드 행은 hover에서 **색을 바꾸지 않습니다.** 그림자는 색 변화가 아니므로 두 조건이 함께 성립합니다.

누를 수 없는 알림 행에는 넣지 않습니다.

## 25. 할 일 추가 시트의 흐름을 다시 짭니다 (2026-08-28)

사용자가 "할 일 탭에서 +를 눌렀을 때 흐름이 너무 어색해"라며 세 가지를 지시했습니다. 추천을 제목 밑에 두고, 추천을 누르면 바로 추가되는 것이 아니라 그 내용이 제목에 들어가게 하고, 마감 고정 선택지는 없애고 날짜 직접 선택만 남기는 것입니다.

### 25.1 지금이 어색한 이유

추천을 누르면 **그 자리에서 곧바로 목록에 추가됩니다.** 그래서 시트 안에 서로 다른 두 개의 완료 동작이 있습니다 — 추천을 누르는 것과 등록하기를 누르는 것입니다. 제목을 적다가 추천을 누르면 적던 것이 사라지지도 않고 추가되지도 않아, 무엇이 등록될지 알 수 없습니다.

추천은 **제목을 채우는 보조 수단**이지 별도의 등록 경로가 아닙니다.

### 25.2 새 순서

| 순서 | 내용 |
|---|---|
| 1 | 제목 입력 |
| 2 | **추천** — 제목 바로 밑 |
| 3 | 언제 할 일인가요 (출국 전 / 현지 정착) |
| 4 | 마감 — **날짜 직접 선택만** |
| 5 | 등록하기 / 취소 |

등록하는 길은 **등록하기 하나뿐입니다.**

### 25.3 추천을 누르면

- 그 항목의 제목이 **제목 입력칸에 들어갑니다.** 목록에 추가되지 않습니다.
- 누른 항목은 **고른 상태로 표시**됩니다. 어느 것을 골랐는지 보여야 합니다.
- 그 항목의 **단계에 맞춰 출국 전 / 현지 정착 선택이 자동으로 바뀝니다.** 출국 전 항목을 골랐는데 현지 정착으로 등록되면 안 됩니다.
- 다른 추천을 누르면 **교체**됩니다. 두 개가 동시에 골라지지 않습니다.

### 25.4 등록할 때 조사 내용이 함께 들어갑니다

추천을 고른 상태로 등록하면, 23.3절대로 원본의 **`body`·`items`·`sourceUrl`·`tag`** 가 함께 들어가고 `id`도 원본 id를 씁니다. **제목만 남기고 나머지를 버리면 안 됩니다** — 출처가 빠지면 근거 없는 제목만 남습니다.

고른 상태가 풀리는 경우는 두 가지입니다. 둘 중 하나라도 일어나면 **평범한 직접 추가 할 일**이 되고, `id`도 새로 만든 값을 씁니다.

- 이용자가 **제목을 직접 고쳤을 때.** 다른 할 일을 적으려는 것이므로 원본 내용을 따라 붙이면 안 됩니다.
- 이용자가 **단계를 직접 바꿨을 때.**

### 25.4-1 "추천" 소제목을 없앱니다

사용자가 "추천이라는 소제목도 없애"라고 지시했습니다. 제목 입력 바로 밑에 항목들이 곧바로 놓입니다.

**보이는 글자만 없애고, 화면 낭독기용 이름은 남깁니다.** 소제목이 사라지면 이 버튼 묶음이 무엇인지 설명하는 것이 아무것도 없어져, 눈으로 화면을 보지 않는 이용자는 제목칸 밑의 버튼들이 왜 있는지 알 수 없습니다. 묶음에 `aria-label`을 두되 화면에는 그리지 않습니다.

소제목이 빠진 만큼 제목 입력과 항목들 사이 간격으로 두 영역을 구분합니다.

### 25.5 마감은 날짜 직접 선택만 남깁니다

고정 선택지(오늘까지·이번 주·이번 달·도착 후)를 **없앱니다.** `DueOption`과 `addTaskDue` 관련 상태·전달 경로도 함께 정리합니다.

- 마감은 **선택 사항**입니다. 비워 두고 등록할 수 있습니다("제목만 있어도 등록됩니다"는 그대로입니다).
- 마감을 넣으면 `deriveDueDisplay`가 `meta`·`week`·`urgent`를 계산합니다(22절). 비워 두면 세 값 모두 넣지 않습니다.
- 마감 날짜의 `min`은 오늘 그대로 유지합니다(20.13절 8번). **출국일과 혼동하지 마세요** — 출국일은 24.4절대로 과거를 허용합니다.
- 고정 선택지가 없어지면서, 홈의 "이번 주 할 일"에 뜨는 유일한 경로는 **마감 날짜를 오늘부터 7일 안으로 고르는 것**이 됩니다. 22.5절이 남기려던 "이용자가 직접 고른 이번 주"가 이제 날짜로만 표현됩니다.

### 25.6 확인할 것

- 추천을 누르면 **제목칸이 채워지기만 하고 목록에 추가되지 않는지**
- 추천을 누르면 단계가 그 항목에 맞게 바뀌는지, 다른 추천을 누르면 교체되는지
- 추천을 고른 채 등록하면 상세에 **본문·준비물·출처**가 다 있는지 (새로고침 후에 확인)
- 추천을 고른 뒤 **제목을 고쳐서** 등록하면 조사 내용이 따라붙지 **않는지**, id도 새 값인지
- 마감을 비운 채 등록되는지, 그 할 일에 마감 자리가 비어 있는지
- 마감을 3일 뒤로 넣으면 홈의 "이번 주 할 일"에 뜨고 8일 뒤면 안 뜨는지
- 고정 선택지 버튼이 화면에서 **사라졌는지**, 관련 상태가 코드에 남아 있지 않은지

### 25.7 추천 항목의 오른쪽 버튼을 자료 보기로 바꿉니다 (2026-08-28)

사용자가 "추천 부분이 타이틀 바로 아래에 간격을 조금만 띄우고 붙게하고 오른쪽 +버튼 대신 !같은 버튼을 만들어서 그걸 클릭하면 우리가 준비했던 자료가 나오도록해"라고 지시했습니다.

#### 간격

25.4-1절에서 "소제목이 빠진 만큼 간격으로 두 영역을 구분한다"고 적었는데, **그 간격을 줄입니다.** 제목 입력 **바로 아래에 붙듯이** 놓되 맞닿지는 않을 정도만 띄웁니다. 추천이 제목을 채우는 보조 수단이라는 관계가 붙어 있는 거리로 드러나야 합니다.

#### 오른쪽 버튼

지금 각 추천 항목 오른쪽에 있는 `+`를 **`!`로 바꿉니다.** 하는 일도 달라집니다.

| 누르는 곳 | 하는 일 |
|---|---|
| 항목 제목 부분 | 그 제목이 **제목 입력칸에 들어갑니다**(25.3절) |
| 오른쪽 `!` 버튼 | **조사해 둔 자료를 보여줍니다** |

`+`는 "누르면 추가된다"는 뜻이라 25절에서 바꾼 흐름(등록하는 길은 등록하기 하나)과 맞지 않습니다. 없애는 것이 맞습니다.

#### 자료를 어떻게 보여주는가

**그 항목 바로 아래에 펼칩니다.** 시트 위에 또 다른 시트를 띄우지 않습니다 — 할 일 추가 시트 자체가 이미 바텀 시트라, 그 위에 겹치면 어디로 돌아가는지 알 수 없어집니다.

- 펼쳐지는 내용은 원본의 **`body`·`items`·`sourceUrl`** 입니다. 상세 화면에서 보여주는 것과 같은 자료입니다.
- **한 번에 하나만 펼칩니다.** 다른 항목의 `!`를 누르면 이전 것은 접힙니다.
- 다시 누르면 접힙니다.
- 펼치는 것은 **고르는 것이 아닙니다.** 자료를 봤다고 해서 제목이 채워지거나 단계가 바뀌지 않습니다.
- 시트 안에서 펼쳐지므로 **시트가 길어지면 스크롤로 닿을 수 있어야 합니다.**

#### 접근성

- `!` 버튼에 `aria-label`을 답니다. 글자 하나만으로는 무엇을 하는 버튼인지 알 수 없습니다. 항목 이름을 포함해 어느 항목의 자료인지 구분되게 합니다.
- `aria-expanded`로 펼침 상태를 알립니다.
- `!`는 보통 경고를 뜻하는 기호라, **위험을 알리는 색(`--alert`)을 쓰지 않습니다.** 읽을 거리가 있다는 표시이지 경고가 아닙니다.

#### 확인할 것

- 제목 입력과 추천 사이 간격이 좁아졌는지, 맞닿지는 않는지
- `!`를 누르면 그 항목 아래에 본문·준비물·출처가 펼쳐지는지
- 다른 항목의 `!`를 누르면 이전 것이 접히는지, 같은 것을 다시 누르면 접히는지
- `!`를 눌러도 제목칸이 **채워지지 않는지**, 단계가 바뀌지 않는지
- 펼친 상태에서 시트가 길어져도 **스크롤로 등록하기까지 닿는지**
- 항목 제목을 누르면 여전히 제목칸이 채워지는지

## 26. 목록 행의 좌우 여백을 맞춥니다 (2026-08-28)

사용자가 "홈 우측 사이드바 아이템 우측에 준 만큼 좌측에도 패딩 넣어 그리고 할 일에도 좌측에만 패딩 들어간 것 같이 보이니까 똑같이 맞춰"라고 지시했습니다.

두 곳이 **서로 반대 방향으로** 어긋나 있습니다. 1440px에서 잰 값입니다.

| | 좌 | 우 | 원인 |
|---|---|---|---|
| 홈 우측 패널 메모 행 | 이름 텍스트 **0px** | **32px** | 삭제 버튼이 `visibility: hidden`이라 안 보여도 자리를 차지합니다 |
| 할 일 목록 행 | 시각 원 **13px** | 화살표 **4px** | 48px 체크 영역 안에 22px 원이 중앙 정렬되어 13px이 생깁니다 |

### 26.1 홈 우측 패널 — 휴지통이 밀고 들어옵니다 (26.1 대체, 2026-08-28)

처음에는 왼쪽에 여백을 넣어 오른쪽 32px과 맞추려 했으나, 사용자가 다른 방향을 지시했습니다.

> "홈 탭에 내 메모 아이템 패딩을 그냥 둘다 처음에는 없다가 마우스를 올리면 휴지통 아이콘이 오른쪽에서 나오면서 자연스럽게 날짜가 밀리는 느낌으로 만들어 hover가 끝나면 다시 돌아가고"

**여백을 채우는 대신, 비어 있던 32px 자체를 없앱니다.** 그 32px은 삭제 버튼이 `visibility: hidden`으로 숨어도 자리를 차지해서 생긴 것이었습니다.

| 상태 | 모습 |
|---|---|
| 평상시 | 좌우 여백 **둘 다 없음**. 이름은 왼쪽 끝, 날짜는 오른쪽 끝 |
| 마우스를 올림 | 휴지통이 **오른쪽에서 밀고 들어오고**, 날짜가 왼쪽으로 밀립니다 |
| 마우스가 떠남 | 휴지통이 다시 들어가고 날짜가 제자리로 돌아옵니다 |

구현에서 지킬 것입니다.

- `visibility: hidden`은 **자리를 차지하므로 쓰지 않습니다.** 숨어 있을 때 폭이 0이어야 날짜가 오른쪽 끝까지 갑니다.
- 날짜가 밀리는 것이 **부드럽게 이어져야 합니다.** 폭이 0에서 제 크기로 늘어나는 동안 날짜가 따라 움직입니다. 튀듯이 자리를 바꾸면 안 됩니다.
- 이름과 날짜 사이 간격도 함께 자연스러워야 합니다. 이름이 길면 줄어드는 쪽은 이름입니다.
- `prefers-reduced-motion`에서는 전환 없이 곧바로 나타나고 사라집니다.
- 마우스가 휴지통 위에 있는 동안에도 **계속 보여야 합니다.** 나타나자마자 커서가 그 위에 올라가 사라지면 누를 수 없습니다.

터치 기기에서는 이 버튼에 닿을 수 없지만, 메모 탭(`NotesScreen`)의 삭제 버튼이 **항상 보이고 48×48**이라 지우는 길은 열려 있습니다. 사용자가 "애초에 눌러서 삭제 가능하고 모바일에서는 이 디자인이 좀 더 나은 것 같다"고 확인했습니다.

### 26.2 할 일 목록

여기는 반대입니다. 왼쪽에는 13px이 있는데 오른쪽 화살표는 4px까지 붙어 있습니다.

**오른쪽을 왼쪽에 맞춥니다.** 왼쪽 13px은 체크 원의 터치 영역(48px)에서 자연히 나오는 값이므로 건드리지 않고, 오른쪽 화살표가 같은 거리만큼 떨어지게 합니다.

체크 원의 **터치 영역 48px은 줄이지 않습니다.** 손가락으로 누르는 곳이라 좁히면 안 됩니다. 여백은 화살표 쪽에서만 조정합니다.

### 26.3 확인할 것

- 홈 우측 패널에서 메모 이름의 좌여백과 삭제 버튼의 우여백이 **같은지**, 마우스를 올렸을 때와 아닐 때 모두 같은지
- 행에 마우스를 올렸을 때 배경이 여백 바깥까지 덮는지
- 할 일 목록 행에서 시각 원의 좌여백과 화살표의 우여백이 **같은지**
- 체크 버튼의 터치 영역이 여전히 48px인지
- 홈의 "이번 주 할 일" 목록에도 같은 행이 쓰이므로 그쪽도 함께 맞는지
- 모바일 폭(390px)에서도 양쪽이 같은지

### 25.8 추천 항목이 디자인 토큰을 쓰지 않고 있습니다 (PM 실측, 2026-08-28)

사용자가 "할 일 추가에 워킹홀리데이 비자 신청이나 건강보험 가입이 타이틀 칸에 비해 너무 강한 채도를 가지고 있어 약간 낮은 색으로 해줘"라고 지시했습니다.

재 보니 원인이 채도 조절보다 근본적입니다. **추천 항목 버튼에 `color`가 지정되어 있지 않습니다.**

| 화면 모드 | 추천 항목 실측 | 제목 입력칸(`--strong`) |
|---|---|---|
| 다크 | `rgb(255, 255, 255)` 순백 | `#f2f3f1` |
| 라이트 | `rgb(0, 0, 0)` 순흑 | `#121312` |

브라우저의 버튼 기본 글자색(`buttontext`)이 그대로 나오고 있습니다. 다크 모드에서 흰색이라 우연히 봐줄 만했을 뿐, 토큰 체계 밖에 있습니다. P-07(버튼이 Arial로 렌더되던 문제)과 같은 계열입니다 — **버튼은 UA 기본값이 상속을 이깁니다.**

같은 영역의 `!` 버튼은 `--text`(`#b7bab6`)로 제대로 들어가 있습니다.

**추천 항목의 글자색을 `--text`로 지정합니다.** 제목 입력칸이 쓰는 `--strong`보다 한 단계 낮아, 사용자가 요청한 "약간 낮은 색"이 되는 동시에 **추천은 제목을 채우는 보조 수단**이라는 25절의 위계와도 맞습니다.

고른 상태로 표시될 때는 `--strong`으로 올려 무엇을 골랐는지 드러냅니다.

확인할 것: 다크와 라이트 **양쪽에서** 추천 항목의 색이 토큰값과 일치하는지, 제목 입력칸보다 옅은지, 고른 항목만 진해지는지.

### 26.4 메모 카드의 hover 배경이 둥근 모서리 밖으로 나옵니다 (2026-08-28)

사용자가 "메모탭에서 메모를 hover하면 직사각형의 사각형이 보여 부모 박스에 overflow를 적용해"라고 지시했습니다. 진단이 맞습니다.

744px 이상에서 `.row`는 모서리가 둥근 카드가 됩니다(`border-radius: 16px`, `background: var(--surface)`, `border: 1px solid var(--line)`). 그런데 그 안의 `.rowMain`이 hover에서 받는 `--sunken` 배경에는 둥글기가 없어, **각진 사각형이 카드의 둥근 모서리를 덮고 튀어나옵니다.**

`.row`에 `overflow: hidden`을 넣어 자식이 카드 모양대로 잘리게 합니다.

**다만 `overflow: hidden`은 요소 바깥으로 그려지는 것을 전부 자릅니다.** `:focus-visible`의 외곽선이 요소 밖에 그려지면 함께 잘려, 키보드로 옮겨 다닐 때 지금 어디에 있는지 알 수 없게 됩니다. 외곽선이 안쪽에 그려지도록(`outline-offset`을 음수로) 함께 손봅니다.

확인할 것: 744px 이상에서 메모 카드에 마우스를 올렸을 때 **네 모서리가 모두 둥근지**, 키보드 `Tab`으로 옮겼을 때 **초점 표시가 보이는지**, 모바일 폭에서 기존 모습이 그대로인지.

## 27. 할 일 행을 토글 하나로 만듭니다 (2026-08-28)

사용자가 "할 일탭에는 이제 상세보기 같은거 없어도 괜찮아 오른쪽 화살표 제거하고 눌렀을때 상세페이지 나오는거 제거해 그리고 지금 원형 버튼과 분리되어 있는데 할 일 영역을 누르면 원형 버튼이 눌리도록 만들어"라고 지시했습니다.

### 27.1 행 전체가 완료 토글이 됩니다

지금 `ListRow`는 체크 원 버튼과 본문 버튼이 형제로 나뉘어 있습니다(7절). 체크는 토글, 본문은 상세 열기였습니다. 이제 **하나로 합칩니다.**

- 오른쪽 화살표(`chevron`)를 **없앱니다.** 누를 곳이 없어졌으므로 남아 있으면 거짓말이 됩니다.
- **행 어디를 눌러도 완료가 토글됩니다.**
- 체크 원의 터치 영역 48px은 그대로 두되, 행 전체가 눌리므로 원 바깥을 눌러도 같은 동작입니다.
- `aria-pressed`로 완료 여부를 알리고, 이름은 "○○ 완료로 표시하기 / 완료 취소하기"를 유지합니다. 행이 하나의 버튼이 되므로 **버튼 안에 버튼이 들어가면 안 됩니다.**

### 27.2 삭제 경로가 끊깁니다 — 행에 휴지통을 둡니다

**21.4절에서 할 일 삭제 버튼을 상세 화면에 두었습니다.** 상세로 가는 길을 막으면 지울 방법이 사라집니다. 이제 목록에 있는 할 일은 전부 이용자가 직접 넣었거나 추천에서 고른 것(23절)이라, 지울 수 없으면 잘못 넣은 항목이 영영 남습니다.

**메모 행과 같은 방식으로 행에 휴지통을 둡니다**(26.1절). 사용자가 그 방식을 두 번 확인했으므로 같은 어휘를 씁니다.

- 평상시에는 폭이 0이고, 마우스를 올리면 오른쪽에서 밀고 들어옵니다.
- 터치 기기에서는 `NotesScreen`처럼 **항상 보입니다.**
- 휴지통은 토글과 **별개 버튼**이므로, 눌러도 완료가 토글되면 안 됩니다.
- 삭제는 기존 확인 시트를 그대로 거칩니다(21.4절).

### 27.3 상세 화면은 홈의 다음 할 일 카드에서만 엽니다

`TaskDetailScreen`을 **지우지 않습니다.** 조사해 둔 본문·준비물·출처를 볼 수 있는 곳이 거기뿐입니다. 홈의 다음 할 일 카드("지금 하기")에서 여는 길은 남깁니다.

홈의 "이번 주 할 일" 목록도 같은 `ListRow`를 쓰므로, 그쪽 행들도 **상세를 열지 않고 토글만 합니다.**

사용자가 상세 화면 자체를 없애길 원하면 다시 알려주기로 합니다.

### 27.4 확인할 것

- 할 일 행에서 화살표가 **사라졌는지**
- 행의 왼쪽 끝·가운데·오른쪽 끝을 각각 눌렀을 때 **모두 완료가 토글되는지**, 상세가 열리지 않는지
- 휴지통을 눌렀을 때 완료가 토글되지 **않고** 확인 시트가 뜨는지
- 마우스를 올리면 휴지통이 밀고 들어오고 떠나면 돌아가는지, 터치 폭에서는 항상 보이는지
- 홈의 "이번 주 할 일" 행도 상세를 열지 않는지
- 홈의 다음 할 일 카드에서는 여전히 상세가 열리는지
- 버튼 안에 버튼이 없는지(중첩된 `<button>`이 없는지)
- 키보드 `Tab`으로 행과 휴지통에 각각 닿고 `Enter`로 동작하는지

## 28. "먼저 간 사람들이 힘들어한 것"의 설명글을 통일합니다 (2026-08-28)

사용자가 "홈탭에 먼저 간 사람들이 힘들어한 것에 작은 설명글로 1가지 2가지 이렇게 나오는데 이거 '자주 나온 어려움'으로 전부 통일해"라고 지시했습니다.

### 29.1 텔레메트리 규칙 확인

`SecurityReview.md` 2절 3번에 **"어떤 형태로든 외부로 텔레메트리를 보내는 SDK를 추가할 때는, localStorage/상태 값이 페이로드에 섞이지 않는지 확인하고 PM 승인을 받는다"** 는 원칙이 있어 도입 전에 확인했습니다.

## 30. 없앤 기능을 가리키는 문구와 확인 방식을 정리합니다 (2026-08-28)

PM이 코드를 훑어 찾은 두 가지입니다.

### 30.1 "문서 탭"을 가리키는 문구를 고칩니다 (완료)

16절에서 문서 저장 기능을 없앴는데, 조사 데이터에 그 탭을 찾아가라는 안내가 남아 있었습니다. **존재하지 않는 곳으로 이용자를 보내고 있었습니다.**

| 위치 | 전 | 후 |
|---|---|---|
| `au-insurance`의 준비물 | `증서 저장` | `가입 증서 보관` |
| `au-g-insurance`의 요점 | `증서는 문서 탭에 저장해 둡니다` | `가입 증서는 입국 심사에서 보여줄 수 있게 준비해 둡니다` |

**사실 관계는 건드리지 않았습니다.** 비자 조건 8501, OVHC, 체류 기간 전체 보장 같은 조사된 내용과 출처 링크는 그대로입니다. 바꾼 것은 앱 안에서 어디로 가라는 안내 문구뿐입니다. 캐나다·일본 데이터에는 같은 참조가 없습니다.

### 30.2 파괴적 동작의 확인 방식을 하나로 모읍니다

되돌릴 수 없는 동작의 확인이 두 가지 모습으로 갈려 있습니다.

| 동작 | 지금 | 바꿀 것 |
|---|---|---|
| 할 일 삭제(목록·상세) | `ConfirmSheet` | 그대로 |
| 메모 삭제 | `window.confirm` | **`ConfirmSheet`** |
| 프로필 사진 삭제 | `window.confirm` | **`ConfirmSheet`** |

브라우저 기본 대화상자는 디자인 토큰·서체·화면 모드를 전혀 따르지 않아 앱 밖에서 튀어나온 것처럼 보입니다. 같은 위험도의 동작이 서로 다른 모습으로 확인을 받으면, 이용자는 어느 쪽이 더 위험한 동작인지 모습만으로 판단할 수 없게 됩니다.

구현은 27.2절에서 만든 방식을 그대로 따릅니다.

- `useWabiApp`에 **`pendingDeleteNoteId`** 와 **`pendingAvatarClear`** 를 두고, 시트는 `WabiApp` 셸 레벨에서 렌더합니다. 메모 삭제는 홈 우측 패널과 메모 탭 두 곳에서 시작되므로 공용으로 두어야 합니다.
- 실제 삭제와 저장은 기존 함수를 **그대로 재사용**합니다. 저장 실패 시 알리고 시트를 닫지 않는 24.1절 동작도 유지합니다.
- 딤 클릭은 **취소와 같습니다**(20.11-2절). `mousedown`과 `mouseup`이 둘 다 딤일 때만 닫힙니다.
- 문구는 할 일 삭제 시트와 같은 결로 씁니다 — 무엇을 지우는지 밝히고 "삭제하면 되돌릴 수 없습니다"를 덧붙입니다.

**`window.alert`는 그대로 둡니다.** 저장 실패를 알리는 용도이고 선택을 요구하지 않아, 확인 시트와 성격이 다릅니다. 지금 손대면 범위가 커집니다.

### 30.3 확인할 것

- 메모 삭제와 프로필 사진 삭제에서 **브라우저 기본 대화상자가 더 이상 뜨지 않는지**(자동화에서 `dialog` 이벤트 0건)
- 두 시트가 할 일 삭제 시트와 **같은 모습인지**, 다크·라이트 양쪽에서 토큰을 따르는지
- 취소하면 **지워지지 않는지**, 확인하면 지워지는지, 새로고침 후에도 결과가 유지되는지
- 홈 우측 패널과 메모 탭 **양쪽에서 시작한 삭제가 모두 동작하는지**
- 저장이 실패하면 알리고 시트가 닫히지 않는지
- 딤을 클릭했을 때 취소로 동작하는지

## 31. 쓰이지 않던 Button 컴포넌트를 지웁니다 (2026-08-28)

`Button`은 디자인 시스템 11종 중 하나였지만 **앱 화면 어디에서도 쓰이지 않았습니다.** 각 화면이 자기 module CSS의 버튼 클래스를 쓰고 있어 겹치는 자리가 없었습니다. 사용자가 지우기로 정했습니다.

## 32. 메모가 많아지면 오른쪽 패널이 무너집니다 (2026-08-28)

사용자가 "오른쪽 사이드 메뉴에 내 메모가 많아지면 레이아웃이 깨지는 문제가 있어 일정 높이부터는 스크롤로 볼 수 있도록해야할 것 같아"라고 지적했습니다.

### 32.1 무엇이 일어나고 있는가

1440×900에서 잰 값입니다.

| 메모 수 | `.inner` 상자 높이 / 실제 내용 높이 | 목록 아래 끝 | "먼저 간 사람들이 힘들어한 것" |
|---|---|---|---|
| 1개 | 808 / 808 | 429 | 84px (정상) |
| 12개 | 808 / **824** | 784 | **48px** (내용 64가 48로 눌림) |
| 40개 | 808 / **2185** | **2145** | y=2167 — 패널 밖 |

두 가지가 겹쳐 있습니다.

- `.inner`는 높이가 808로 정해지는데 `overflow: visible`이라 **내용이 상자 밖으로 흘러넘칩니다.**
- 넘치는 압력을 받으면 **먼저 간 사람들이 힘들어한 것 카드가 먼저 찌그러집니다.** flex 항목이라 줄어들 수 있기 때문입니다. 메모 12개만 되어도 84px 카드가 48px로 눌려 글자가 잘립니다.

40개에서는 패널 자체가 스크롤되긴 하지만(`scrollHeight` 2231), 그러면 **"내 메모" 제목과 입력칸까지 함께 위로 사라집니다.** 메모를 보려고 내리면 적을 곳이 없어집니다.

### 32.2 어떻게 고치는가

**목록만 스크롤합니다.** 나머지는 제자리에 있습니다.

| 요소 | 처리 |
|---|---|
| 제목("내 메모") · 입력칸 · 저장하기 | **줄어들지 않습니다**(`flex: none`) |
| 메모 목록 | **남는 높이를 채우고 넘치면 스크롤**합니다 |
| 먼저 간 사람들이 힘들어한 것 | **줄어들지 않습니다**(`flex: none`). 지금 이것이 먼저 찌그러지는 것이 문제입니다 |

구현에서 놓치기 쉬운 것이 있습니다.

- 목록에 **`min-height: 0`이 반드시 필요합니다.** flex 항목의 `min-height` 기본값은 `auto`라 내용보다 작아지지 않고, 그래서 목록이 줄지 않고 형제(힘들어한 것 카드)가 대신 눌립니다. 26.1절에서 삭제 버튼의 `min-width: auto` 때문에 폭이 0이 되지 않던 것과 **같은 함정**입니다.
- `.inner`가 패널 높이를 실제로 채우도록 세로 방향 흐름을 정리합니다. 지금은 높이만 808로 잡히고 내용이 밖으로 흘러넘치는 상태입니다.
- 화면이 아주 낮아 고정 요소만으로도 넘칠 때를 대비해, 목록에 **최소 높이를 두고** 그때는 패널 전체가 스크롤되도록 남겨 둡니다. 목록이 0이 되어 아무것도 안 보이면 안 됩니다.
- 스크롤이 생겨도 **패널 폭(336)과 접기 전환(20.7절)은 그대로**여야 합니다. 스크롤바가 폭을 밀어내면 접힘 애니메이션이 틀어집니다.

### 32.3 확인할 것

- 메모 1개·12개·40개에서 **"먼저 간 사람들이 힘들어한 것" 카드 높이가 모두 같은지**(지금은 84 → 48로 눌립니다)
- 메모 40개에서 **목록만 스크롤되고** 제목·입력칸·저장하기·힘들어한 것 카드는 제자리인지
- 목록을 끝까지 내렸을 때 마지막 메모가 잘리지 않는지
- 뷰포트 높이 900·700·560에서 각각 목록이 보이는지(0으로 접히지 않는지)
- 패널 폭이 336 그대로인지, 접기 전환이 여전히 부드러운지
- 메모가 0개일 때 빈 문구가 그대로 보이는지

## 33. 자료를 펼치면 제목 입력칸이 찌그러집니다 (2026-08-28)

사용자가 "할 일 추가에 !를 누르면 title input 높이가 줄어들어"라고 지적했습니다. 1440×900에서 잰 값입니다.

| | 시트 높이 | 제목 입력칸 | 마감 입력칸 |
|---|---|---|---|
| `!` 누르기 전 | 634 | **54** | 54 |
| `!` 누른 후 | **774** (= `max-height` 한계) | **23** | 54 |

### 33.1 원인

시트는 `display: flex; flex-direction: column`에 `max-height: 774px`인데 **`overflow-y: visible`** 입니다. 자료가 펼쳐져 내용이 한계를 넘자, 스크롤할 곳이 없으니 **줄어들 수 있는 자식이 대신 눌렸습니다.** 제목 입력칸은 `flex-shrink: 1`이라 54에서 23으로 찌그러졌습니다.

**32절과 같은 계열입니다.** 세로로 쌓인 flex 상자에서 넘치는 압력을 흡수할 스크롤 영역이 없으면, 압력은 엉뚱한 형제에게 갑니다. 32절에서는 "먼저 간 사람들이 힘들어한 것" 카드가 눌렸고 여기서는 입력칸이 눌립니다.

### 33.2 어떻게 고치는가

- **시트 본문이 스크롤합니다.** 넘치는 내용은 스크롤로 보고, 자식을 찌그러뜨리지 않습니다. 스크롤 영역에는 `min-height: 0`이 함께 필요합니다(32절과 같은 이유).
- **입력칸·버튼은 줄어들지 않습니다**(`flex-shrink: 0`). 입력칸 높이는 어떤 상태에서도 54를 유지합니다.
- 시트의 손잡이·제목과 아래쪽 등록하기·취소는 **스크롤과 함께 사라지지 않는 편이 낫습니다.** 자료를 읽으려고 내렸을 때 등록할 방법이 사라지면 안 됩니다.
- 스크롤이 생겨도 시트가 **위로 열리는 애니메이션(`wabiSheetUp`)은 그대로**여야 합니다.

### 33.3 확인할 것

- `!`를 누르기 전과 후, 그리고 두 항목을 번갈아 펼친 뒤에도 **제목 입력칸 높이가 54로 같은지**
- 마감 입력칸·등록하기·취소 버튼 높이도 변하지 않는지
- 자료를 펼친 상태에서 **스크롤로 끝까지 읽을 수 있는지**, 마지막 줄이 잘리지 않는지
- 등록하기 버튼에 **스크롤 없이도 닿는지**
- 뷰포트 높이 900·700·560에서 각각 확인
- 시트 열림 애니메이션이 그대로인지(전환 도중 값을 재서 확인)

## 34. 달력을 다시 눌러 닫으면 깜빡이며 되열립니다 (2026-08-28)

사용자가 "캘린더를 열 때 버튼을 한 번 더 눌러서 끄려 하면 캘린더가 깜빡이면서 다시 켜지는 문제"를 지적했습니다.

### 34.1 원인

달력이 열린 상태에서 입력칸을 다시 누르면 **두 가지가 연달아 일어납니다.**

1. 브라우저가 바깥 클릭으로 판단해 달력을 **닫습니다.**
2. 그 클릭이 그대로 입력칸의 `onClick`에 도달해 `openDatePicker()`가 **다시 엽니다.**

닫히고 열리는 것이 한 프레임 안에서 일어나 깜빡임으로 보입니다. **닫으려는 동작이 여는 동작이 됩니다.**

### 34.2 고칠 곳

날짜 입력은 두 군데이고 **둘 다 같은 헬퍼(`src/Front/common/dom/openDatePicker.ts`)를 씁니다.** 한 곳만 고치면 둘 다 낫습니다.

| 위치 | 사용자 표현 |
|---|---|
| `AddTaskSheet`의 마감 날짜 | "할 일 마감", "+ 버튼 클릭시 나오는 마감버튼" |
| `MeScreen`의 출국일 | "프로필에 출국일 버튼" |

### 34.3 어떻게 고치는가

헬퍼가 **어느 입력칸의 달력이 열려 있는지 기억**하게 합니다. 호출부(`onClick={(e) => openDatePicker(e.currentTarget)}`)는 그대로 두어, 앞으로 날짜 입력이 늘어도 자동으로 같은 동작을 얻습니다.

- 열려 있다고 기록된 입력칸을 다시 누르면 **`showPicker()`를 부르지 않고 기록만 지웁니다.** 브라우저가 이미 닫았으므로 그대로 닫힌 채 둡니다.
- 열려 있지 않으면 지금처럼 `showPicker()`를 부르고 열렸다고 기록합니다.

**기록을 지워야 하는 순간이 세 가지 더 있습니다.** 이걸 빠뜨리면 다음 클릭에서 달력이 안 열리는 반대 방향의 결함이 생깁니다.

| 언제 | 왜 |
|---|---|
| 날짜를 골랐을 때(`change`) | 달력이 스스로 닫힙니다 |
| 입력칸이 초점을 잃었을 때(`blur`) | 다른 곳을 눌러 닫았습니다 |
| `Escape`를 눌렀을 때 | 키보드로 닫았습니다 |

기록은 **입력칸 요소 자체를 열쇠로** 보관합니다(예: `WeakSet`). 두 화면이 같은 헬퍼를 쓰고 동시에 열릴 일이 없으므로 전역 변수 하나로도 되지만, 요소별로 두는 편이 안전합니다.

`showPicker()`를 지원하지 않는 브라우저에서 포커스로 대체하는 기존 동작은 **그대로 둡니다.**

### 34.4 확인할 것

- 할 일 마감과 출국일 **양쪽에서**, 달력을 연 뒤 같은 자리를 다시 눌렀을 때 **깜빡임 없이 닫히는지**
- 닫힌 뒤 **한 번 더 누르면 정상적으로 열리는지** (기록이 남아 안 열리면 안 됩니다)
- 날짜를 고른 뒤 다시 눌렀을 때 열리는지
- 다른 곳을 눌러 닫은 뒤 다시 눌렀을 때 열리는지
- `Escape`로 닫은 뒤 다시 눌렀을 때 열리는지
- 출국일에 **과거 날짜가 여전히 선택되는지**(24.4절), 할 일 마감의 `min`은 여전히 오늘인지(20.13절 8번)

## 35. 국가 선택과 완료 표시가 저장되지 않습니다 (2026-08-28)

사용자가 "호주 캐나다 일본 중 뭘로 바꿔도 새로고침 되면 호주로 고정되네"라고 지적했습니다. 원인을 보다가 **같은 원인의 더 큰 결함**을 찾았습니다.

### 35.1 실측

| 동작 | 새로고침 후 |
|---|---|
| 국가를 일본으로 바꿈 | **호주로 되돌아감** |
| 할 일을 완료로 표시 | **해제됨** |

새로고침 뒤 `localStorage`에 있는 키는 `wabi:custom-tasks` 하나뿐이었습니다.

### 35.2 원인

두 상태 모두 저장 계층이 **아예 없습니다.**

```
const [countryCode, setCountryCode] = useState(COUNTRIES[0]?.code ?? null);  // 항상 호주로 시작
const [done, setDone] = useState(emptyDoneByCountry);                        // 항상 빈 상태로 시작
```

`toggleTask`는 메모리 상태만 바꾸고 아무 데도 쓰지 않습니다. 메모·직접 추가한 할 일·출국일·프로필 사진은 저장되는데 이 둘만 빠져 있습니다.

**완료 표시 쪽이 더 큽니다.** 준비 진행률이 이 앱의 중심인데, 할 일을 아무리 체크해도 다시 열면 처음으로 돌아갑니다. 이용자가 어디까지 했는지가 남지 않습니다.

### 35.3 어떻게 고치는가

메모·출국일과 **같은 방식**으로 저장합니다. 새 저장소를 발명하지 않습니다.

| 무엇 | 키 | 모양 |
|---|---|---|
| 고른 국가 | `wabi:country` | 국가 코드 문자열 |
| 완료 표시 | `wabi:done` | 국가별로 나눈 기록 — 지금 상태 모양(`Record<CountryCode, Record<string, boolean>>`)을 그대로 |

- **완료 표시는 반드시 국가별로 나눠 저장합니다.** 호주에서 체크한 것이 캐나다로 넘어가면 안 됩니다.
- 저장 실패 시 알리고 화면 상태를 바꾸지 않는 24.1절 동작을 따릅니다. `writeStoredNotes`와 같이 성공 여부를 돌려줍니다.
- 읽을 때 손상된 값은 걸러냅니다(`notes.ts`의 `normalize`와 같은 방식). 저장된 국가 코드가 `COUNTRIES`에 없는 값이면 무시하고 기본값을 씁니다.
- 이제 목록에 남지 않는 할 일의 완료 기록이 쌓일 수 있습니다. **지우지는 않되**(잠시 지웠다 되살릴 수 있음) 화면은 목록에 있는 할 일만 보므로 문제가 없습니다.

### 35.4 첫 화면이 깜빡이는 문제

앱은 정적으로 미리 렌더되므로, 서버가 그린 화면과 처음 클라이언트가 그린 화면이 **같아야 합니다.** 그래서 메모·출국일과 같이 **초기값은 기본값으로 두고 마운트 뒤에 저장소를 읽습니다.**

그러면 일본을 고른 이용자에게 **호주 화면이 한 번 스쳤다가 일본으로 바뀝니다.** 테마는 이 문제를 `layout.tsx`의 인라인 스크립트로 풀었습니다(첫 페인트 전에 `data-theme`을 붙입니다).

국가는 화면 내용 전체를 좌우하므로 깜빡임이 테마보다 눈에 띕니다. 다만 **인라인 스크립트로 풀 수 없습니다** — 국가에 따라 바뀌는 것은 속성 하나가 아니라 렌더 결과 전체이기 때문입니다.

그래서 이렇게 합니다.

- 저장된 국가를 읽기 전까지는 **국가에 딸린 내용을 그리지 않습니다.** 틀린 내용을 보여줬다 바꾸는 것보다 잠깐 비워 두는 편이 낫습니다.
- 비어 있는 동안 **레이아웃이 흔들리지 않아야 합니다.** 자리는 유지한 채 내용만 나중에 채웁니다.
- 이 상태는 **한 프레임 정도로 짧아야 합니다.** 로딩 표시나 스피너를 새로 만들지 않습니다.

### 35.5 확인할 것

- 국가를 일본으로 바꾸고 새로고침했을 때 **일본이 유지되는지**, 캐나다도 마찬가지인지
- 할 일을 완료로 표시하고 새로고침했을 때 **완료가 유지되는지**
- 호주에서 완료한 것이 **캐나다 목록에 영향을 주지 않는지**
- 진행률 숫자가 새로고침 뒤에도 같은지
- 저장소를 비운 첫 방문에서 **호주로 시작하는지**, 오류 없이 뜨는지
- `wabi:country`에 이상한 값(`"XX"`)을 넣고 열었을 때 **깨지지 않고 기본값으로 뜨는지**
- 첫 화면에서 **호주 내용이 스쳤다 바뀌는 깜빡임이 없는지**(전환 도중 화면을 재서 확인)
- 저장이 실패할 때 알리고 화면이 어긋나지 않는지

## 36. 날짜 입력에 누를 수 있다는 표시를 붙입니다 (2026-08-28, PM 처리 완료)

사용자가 "할 일 탭 + 누르면 나오는 마감에 cursor-pointer 없어졌어"라고 지적했습니다.

| 위치 | 전 | 후 |
|---|---|---|
| 할 일 마감 | `default` | **`pointer`** |
| 프로필 출국일 | `pointer` | 그대로 |
| 할 일 제목 | `text` | 그대로 (글을 적는 칸입니다) |

원인은 `TextField`에 `cursor` 규칙이 **아예 없던 것**입니다. 출국일은 감싼 행(`.settingRowDate`)이 `pointer`를 줘서 **우연히** 정상이었고, 할 일 마감은 감싸는 것이 없어 브라우저 기본값 `default`로 남아 있었습니다.

`TextField.module.css`에 `.field[type="date"]` 규칙을 넣어 한 곳에서 해결했습니다. 앞으로 날짜 입력을 어디에 새로 놓아도 같은 동작을 얻습니다.

## 37. 홈의 다음 할 일 카드를 정리합니다 (2026-08-28)

사용자가 "홈 탭 다음 할일 직접 등록한 일입니다 문구 삭제, 지금 하기 버튼 삭제, 버튼 자리에 대신 설정한 기한을 보여줘"라고 지시했습니다.

### 37.1 세 가지 변경

| 대상 | 처리 |
|---|---|
| "직접 등록한 할 일입니다." | **없앱니다.** 이용자가 만든 할 일에 이 문구를 지어 넣지 않습니다 |
| "지금 하기" 버튼 | **없앱니다** |
| 그 자리 | **설정한 기한**을 보여줍니다 |

**설명 문구를 지어내지 않습니다.** 지금은 이용자가 직접 만든 할 일에 `body: "직접 등록한 할 일입니다."` 를 넣고 있습니다. 아무 정보도 주지 않으면서 자리만 차지합니다. 22절에서 지어낸 `meta`를 없앤 것과 같은 이유입니다 — **이용자가 적지 않은 것을 앱이 대신 지어내지 않습니다.**

- 이용자가 만든 할 일의 `body`는 **비워 둡니다.**
- 카드에서 설명이 비어 있으면 **그 자리를 그리지 않습니다.** 빈 줄이나 대체 문구를 넣지 않습니다.
- 추천에서 고른 할 일은 조사한 본문이 그대로 있으므로 지금처럼 첫 문장을 보여줍니다.

### 37.2 기한 표시

버튼이 있던 자리에 **그 할 일에 설정된 기한**을 보여줍니다. 이미 `meta`가 그 값을 담고 있습니다(`"3일 남음"` `"오늘까지"` `"마감 지남"`).

- 기한이 없으면(마감을 정하지 않은 할 일) **그 자리를 비웁니다.** 22절과 같은 원칙입니다 — "기한 없음" 같은 문구를 만들지 않습니다.
- 마감이 지난 할 일은 지금처럼 강조 색을 씁니다.
- 이 자리는 이제 **누르는 곳이 아니므로**, 버튼처럼 보이면 안 됩니다. 테두리·배경·`cursor: pointer`를 남기지 않습니다.

### 37.3 남는 문제 — 상세 화면으로 가는 길이 사라집니다

27.3절에서 `TaskDetailScreen`을 남긴 **유일한 이유가 "홈의 다음 할 일 카드에서 여는 길"** 이었습니다. 그 버튼을 없애면 상세로 갈 방법이 앱에서 사라집니다.

그러면 **이미 추가한 할 일의 조사 내용(본문·준비물·출처 링크)을 볼 곳이 없어집니다.** 추가 시트의 `!` 버튼은 아직 추가하지 않은 추천 항목만 보여줍니다.

출처를 보여주는 것은 사용자가 직접 요청했던 기능이고("출처 표시해줘"), 23.4절에서 "출처가 빠지면 근거 없는 제목만 남는다"고 정한 바 있습니다. **어떻게 할지 사용자에게 확인받습니다.** 확인 전까지 `TaskDetailScreen`은 지우지 않고 그대로 둡니다.

### 37.4 확인할 것

- 이용자가 직접 만든 할 일이 다음 할 일 카드에 떴을 때 **설명 자리가 비어 있는지**(문구도, 빈 줄도 없는지)
- 추천에서 고른 할 일은 조사 본문의 첫 문장이 **그대로 보이는지**
- "지금 하기" 버튼이 **사라졌는지**
- 마감을 정한 할 일은 그 자리에 **기한이 보이는지**, 정하지 않았으면 비어 있는지
- 마감이 지난 할 일에 강조 색이 유지되는지
- 기한 자리가 **눌리지 않는지**(커서·테두리·배경이 버튼처럼 보이지 않는지)
- 카드 높이가 상태에 따라 들쭉날쭉하지 않은지

## 38. 상세 화면을 없앱니다 (2026-08-29)

## 39. 홈과 할 일의 정렬을 하나로 맞춥니다 (2026-08-29)

사용자가 처음에는 "홈 탭도 최신 할 일이 가장 위로"라고 했다가, 곧 **"홈과 할 일 시간 순으로 정렬하고 시간을 설정하지 않았을 때는 항상 가장 아래로"** 로 바꿨습니다. 40절이 최종 규칙입니다.

시작은 두 화면이 서로 다른 순서를 보여주던 것이었습니다.

```
phaseTasks = sortTasksForDisplay(...)          // 할 일 탭 — 정렬함
weekTasks  = allTasks.filter((task) => task.week)  // 홈 — 거르기만 함
```

저장된 순서는 만든 순(오래된 것이 먼저)이라 같은 할 일이 두 화면에서 정반대 자리에 놓였습니다. **두 화면이 같은 함수를 쓰게** 해서 어긋날 수 없게 만듭니다.

## 40. 마감이 이른 순으로, 마감 없는 것은 맨 아래로 (2026-08-29)

`sortTasksForDisplay`의 규칙을 다시 정합니다.

| 순위 | 기준 |
|---|---|
| 1 | **마감이 있는 할 일이 먼저.** 마감을 정하지 않은 것은 언제 해도 되는 일이라 뒤로 밉니다 |
| 2 | 마감이 이른 것이 위 |
| 3 | 마감이 같거나 둘 다 없으면 **최근에 만든 것이 위**(21.3절) |

### 40.1 구현에서 정한 것

- 마감일은 `yyyy-mm-dd` 형태라 **사전순 비교가 곧 날짜순**입니다. `Date`로 바꿔 비교하지 않습니다 — P-06처럼 시간대가 끼어들 여지를 만들지 않기 위해서입니다.
- 함수의 `builtinTasks`/`customTasks` 두 갈래 인자를 **없앴습니다.** 23절 이후 목록 전체가 이용자가 넣은 것이라 두 호출부 모두 빈 배열을 넘기고 있었습니다. 쓰이지 않는 갈래를 남겨 두면 다음에 읽는 사람이 그 구분이 아직 살아 있다고 믿습니다.
- **원본 배열을 바꾸지 않습니다.** `sort`는 제자리 정렬이라 복사한 뒤 정렬합니다. 이 값은 `useMemo` 결과에서 파생되므로 원본을 흔들면 다른 계산이 함께 어긋납니다.
- `createdAt`이 없는 항목도 버리지 않고 가장 오래된 것으로 취급합니다(21.2절).

### 40.2 다음 할 일 카드

`pickNextTask`는 여전히 정렬되지 않은 `allTasks`에서 완료되지 않은 첫 할 일을 고릅니다(21.3절). 목록 순서와 다른 규칙이라 이번에도 건드리지 않았고, 사용자에게 알립니다.

### 40.3 확인할 것

- 마감이 다른 할 일 여럿을 만들었을 때 **홈과 할 일 탭 모두 이른 마감이 위**인지
- 마감을 정하지 않은 할 일이 **항상 맨 아래**인지, 마감 있는 것 사이에 끼지 않는지
- 마감 없는 것끼리는 최근에 만든 것이 위인지
- 두 화면의 순서가 **완전히 같은지**
- 새로고침 후에도 같은 순서인지
- 세 시간대(Asia/Seoul·UTC·America/Toronto)에서 결과가 같은지
